# Live validation

Live validation runs the repository's documented live checks on a real Windows host and a real Linux host over SSH. The user owns the decision to start and the hosts it runs on, so the run passes a two-stage gate. A **live invocation** is one request to validate one target revision; the gate is per invocation. Cleaning up after a run belongs to that run's invocation and reuses its host agents and authorization. A standalone request to clean up what a run left authorizes the scope the user names: apply the [image cleanup](#image-cleanup) rules on that host without starting the suite, judge eligibility from the run's recorded inventory and asset hash, and ask only for an alias the request leaves missing.

## Stage 1: consent to start

The Yes/No checkpoint below is this project's workflow, set by its owner; it is not a permission the skill infers, and a request such as "run live validation" is the trigger, never the answer. For a new test invocation, ask it first, before any step on a live or remote host and before any alias step. Offline checks in the local checkout need no checkpoint. Use the host's question tool with Yes/No choices when it has one; otherwise ask in plain text with the two choices and end the turn.

> Live validation would run the documented live checks for `<change>` at revision `<sha>` on a Windows host and a Linux host over SSH. Should live validation start now?
> Choices: Yes / No

Complete when the user has answered. No answer is not consent: take no live-host or alias action while waiting.

- **Yes** authorizes this live invocation only. Continue with stage 2.
- **No, or deferred** ("later", "not now"): put `Live validation: pending (not started: <the user's words>)` in your next report, continue offline work that is still useful, and describe the change as unvalidated live, never as validated.

A Yes already given to this checkpoint in the same live invocation stays valid: resuming after an interruption, or the run's own image builds and sandbox starts, reopens nothing. A new request to validate, or a new target revision, is a new invocation and asks again.

## Stage 2: both SSH aliases

After Yes, ask for both aliases together in a prompt of its own:

> Which SSH host aliases should live validation use? Give both, as they appear in your SSH configuration.
> Windows SSH alias:
> Linux SSH alias:

- **Both given**: continue with stage 3.
- **One given**: keep it and ask for the missing one only: `Keeping the <platform> alias <alias>. Which SSH alias is the <other platform> host?`
- **Aliases named in the triggering request** belong to this invocation: after Yes, confirm them in the alias prompt (`Windows: <alias>, Linux: <alias>. Correct?`) or ask only for the missing one, never for the same text again.
- **An alias from an earlier task, session, memory, or the SSH configuration itself**, or "the same as last time": name it and ask the user to confirm it for this invocation before using it.

Complete when the user has named or confirmed both aliases in this invocation. The suite starts on neither host before then.

## Stage 3: one dedicated agent per host

After both aliases are confirmed, the session that passed the gates is the **coordinator**. It launches two **host agents** asynchronously through the host's delegation tool before waiting on either, one owning the Windows alias and one owning the Linux alias, and it runs no suite itself. Route each host agent's model with the `model-routing` skill and pass the result in the tool's target and option fields, never as a model assignment in the task text. Take every argument of the delegation call, an optional role included, from that tool's own schema as the session shows it: a routing category such as `operate` is not a tool role, so omit an optional role or select one that the tool supports. Give each launch a stable request identifier where the tool offers one, and keep it with the returned handle, so that a retry never starts a second agent for the same host. Keep each returned task handle: a second request for the same host resumes its running agent instead of starting another, and a session resumed mid-run reattaches to the handles it kept. A launch that fails marks its host `pending` with the tool's own message while any agent that did start keeps running and its result and cleanup are still collected; when neither agent can start, report `Live validation: blocked (no delegation available)` with the tool's own message. Running a host in the coordinator, or the two hosts one after the other, is not a fallback.

Give each host agent, in its brief: the target revision, its confirmed alias, that consent and both aliases are already settled so it asks no gate again, the user's constraints for this invocation, the documented checks below, the **owner connection** rule below as a mandatory item, the progress duties in step 3, for the Windows host the [Windows host queries](#windows-host-queries), the [image cleanup](#image-cleanup) rules, and both branches of the target-helper rule written into the brief as a condition, because the presence of `internal/liverun/cmd/live-run` is known only after the host agent has looked: if the target checkout has it, the helper workflow below; if it lacks it, the manual commands that the paragraph below prints. A revision that has the helper uses it, and no fallback bypasses a refusal of the helper. Dispatch is complete when both launches are accepted with a target that the tool's schema validates and a brief that carries both branches; a launch that cannot meet that marks its host `pending` as above. A host agent that reports blocked leaves the other running; the coordinator records that host as `pending` with the reason. A refusal before the suite starts, such as insufficient space, is a blocked return: the agent keeps its private preparation artifacts as they are, ends and does not linger as a worker, the other host continues, and any repair or configuration change it proposes waits for the user's decision through the coordinator, with no new permission gate.

Each host agent runs the live checks the repository documents in [docs/images.md](../../../docs/images.md) under "Live image tests", with the variables that section names (the opt-in, the dedicated controller group, the record directory, and the image selection), on its host over its alias. That section is the default workflow, and its [host commands](../../../docs/images.md#running-a-live-run-with-the-host-commands) run it through the repository's `live-run` helper in steps 1 to 5; ordinary read-only diagnostics beside it need no further consent. A target revision whose checkout lacks `internal/liverun/cmd/live-run` predates the helper: steps 1 to 5 then use the commands that section prints for the suite and the collector, with the suite in the background, its private log outside the record directory, and the exit status of `go test` kept (`${PIPESTATUS[0]}` after `set -o pipefail`, or `$LASTEXITCODE` in PowerShell). Step 6 then applies the image-cleanup rules by hand. A revision that has the helper uses it, and no fallback bypasses a refusal that the helper makes, such as `session-detachment`, a modified, untracked, or ignored file in the checkout, or a missing bound.

**Owner connection.** Before your first operation on the host, open one dedicated SSH connection to your alias, the **owner connection**, and keep it open continuously until all your assigned host work is finished: through `prepare`, `run`, every `status` poll, `collect`, `cleanup`, any assigned native check, and your final report.

- **Keepalive.** Enable client keepalive for this invocation only, on the command line (for example `-o ServerAliveInterval=30 -o ServerAliveCountMax=4`); the user's SSH configuration and the host's stay as they are.
- **Handle.** Start it as a process you own and retain its handle across model turns, background waits, and handoffs. It stays open when the helper detaches and between polls.
- **Existing owner.** Hold open the same way an SSH connection that already owns something the run depends on, such as the one that started the Windows machine.
- **Other connections.** Run bounded commands over further connections as you need them while the owner connection stays open.
- **Loss.** When the owner connection is lost, record the event with its time and the client's message, open a new owner connection, and reattach to the existing run through its private run directory and `live-run status`. A lost connection says nothing about whether the run ended: the run, its settings, and every gate stay as they were, and `live-run status` alone tells you its state.
- **Limits.** The helper's detachment, bounds, and private-log rules are unchanged, and an open connection is no proof that a run survives an abrupt disconnect. A stop from the user ends the owner connection with the rest of the work.

1. Confirm the host has a checkout at the target revision and record the SHA it reports. A missing revision is routine preparation inside the Yes: fetch it into a separate temporary checkout on the host and leave the host's existing work untouched. When the host cannot reach the revision, or access fails, report the host as `pending` with the reason; pushing source to a remote or changing the host's configuration is outside this authorization. Then build the helper in that checkout, `go build -o <private dir>/live-run ./internal/liverun/cmd/live-run` (`live-run.exe` on Windows), so that its code matches the target revision; keep its binary, the run directory, and the log in a private directory outside the checkout and outside the record directory. Its validation so far is offline tests, a Linux fixture that ends the launching session, and Windows fixtures that compile for Windows and are in the Windows pull-request test list but have not run natively, which show no behaviour on native Windows 11 or in non-administrator Windows PowerShell 5.1 and in particular not that a Windows run survives the end of its SSH session. On Windows the helper reads the launching job's limits before any engine or build query and refuses when the job offers no way out, and the supervisor refuses when it remains in an inherited job: report that `check session-detachment failed` as the helper's own message about the host's session, never as a result of the suite. Report a failure there with the helper's own message, and report a Windows run whose supervisor ended with the session as the status the helper gives (137 with `interrupted`), never as a result of the suite.
2. Before any build, record the **before** measurement and the **before** inventory defined under [Image cleanup](#image-cleanup); on Windows take them with the [Windows host queries](#windows-host-queries). Judge headroom against a conservative bound on the peak additional space the suite needs before any cleanup: the initial build of the base image and every toolchain set, the no-cache rebuild of all of them while the first set still exists, the intermediate build layers, and the writable layers of the running sandboxes. Take the bound from the peak a documented or recorded run on that host reached only when that run's documented conditions cover this run's cache state, selected toolchain sets, dependency versions (a floating release such as `npm@latest` included), and every component listed above; when the conditions are unknown or do not cover them, or no run exists, take it from a reasoned conservative estimate of those components even if an older peak exists. Never take it from net growth after cleanup or from a fixed figure. On Windows the bound must fit both the host drive that holds the machine's virtual disk and the machine's own image filesystem. When the headroom is insufficient, first remove, in one pass, the images that an earlier run's record marks eligible under those rules; that removal needs no further permission, while any repair, prune, or compaction stays outside this invocation. After any such removal, keep the earlier inventory only for the cleanup and provenance audit; take a fresh whole-engine **before** inventory and free-space measurement that replace the earlier ones as the before records, select the bound again for the post-removal state under the rule above, and recheck every measured filesystem against it, without a second removal pass. The last inventory taken before the first build is the **snapshot** of the run's start; note what else runs on the host: the **comparison context** (`host_load`, `base_image`, `build_cache`) is classified after the run from the snapshot alone, by the rules under [Retaining case durations](../../../docs/images.md#retaining-case-durations), and a value the snapshot cannot show is `unknown`. Start the suite only when the free space on every measured filesystem exceeds the bound selected for the state the build starts from, never one chosen before a removal, with one exception: no bound exists and the user has decided to proceed without one after the coordinator stated the free space and the risk that the build exhausts the host. That decision is specific to this invocation, is recorded in the report, and is not covered by the Yes of stage 1. In every other case without a reliable bound, and whenever the host's own numbers cannot be read or the space is known to be insufficient, report the host as `pending (<free> free; <bound> expected, or no reliable estimate>)` without starting the suite.
   - `live-run prepare` carries out this step: give it the exact target revision, a new private run directory, a fresh record directory, a peak record that admits a bound as `-peak-record` (the JSON file that the [host commands](../../../docs/images.md#running-a-live-run-with-the-host-commands) define: a maintainer's reasoned bound, accepted in its original three fields; the sampled facts the helper writes after a run are observations in other files and carry no bound: a sampled peak is a lower observation, never an upper bound and never the bound; only a maintainer writes the bound record, independently justifying a conservative upper bound, and sampled observations may constrain or reject it but are never an automatic upper bound), and `-host-load` only when the load was observed, otherwise leave it unknown.
   - Pass `-overlap N` and `-build-jobs N` only when the user chose them: both default to `1`, no larger value is calibrated, they are saved with the run and change no refusal, headroom, or cleanup rule, and you report the values used. For the concurrency chosen, check the engine's available CPU and memory (a capacity check, not part of the headroom bound; keep `1` if you cannot judge them), and make the disk bound you supply cover the disk bytes that the work uses at the same time, including the temporary output logs of `--jobs` above `1` on the host; serial observations alone establish neither, and on Windows a value above `1` is not advised until the #181 capacity decision permits it.
   - It takes the before measurement, the `podman system df` text, and the whole-engine before inventory in one pass and keeps them privately in `preparation.json` of the run directory, and it refuses a checkout with a modified, untracked, or ignored file (never clean the user's checkout: make a new temporary checkout at the revision, as step 1 describes, and build the helper and run every phase there), a run or record directory inside the checkout, a missing, mismatched, inadmissible, or contradicted bound (the highest sampled growth that the engine's observed-peak file retains for the filesystem exceeds it), or free space that does not strictly exceed the bound on every measured filesystem, printing for the bound only free bytes and the expected bytes: report that refusal as the `pending` line above and start no suite after a failed preparation.
   - The helper checks a record's fields and sampled constraints only, never whether its `Basis` covers this run's cache state, selected toolchain sets, and dependency versions (`npm@latest` included), and when `-peak-record` is left out it reads `KEY-peak.json` in its coordination root as the bound. Verify that the record you pass, or the default file, covers this run as the bound rule above requires, before you pass it or let the default select one. A record that does not cover the run, or whose basis does not say, is not a reliable bound: the host stays `pending` as above until a maintainer writes a covering reasoned record, which you pass with `-peak-record`. The informed no-bound decision for this invocation stays the existing exception: with it, and only when no covering record exists and you have inspected the default record and the engine's observed-peak file (each readable, or confirmed absent), `-peak-record` may name an absolute, fresh private path that you have confirmed does not exist (the helper does not create it), so the default record is not selected. Never hide, unlink, rename, or edit an existing default record, and never choose a missing path to get past an unreadable bound or observation record or a known insufficiency, including one that a readable default record shows.
   - The decision to proceed without a bound is passed as `-allow-unbounded` together with `-unbounded-decision` and the user's words of that recorded decision, passed unchanged (the host commands give the quoting; words that cannot be passed unchanged keep the host `pending`), never inferred from the Yes of stage 1, and it never covers free space that cannot be read, an existing bound or observation record that cannot be read, or known insufficiency (no free space, or a bound or a sampled growth for this engine at least as large as the free space).
   - When the headroom was insufficient and you removed, in one pass, the images that an earlier run's record marks eligible, run `prepare` again in the same private run directory after that removal (a failed `prepare` can be repeated until a `run` has been attempted): its fresh whole-engine inventory and free-space measurement replace the earlier ones as the before records, the bound is selected again for that state and never reused from before the removal, and there is no second removal pass. The repeated `prepare` replaces `preparation.json`, so before repeating it copy the rejected `preparation.json`, the current pre-removal inventory, to a distinct audit file such as `preparation-before-removal.json` in the same private run directory, and overwrite no evidence; the cleanup that did the removal also keeps its own whole-engine image inventory of that moment as the lowest-numbered `inventory-NNNNN.json` in its `cleanup-RANDOM` directory in the earlier run's private directory, and an older snapshot such as the earlier run's original `before.json` is not a fresh audit. The manual branch takes the fresh inventory and measurement the same way.
   - On Windows `live-run prepare` takes its own measurements without administrator rights; the [Windows host queries](#windows-host-queries) apply to every query you make yourself, the manual branch included.
   - The final snapshot that `live-run run` saves in `before.json` after repeating these checks is the snapshot the comparison context and the cleanup use.
3. Start the suite with `live-run run -run-dir <run dir>`.
   - It detaches from the SSH session, which stays open as the owner connection, repeats the preparation checks under the engine lock, and runs the documented live suite in verbose mode with the image selection, the dedicated group, the record directory, and `SANDBOXED_AGENTS_LIVE_STOP_AFTER_FAILURE=1`, which starts no case after the first failed one and fabricates neither coverage nor a pass.
   - The suite's **private log** is `suite.log` in the run directory, outside the record directory. When `go test` returns, the run directory holds `exit.json` and `exit-status`, the exit status as a plain integer; a run whose supervisor died reports status 137 with `interrupted`, and an interrupted run reports its non-zero status.
   - After any failed `live-run run`, use a new run directory and a new record directory, because a retry in the same run directory is refused. A `status` that shows `ended` with exit status 1, no case, and operation `unknown` right after such a failure is the supervisor's startup refusal, not a suite result, and `running` stays false while the supervisor is still preparing.
   - Run `prepare` and `run` in the same shell environment, `PATH` and Go environment included, because `run` repeats the checks in the environment it starts from. Once the suite has ended, `live-run status` also reports `log_verified`; false means the private log is incomplete, and `collect` and `cleanup` then refuse it.
   - Poll `live-run status -run-dir <run dir>` with no blocking foreground call: it returns, without a raw line, a path, or an object name, the latest observed fixed `case` and `operation`, `last_output_age_seconds`, `free_space`, and whether the suite has `ended` with its exit code. The status is the most recent observation of the case and operation, not a claim that the other cases are idle. When the suite overlaps its cases (the optional `SANDBOXED_AGENTS_LIVE_OVERLAP` above `1`), more than one operation can be in flight: the status and the last log line are the latest observation only, never a list of what is active. An `up` shows as `image build or sandbox start`, one class for its image build and its sandbox start together; read no image state and no build time into it, and report `unknown` when the status names none.
   - The log holds names, paths, and program output and stays on the host: the only excerpts that leave it are the failure text of step 4 and the operation summary of the status report.
   - Send the coordinator an event at suite start, at every change of test or operation, and at least once a minute while an operation is still running. Name the test the suite is in and the image or sandbox it is working on, and classify the observed operation from the `operation` of `live-run status`, from the last line the suite printed, or from read-only evidence such as the host's existing logs or process metadata: **image build or sandbox start** (`up`), **image archive** (the image save of the `images` case's host-key check), **sandbox start or restart** (`stop`, `start`, `restart`), **SSH server check**, **smoke** (`shell`), **update or rollback** (`update`), **agent install** (`agents enable`), **agent session** (`agents session`, its status, stop, and disable), **rebuild** (`build`), or **cleanup** (`remove`), and, while the suite's `t3code` case runs, **Tool install** (`tools enable`), **Tool update** (`tools update`, and the fixture's break and repair of a Tool installation), **Tool delete** (`tools delete`), or **Tool probe** (`tools status` and the case's read-only checks of the service's HTTP response, listener, and process identity). A silent buffer keeps its last observed operation: send that observation and its age, and never read a pass, a finished check, or a next operation into silence; the suite's own `--- PASS` or `--- FAIL` line is the only result.
4. When a preflight or check fails, report the suite's own failure text as the finding; a failed `live-run` check prints the name of the check and keeps the engine's message in its private diagnostic, so report the printed text; the `engine` check also prints a fixed kind and reason, such as `machine stopped` or `connection refused`, which is the diagnosis to report, while the raw message, paths, and names stay private; a `session-detachment` failure on Windows names a launching job that offers no breakaway, which is a host setting for the user to decide, not a repair of this invocation. A repair the user has already authorized proceeds; a Podman, WSL, or SSH configuration change outside that authorization is the user's decision: propose it through the coordinator and wait for the answer.
5. After `live-run status` shows the suite `ended`, pass or fail, collect the run's durations with `live-run collect -run-dir <run dir>` instead of calling the collector yourself. It runs the collector command of [Retaining case durations](../../../docs/images.md#retaining-case-durations) on the private log and the schema 2 record the suite wrote, takes the comparison context only from the final `before.json` snapshot together with the asset hash in the log's preflight output, and passes the run's preparation timestamps. A success is exit status 0 with `collected` true and the `durations_file` name of `durations-<platform>.json` in the record directory, beside the record; only that file is this invocation's evidence. A true `optional_operation_evidence_unverified` in the same output means the case durations are this invocation's and the optional operations file was not updated: report the durations as collected and the operations evidence as unverified. The `collect` phase takes no post-suite interval: the collection that `live-run cleanup` runs in step 6 replaces this file and carries it. Collection reads the record and changes nothing else, and a failed or interrupted run is collected from its failing record and the log as it ended. The file holds only the completion lines the log emitted; `go test -v` prints a case's line when the parent ends, so a kill or timeout that ends the test binary can leave `cases` empty, a valid file that shows no observations, never zero and never proof that no case finished. A collector failure is reported with its own message, leaves any earlier `durations-<platform>.json` in place as it was, and does not alter the suite's result: that file belongs to an earlier run, even at the same revision, and its numbers are never this run's.
6. After the suite has returned, pass or fail, and its own cleanup of sandboxes, volumes, and group state has run, remove the run's unused images as [Image cleanup](#image-cleanup) describes, with `live-run cleanup -run-dir <run dir>` (repeat `-retain sha256:<full image ID>` for each image the user asked to keep), then record the **after** measurement, which the command's report carries.
   - Its `status` is `complete`, `partial` (coverage is not established: an image absent from the before inventory that has no valid primary receipt and no revalidated known registry input stays, with its size, even when every surviving attempt is closed), or `unverified` (any malformed, lost, unconfirmed, or contradictory evidence, a vetoed receipt (reuse not excluded, an ID repeated across attempts, or an ID that is also a known input), and any failed query; it takes precedence over `partial`): report `partial` and `unverified` as such, and never remove a skipped image here.
   - A repeated `live-run cleanup` of the same run lists under `removed_earlier` each build result (an image this run built, whose build recorded the ID) that is no longer on the engine and that an earlier cleanup of that run removed, with the reason `removed by an earlier cleanup of this run`, size 0 and `size_verified` false, never as unverified. A `removed_earlier` entry never changes the status or exit status. Report each `removed_earlier` entry as removed by the earlier cleanup, never as removed again or as freed bytes. If the final inventory shows such an image again, the report adds a separate unverified item, `removed earlier but present in final inventory`: the image is on the engine again, so report it as unverified, remove nothing by hand, and leave the decision to the user. A build result missing from the engine that no counted earlier cleanup lists under `removed` stays `unverified`; see "Which earlier cleanups count" under [Running a live run with the host commands](../../../docs/images.md#running-a-live-run-with-the-host-commands). Such an image is gone, and cleanup cannot prove who removed it: report it as unverified, and neither run `live-run cleanup` again for it nor remove anything by hand. Each cleanup overwrites `cleanup-<platform>.json`, so report each cleanup's removed sizes before running it again. If you already ran cleanup again without saving a report, the overwritten report's removed sizes are no longer in `cleanup-<platform>.json`: take the IDs it removed from the latest report's `removed_earlier`, report their tags and sizes as unknown and say why, and do not copy them out of the private cleanup directory.
   - If images remain that no receipt explains, report them with their exact count and bytes. Those that appeared during the run (for example one another writer created, or a pulled base without a known input) give `partial` with a non-zero exit, and only a revalidated known registry input is reported as `not committed by this run's builds` without making the status `partial`. Images that earlier runs left, old intermediates included, were already in the before inventory: they are skipped as `present before invocation`, are never counted as part of this run or relabeled, and do not make the status `partial`. Either way such images persist across runs and reduce the headroom of the next run, and no supported path in this invocation removes them.
   - When `log_verified` is false, `live-run cleanup` stops with `cleanup: pending (private suite log unverified)`, writes no report and removes nothing: report cleanup as `pending` with that line and the run's images as left behind, and remove no image by hand.
   - A `cleanup: pending` for an unreachable engine is handled as in step 4: starting or repairing the engine is the user's decision, proposed through the coordinator, except that a repair the user has already authorized proceeds; remove no image by hand.
   - A kill or timeout that kept the suite's own cleanup from running does not defer this step: the image rules already skip any image a leftover container references, and the leftover sandboxes, volumes, and group state are reported as left behind, never removed here. The private log stays on the host with the host's other evidence.
7. Return the suite's result line, the commit it ran on, its duration, the validation record the suite wrote in the record directory (its file name and its content, which holds no host detail), the `durations-<platform>.json` from the same directory (file name and content only when this invocation's final collection succeeded, which is the `live-run cleanup` report's `collected` true with its `durations_file`, or, when that command ended before it collected, the successful `live-run collect` of step 5, which carries no post-suite interval, with an empty `cases` list reported as empty, no emitted observations; otherwise `unverified` with the collector's own message, whether or not an earlier file or one at the same revision is present; its `unknown` context values stay `unknown`), and, when the validation record lists a `t3code` check, also its supplemental `t3code-<platform>.json` from the same directory, with file name and content, whatever that check's result: `pass`, `fail`, or `not-run`.
   - A record that lists the check while the supplemental file is absent is reported as unverified, never as passed, whatever the suite's result line says, and with the failed preflight named as the likely reason when the record shows `preflight` failed.
   - Whether the check is expected depends on the target revision's suite, read from its `liveCheckNames` in `cmd/sandboxed-agents/live_test.go` or its documented cases in `docs/releases.md`: when that suite has no `t3code` case, the revision predates it, so say so and expect no supplemental file; when it has the case and the record omits the check, report the omission as unverified, never as old or not present.
   - Return also the supplemental `operations-<platform>.json` as the paragraph after the final report describes.
   - Fill the cleanup facts from the sanitized report instead of pointing at it: the removed image IDs with their tags and sizes, any `removed_earlier` IDs as removed by an earlier cleanup, with size 0 and `size_verified` false because the earlier report already counted their bytes, the skipped and unverified items (say `unknown` where the report does), and both measurements. After a rerun of `live-run cleanup`, take the status, the skipped and unverified items, and the after measurement from the latest report, and the removed sizes from every report, since each lists only what it removed; take the before measurement from the latest report as well, since it is the run's own and the same in every cleanup of the run; `post_suite_seconds` and `post_suite_total_seconds` then run from the suite's end to the latest cleanup and include the time between the cleanups, so say so beside them. `post_suite_seconds` is a lower bound that ends before the final collection and publication, never a total, and the numeric `post_suite_total_seconds` of `live-run status` is a separate figure; invent nothing that the report does not hold, and put no raw path or log line in the report.

### Windows host queries

The Windows account may be an ordinary, non-admin user. Query as that account and assume no CIM/WMI access and no `Get-Volume`; this grants no administrator permission and no change to host configuration.

- **Host drive space:** [`System.IO.DriveInfo`](https://learn.microsoft.com/en-us/dotnet/api/system.io.driveinfo.availablefreespace) `AvailableFreeSpace` for the drive that holds the machine's virtual disk. The engine inventory, `graphroot`, and the guest `df` still come from native `podman` on the selected `--connection`, as under [Image cleanup](#image-cleanup).
- **Processes:** [`Get-Process`](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/get-process?view=powershell-5.1) for your own processes' basic metadata, without `-IncludeUserName` or module data.
- **Launched queries:** start them with [`Start-Process -PassThru`](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/start-process?view=powershell-5.1) and private stdout and stderr files, or with `System.Diagnostics.ProcessStartInfo`, and keep the process object, so the PID, start time, and command are known; a blocking collector cannot say which subcommand it waits on. Bound every wait. Record each command's start, end, exit status, and artifacts as it happens. When you redirect pipes, read both streams concurrently so a full buffer cannot deadlock the query.
- **Stopping:** terminate only a query you launched, through its verified handle. Never stop an older process of unknown origin by its name or start time.
- **CIM denied:** that is an API limitation, not an engine failure and not a reason to ask for administrator rights. Use the queries above. When the full gate still cannot be measured, report `pending (<the exact missing query>)`.
- **PowerShell 5.1 JSON:** call `ConvertFrom-Json` without `-Depth`, and `ConvertTo-Json` with an explicit `-Depth` that covers the whole snapshot.


## Image cleanup

The suite removes its sandboxes, volumes, and group state and leaves every image it built. Images are shared across controller groups and executables: the marker label and the asset hash say which executable built an image, not who owns it, so they never make an image disposable on their own. A rebuild moves a tag to the new image and leaves the previous one untagged, still backing any sandbox created from it. Repeated no-cache rebuilds therefore fill a host; the project's Windows host has a 100 GB drive.

**Measurement.** Record, as text in the host agent's report: the free space of the filesystem that holds Podman's storage (on Windows the host drive that holds the machine's virtual disk and, through the selected connection, the machine's own image filesystem), and `podman system df` for the same engine. Take it before any build and again after cleanup.

**Inventory.** Enumerate every image ID with `podman images --all --no-trunc` (a tag or digest is not an ID), read each image's labels and creation time with `podman image inspect`, and enumerate every container with `podman ps --all`, then read the image ID each one references from `podman container inspect` (the `ps` image column may show a name or tag), for the whole engine, not one group. Take it before any build. Keep this invocation's build output and record from it the exact full image ID of every image its build steps produced, with the step or result each ID came from; resolve any shortened ID against the engine's full IDs and keep it only when it resolves to exactly one image, then confirm it against `podman image inspect` and the before inventory. That record is the only proof that an image belongs to this invocation; the asset hash, the creation time, and the difference between inventories are not.

**Eligible for removal.** An image is eligible when all of these hold: it is absent from the before inventory; its full ID is in this invocation's build record; it carries this invocation's asset hash where the build labels one; no container on the engine, in any group, references it after the suite's own cleanup; and the user has not asked to keep it. That holds for every eligible image, an untagged image the rebuild superseded or an intermediate ancestor included: its full ID must be traced to this invocation's build output. The engine's verified parent chain only corroborates ownership or supersession of an ID already in the record; an ancestor seen only in a chain, or tied only by a matching hash or creation time, stays, even when that skips an image this invocation did create. An image present before the run, shared by other sandboxes, created by a concurrent workflow, matched by more than one candidate, or whose provenance the record cannot show stays, named as skipped. A query that fails leaves the image unverified, never absent.

**Removal.** Remove eligible images one by one by ID, toolchain images before the base image they depend on, with `podman rmi --no-prune <id>` and no `--force`; on Windows through the selected `--connection`. `--no-prune` keeps the dangling parents of the removed image, so an ancestor the build record does not prove stays in place instead of being removed by the engine's cascade; a proven parent is removed by its own ID after its children. Never run `podman image prune`, `podman system prune`, `podman system reset`, or any host-wide removal, and never delete, compact, or reconfigure a machine, its virtual disk, or WSL: those are host configuration changes with their own authorization. Keep the host's logs, checkouts, and evidence files. When the engine is unreachable, report `cleanup: pending (engine unreachable: <message>)` and stop.

**Reporting.** List removed IDs with their tags and sizes, skipped IDs with the reason, unverified items with the failing query, and the before and after measurements. A retention the user asked for is honoured and its disk cost reported. This cleanup is part of the authorized invocation and opens no new checkpoint.

Apply these unchanged rules after the suite has ended with `live-run cleanup -run-dir PRIVATE_RUN`, using the same private run directory prepared and run for this invocation. To remove the images an earlier run left, whether for headroom or for a standalone request, pass that run's own private directory; the command needs that run's checkout at its original revision and strictly clean, and ends with `cleanup: pending` otherwise. Repeat `-retain sha256:FULL_IMAGE_ID` for any image the user asked to keep. The command keeps detailed inventories, its private build record, query output, logs, and checkouts private, and it proves an image only from its own private primary record, the final images this invocation built (live builds are layer-free once the engine is confirmed, so such a build commits one image, and a registry base that a `FROM` pulls is never part of the build record), so an unproven image, an intermediate included, stays and is reported as skipped with its size; an image that appeared during the run and that no valid receipt or revalidated known registry input explains makes the status `partial`, even when every surviving attempt is closed; an image already in the before inventory is skipped as `present before invocation`; malformed, lost, unconfirmed, or contradictory producer evidence, or a vetoed receipt, makes the status `unverified`, which takes precedence over `partial`; and no image becomes eligible by any of this, which no rule above changes; its bounded `cleanup-<platform>.json` in the record directory and standard output contain the sanitized removal decisions and before/after measurements. It runs the final durations collection with both preparation and post-suite intervals; only a true `collected` value and the named durations file confirm this invocation's collection. Pending or unverified cleanup and collection are reported as such, independently of the suite's result. The command and its limits are described in the [host commands](../../../docs/images.md#running-a-live-run-with-the-host-commands).
