# Live validation

Live validation runs the repository's documented live checks on a real Windows host and a real Linux host over SSH. The user owns the decision to start and the hosts it runs on, so the run passes a two-stage gate. A **live invocation** is one request to validate one target revision; the gate is per invocation. Cleaning up after a run belongs to that run's invocation and reuses its host agents and authorization. A standalone request to clean up what a run left authorizes the scope the user names: apply the [image cleanup](#image-cleanup) rules on that host without starting the suite, judge eligibility from the run's recorded inventory and asset hash, and ask only for an alias the request leaves missing.

## Stage 1: consent to start

The Yes/No checkpoint below is this project's workflow, set by its owner; it is not a permission the skill infers, and a request such as "run live validation" is the trigger, never the answer. For a new test invocation, ask it first, before any step on a live or remote host and before any alias step. Offline checks in the local checkout need no checkpoint. Use the host's question tool with Yes/No choices when it has one; otherwise ask in plain text with the two choices and end the turn.

> Live validation would run the documented live checks for `<change>` at revision `<sha>` on a Windows host and a Linux host over SSH. Should live validation start now?
> Choices: Yes / No

Complete when the user has answered. No answer is not consent: take no live-host or alias action while waiting.

- **Yes** authorizes this live invocation only. Continue with stage 2.
- **No, or deferred** ("later", "not now"): put `Live validation: pending (not started: <the user's words>)` in your next report, continue offline work that is still useful, and describe the change as unvalidated live, never as validated.

A Yes already given to this checkpoint in the same live invocation stays valid: resuming after an interruption, or the run's own image builds and sandbox starts, reopens nothing. A new request to validate, or a new target revision, is a new invocation and asks again.

## Stage 2: both SSH aliases

After Yes, ask for both aliases together in a prompt of its own:

> Which SSH host aliases should live validation use? Give both, as they appear in your SSH configuration.
> Windows SSH alias:
> Linux SSH alias:

- **Both given**: continue with stage 3.
- **One given**: keep it and ask for the missing one only: `Keeping the <platform> alias <alias>. Which SSH alias is the <other platform> host?`
- **Aliases named in the triggering request** belong to this invocation: after Yes, confirm them in the alias prompt (`Windows: <alias>, Linux: <alias>. Correct?`) or ask only for the missing one, never for the same text again.
- **An alias from an earlier task, session, memory, or the SSH configuration itself**, or "the same as last time": name it and ask the user to confirm it for this invocation before using it.

Complete when the user has named or confirmed both aliases in this invocation. The suite starts on neither host before then.

## Stage 3: one dedicated agent per host

After both aliases are confirmed, the session that passed the gates is the **coordinator**. It launches two **host agents** asynchronously through the host's delegation tool before waiting on either, one owning the Windows alias and one owning the Linux alias, and it runs no suite itself. Route each host agent's model with the `model-routing` skill. Keep each returned task handle: a second request for the same host resumes its running agent instead of starting another, and a session resumed mid-run reattaches to the handles it kept. A launch that fails marks its host `pending` with the tool's own message while any agent that did start keeps running and its result and cleanup are still collected; when neither agent can start, report `Live validation: blocked (no delegation available)` with the tool's own message. Running a host in the coordinator, or the two hosts one after the other, is not a fallback.

Give each host agent, in its brief: the target revision, its confirmed alias, that consent and both aliases are already settled so it asks no gate again, the user's constraints for this invocation, the documented checks below, the progress duties in step 3, for the Windows host the [Windows host queries](#windows-host-queries), and the [image cleanup](#image-cleanup) rules. A host agent that reports blocked leaves the other running; the coordinator records that host as `pending` with the reason.

Each host agent runs the live checks the repository documents in [docs/images.md](../../../docs/images.md) under "Live image tests", with the variables that section names (the opt-in, the dedicated controller group, the record directory, and the image selection), on its host over its alias. That section is the default workflow, and its [host commands](../../../docs/images.md#running-a-live-run-with-the-host-commands) run it through the repository's `live-run` helper in steps 1 to 5; ordinary read-only diagnostics beside it need no further consent. A target revision whose checkout lacks `internal/liverun/cmd/live-run` predates the helper: steps 1 to 5 then use the commands that section prints for the suite and the collector, with the suite in the background, its private log outside the record directory, and the exit status of `go test` kept (`${PIPESTATUS[0]}` after `set -o pipefail`, or `$LASTEXITCODE` in PowerShell).

1. Confirm the host has a checkout at the target revision and record the SHA it reports. A missing revision is routine preparation inside the Yes: fetch it into a separate temporary checkout on the host and leave the host's existing work untouched. When the host cannot reach the revision, or access fails, report the host as `pending` with the reason; pushing source to a remote or changing the host's configuration is outside this authorization. Then build the helper in that checkout, `go build -o <private dir>/live-run ./internal/liverun/cmd/live-run` (`live-run.exe` on Windows), so that its code matches the target revision; keep its binary, the run directory, and the log in a private directory outside the checkout and outside the record directory. Its behaviour on native Windows 11 and in non-administrator Windows PowerShell 5.1 is not yet proven by a live run: report a failure there with the helper's own message.
2. Before any build, record the **before** measurement and the **before** inventory defined under [Image cleanup](#image-cleanup); on Windows take them with the [Windows host queries](#windows-host-queries). Judge headroom against a conservative bound on the peak additional space the suite needs before any cleanup: the initial build of the base image and every toolchain set, the no-cache rebuild of all of them while the first set still exists, the intermediate build layers, and the writable layers of the running sandboxes. Take the bound from the peak a documented or recorded run on that host reached only when that run's documented conditions cover this run's cache state, selected toolchain sets, dependency versions (a floating release such as `npm@latest` included), and every component listed above; when the conditions are unknown or do not cover them, or no run exists, take it from a reasoned conservative estimate of those components even if an older peak exists. Never take it from net growth after cleanup or from a fixed figure. On Windows the bound must fit both the host drive that holds the machine's virtual disk and the machine's own image filesystem. When the headroom is insufficient, first remove, in one pass, the images that an earlier run's record marks eligible under those rules; that removal needs no further permission, while any repair, prune, or compaction stays outside this invocation. After any such removal, keep the earlier inventory only for the cleanup and provenance audit; take a fresh whole-engine **before** inventory and free-space measurement that replace the earlier ones as the before records, select the bound again for the post-removal state under the rule above, and recheck every measured filesystem against it, without a second removal pass. The last inventory taken before the first build is the **snapshot** of the run's start; note what else runs on the host: the **comparison context** (`host_load`, `base_image`, `build_cache`) is classified after the run from the snapshot alone, by the rules under [Retaining case durations](../../../docs/images.md#retaining-case-durations), and a value the snapshot cannot show is `unknown`. Start the suite only when the free space on every measured filesystem exceeds the bound selected for the state the build starts from, never one chosen before a removal, with one exception: no bound exists and the user has decided to proceed without one after the coordinator stated the free space and the risk that the build exhausts the host. That decision is specific to this invocation, is recorded in the report, and is not covered by the Yes of stage 1. In every other case without a reliable bound, and whenever the host's own numbers cannot be read or the space is known to be insufficient, report the host as `pending (<free> free; <bound> expected, or no reliable estimate>)` without starting the suite. `live-run prepare` carries out this step: give it the exact target revision, a new private run directory, a fresh record directory, the host's last recorded peak as `-peak-record`, when the bound rule above allows taking the bound from it (the JSON file that the [host commands](../../../docs/images.md#running-a-live-run-with-the-host-commands) define), and `-host-load` only when the load was observed, otherwise leave it unknown. It takes the before measurement, the `podman system df` text, and the whole-engine before inventory in one pass and keeps them privately in `preparation.json` of the run directory, and it refuses a missing or mismatched bound, or free space that does not strictly exceed the bound on every measured filesystem, printing only free bytes and the expected bytes: report that refusal as the `pending` line above and start no suite after a failed preparation. When the headroom was insufficient and you removed, in one pass, the images that an earlier run's record marks eligible, run `prepare` again after that removal in the same run directory: its fresh whole-engine inventory and free-space measurement replace the earlier ones as the before records, the bound is selected again for that state, and there is no second removal pass. The decision to proceed without a bound is passed as `-allow-unbounded` together with `-unbounded-decision` and the text of that recorded decision, never inferred from the Yes of stage 1, and it never covers free space that cannot be read. The final snapshot that `live-run run` saves in `before.json` after repeating these checks is the snapshot the comparison context and the cleanup use.
3. Start the suite with `live-run run -run-dir <run dir>`. It detaches from the SSH session, repeats the preparation checks under the engine lock, and runs the documented live suite in verbose mode with the image selection, the dedicated group, the record directory, and `SANDBOXED_AGENTS_LIVE_STOP_AFTER_FAILURE=1`, which starts no case after the first failed one and fabricates neither coverage nor a pass. The suite's **private log** is `suite.log` in the run directory, outside the record directory. When `go test` returns, the run directory holds `exit.json` and `exit-status`, the exit status as a plain integer; a run whose supervisor died reports status 137 with `interrupted`, and an interrupted run reports its non-zero status. Poll `live-run status -run-dir <run dir>` with no blocking foreground call: it returns, without a raw line, a path, or an object name, the latest observed fixed `case` and `operation`, `last_output_age_seconds`, `free_space`, and whether the suite has `ended` with its exit code. Send the coordinator an event at suite start, at every change of case or operation, and at least once a minute while an operation is still running. Name the case, the image or sandbox when you read it from the private log, and the operation, and classify the operation as the fixed classes of the [operation timings](../../../docs/images.md#operation-timings) name: **image build** (`up` of a missing image), **sandbox start or restart** (`up` of an existing image, `stop`, `start`), **SSH server check**, **smoke** (`shell`), **update or rollback** (`update`), **agent install** (`agents enable`), **agent session** (`agents session`, its status, stop, and disable), **rebuild** (`build`), or **cleanup** (`remove`), and, while the suite's `t3code` case runs, **Tool install** (`tools enable`), **Tool update** (`tools update`), **Tool delete** (`tools delete`), or **Tool probe** (`tools status` and the case's read-only checks of the service's HTTP response, listener, and process identity). A log from before the suite streamed its operation markers shows an `up` as `image build or sandbox start`; read no image state into it, and report `unknown` when the status names none. The status is the most recent observation of the case and operation, not a claim that the other cases are idle. A silent buffer keeps its last observation: send it and its age, and never read a pass, a finished check, or a next operation into silence; the suite's own `--- PASS` or `--- FAIL` line is the only result. The log holds names, paths, and program output and stays on the host: the only excerpts that leave it are the failure text of step 4 and the operation summary of the status report. Send the coordinator an event at suite start, at every change of test or operation, and at least once a minute while an operation is still running. Name the test the suite is in and the image or sandbox it is working on, and classify the observed operation from the last line the suite printed, or from read-only evidence such as the host's existing logs or process metadata: **image build** (`up` of a missing image), **sandbox start or restart** (`up` of an existing image, `stop`, `start`), **SSH server check**, **smoke** (`shell`), **update or rollback** (`update`), **agent install** (`agents enable`), **agent session** (`agents session`, its status, stop, and disable), **rebuild** (`build`), or **cleanup** (`remove`), and, while the suite's `t3code` case runs, **Tool install** (`tools enable`), **Tool update** (`tools update`), **Tool delete** (`tools delete`), or **Tool probe** (`tools status` and the case's read-only checks of the service's HTTP response, listener, and process identity). A silent buffer keeps its last observed operation: send the last line and its age, and never read a pass, a finished check, or a next operation into silence; the suite's own `--- PASS` or `--- FAIL` line is the only result.
4. When a preflight or check fails, report the suite's own failure text as the finding; a failed `live-run` check prints the name of the check and keeps the engine's message in its private diagnostic, so report the printed text. A repair the user has already authorized proceeds; a Podman, WSL, or SSH configuration change outside that authorization is the user's decision: propose it through the coordinator and wait for the answer.
5. After `live-run status` shows the suite `ended`, pass or fail, collect the run's durations with `live-run collect -run-dir <run dir>` instead of calling the collector yourself. It runs the collector command of [Retaining case durations](../../../docs/images.md#retaining-case-durations) on the private log and the schema 2 record the suite wrote, takes the comparison context only from the final `before.json` snapshot together with the asset hash in the log's preflight output, and passes the run's preparation timestamps. A success is exit status 0 with `collected` true and the `durations_file` name of `durations-<platform>.json` in the record directory, beside the record; only that file is this invocation's evidence. The `collect` phase takes no post-suite interval: the collection that `live-run cleanup` runs in step 6 replaces this file and carries it. Collection reads the record and changes nothing else, and a failed or interrupted run is collected from its failing record and the log as it ended. The file holds only the completion lines the log emitted; `go test -v` prints a case's line when the parent ends, so a kill or timeout that ends the test binary can leave `cases` empty, a valid file that shows no observations, never zero and never proof that no case finished. A collector failure is reported with its own message, leaves any earlier `durations-<platform>.json` in place as it was, and does not alter the suite's result: that file belongs to an earlier run, even at the same revision, and its numbers are never this run's.
6. After the suite has returned, pass or fail, and its own cleanup of sandboxes, volumes, and group state has run, remove the run's unused images as [Image cleanup](#image-cleanup) describes, with `live-run cleanup -run-dir <run dir>` (repeat `-retain sha256:<full image ID>` for each image the user asked to keep), then record the **after** measurement, which the command's report carries. A kill or timeout that kept the suite's own cleanup from running does not defer this step: the image rules already skip any image a leftover container references, and the leftover sandboxes, volumes, and group state are reported as left behind, never removed here. The private log stays on the host with the host's other evidence.
7. Return the suite's result line, the commit it ran on, its duration, the validation record the suite wrote in the record directory (its file name and its content, which holds no host detail), the `durations-<platform>.json` from the same directory (file name and content only when this invocation's final collection succeeded, which is the `live-run cleanup` report's `collected` true with its `durations_file`, or, when that command ended before it collected, the successful `live-run collect` of step 5, which carries no post-suite interval, with an empty `cases` list reported as empty, no emitted observations; otherwise `unverified` with the collector's own message, whether or not an earlier file or one at the same revision is present; its `unknown` context values stay `unknown`), and, when the validation record lists a `t3code` check, also its supplemental `t3code-<platform>.json` from the same directory, with file name and content, whatever that check's result: `pass`, `fail`, or `not-run`. A record that lists the check while the supplemental file is absent is reported as unverified, never as passed, whatever the suite's result line says, and with the failed preflight named as the likely reason when the record shows `preflight` failed. Whether the check is expected depends on the target revision's suite, read from its `liveCheckNames` in `cmd/sandboxed-agents/live_test.go` or its documented cases in `docs/releases.md`: when that suite has no `t3code` case, the revision predates it, so say so and expect no supplemental file; when it has the case and the record omits the check, report the omission as unverified, never as old or not present. Return the before and after measurements, and the cleanup state: what the suite removed, which image IDs this step removed, which it skipped and why, and anything left behind or unverified, with the sanitized `cleanup-<platform>.json` from the record directory; its `post_suite_seconds` ends before the final collection and publication and is a lower bound, never a total.

The coordinator turns the host agents' events into one status report, at least once a minute while either suite runs and at every event, in exactly this layout. The timestamp is the current UTC clock when the report is written, never a time copied from a log line. The Windows and Linux lines stay adjacent, each one compact line that names the alias, the test, the image or sandbox, the operation, and the age of the last output; the raw log line stays out of it. One blank line separates the header, the two-host group, and the footer, and one blank line follows the footer before anything else. The Windows line ends with a backslash so Markdown keeps the two hosts on separate lines. A host whose agent has not started, is blocked, or has finished says so in place of the operation.

```markdown
Live validation — <YYYY-MM-DD HH:MM:SS UTC>
| --- | --- |
| Windows:<br />**<alias>** | <test> on <image or sandbox>, <operation>, last output <n>s ago<br /><disk space left> |
| Linux:<br />**<alias>** | <test> on <image or sandbox>, <operation>, last output <n>s ago <br /><disk space left> |
Next update: within 60 seconds
```

Report in this form when both host agents have returned, then stop:

```markdown
Live validation: <done | failed | pending>
Revision: <sha>

| | Windows (<alias>) | Linux (<alias>) |
| --- | --- | --- |
| Result | <suite result line> | <suite result line> |
| Duration | <mm:ss> | <mm:ss> |
| Disk | <free before → after; Podman storage before → after> | <free before → after; Podman storage before → after> |
| Cleanup | <sandboxes, volumes, state; images removed / skipped / unverified> | <sandboxes, volumes, state; images removed / skipped / unverified> |
| Durations record | <durations file name and its case seconds, or empty (no case lines emitted), or unverified (<collector failure or reason>)> | <durations file name and its case seconds, or empty (no case lines emitted), or unverified (<collector failure or reason>)> |
| T3 Code record | <t3code result and file name, or unverified (file or check missing), or not present in this revision (its suite has no t3code case)> | <t3code result and file name, or unverified (file or check missing), or not present in this revision (its suite has no t3code case)> |
```

Complete when both hosts have a recorded result (when the target revision's suite has a `t3code` case, that check with its supplemental file, or the word unverified when either is missing), both measurements, and a cleanup state that accounts for every image the run created, or a recorded reason they have none.

### Windows host queries

The Windows account may be an ordinary, non-admin user. Query as that account and assume no CIM/WMI access and no `Get-Volume`; this grants no administrator permission and no change to host configuration.

- **Host drive space:** [`System.IO.DriveInfo`](https://learn.microsoft.com/en-us/dotnet/api/system.io.driveinfo.availablefreespace) `AvailableFreeSpace` for the drive that holds the machine's virtual disk. The engine inventory, `graphroot`, and the guest `df` still come from native `podman` on the selected `--connection`, as under [Image cleanup](#image-cleanup).
- **Processes:** [`Get-Process`](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/get-process?view=powershell-5.1) for your own processes' basic metadata, without `-IncludeUserName` or module data.
- **Launched queries:** start them with [`Start-Process -PassThru`](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/start-process?view=powershell-5.1) and private stdout and stderr files, or with `System.Diagnostics.ProcessStartInfo`, and keep the process object, so the PID, start time, and command are known; a blocking collector cannot say which subcommand it waits on. Bound every wait. Record each command's start, end, exit status, and artifacts as it happens. When you redirect pipes, read both streams concurrently so a full buffer cannot deadlock the query.
- **Stopping:** terminate only a query you launched, through its verified handle. Never stop an older process of unknown origin by its name or start time.
- **CIM denied:** that is an API limitation, not an engine failure and not a reason to ask for administrator rights. Use the queries above. When the full gate still cannot be measured, report `pending (<the exact missing query>)`.
- **PowerShell 5.1 JSON:** call `ConvertFrom-Json` without `-Depth`, and `ConvertTo-Json` with an explicit `-Depth` that covers the whole snapshot.

## Image cleanup

The suite removes its sandboxes, volumes, and group state and leaves every image it built. Images are shared across controller groups and executables: the marker label and the asset hash say which executable built an image, not who owns it, so they never make an image disposable on their own. A rebuild moves a tag to the new image and leaves the previous one untagged, still backing any sandbox created from it. Repeated no-cache rebuilds therefore fill a host; the project's Windows host has a 100 GB drive.

**Measurement.** Record, as text in the host agent's report: the free space of the filesystem that holds Podman's storage (on Windows the host drive that holds the machine's virtual disk and, through the selected connection, the machine's own image filesystem), and `podman system df` for the same engine. Take it before any build and again after cleanup.

**Inventory.** Enumerate every image ID with `podman images --all --no-trunc` (a tag or digest is not an ID), read each image's labels and creation time with `podman image inspect`, and enumerate every container with `podman ps --all`, then read the image ID each one references from `podman container inspect` (the `ps` image column may show a name or tag), for the whole engine, not one group. Take it before any build. Keep this invocation's build output and record from it the exact full image ID of every image its build steps produced, with the step or result each ID came from; resolve any shortened ID against the engine's full IDs and keep it only when it resolves to exactly one image, then confirm it against `podman image inspect` and the before inventory. That record is the only proof that an image belongs to this invocation; the asset hash, the creation time, and the difference between inventories are not.

**Eligible for removal.** An image is eligible when all of these hold: it is absent from the before inventory; its full ID is in this invocation's build record; it carries this invocation's asset hash where the build labels one; no container on the engine, in any group, references it after the suite's own cleanup; and the user has not asked to keep it. That holds for every eligible image, an untagged image the rebuild superseded or an intermediate ancestor included: its full ID must be traced to this invocation's build output. The engine's verified parent chain only corroborates ownership or supersession of an ID already in the record; an ancestor seen only in a chain, or tied only by a matching hash or creation time, stays, even when that skips an image this invocation did create. An image present before the run, shared by other sandboxes, created by a concurrent workflow, matched by more than one candidate, or whose provenance the record cannot show stays, named as skipped. A query that fails leaves the image unverified, never absent.

**Removal.** Remove eligible images one by one by ID, toolchain images before the base image they depend on, with `podman rmi --no-prune <id>` and no `--force`; on Windows through the selected `--connection`. `--no-prune` keeps the dangling parents of the removed image, so an ancestor the build record does not prove stays in place instead of being removed by the engine's cascade; a proven parent is removed by its own ID after its children. Never run `podman image prune`, `podman system prune`, `podman system reset`, or any host-wide removal, and never delete, compact, or reconfigure a machine, its virtual disk, or WSL: those are host configuration changes with their own authorization. Keep the host's logs, checkouts, and evidence files. When the engine is unreachable, report `cleanup: pending (engine unreachable: <message>)` and stop.

**Reporting.** List removed IDs with their tags and sizes, skipped IDs with the reason, unverified items with the failing query, and the before and after measurements. A retention the user asked for is honoured and its disk cost reported. This cleanup is part of the authorized invocation and opens no new checkpoint.

Apply these unchanged rules after the suite has ended with `live-run cleanup -run-dir PRIVATE_RUN`, using the same private run directory prepared and run for this invocation. Repeat `-retain sha256:FULL_IMAGE_ID` for any image the user asked to keep. The command keeps detailed inventories, exact build-step proof, query output, logs, and checkouts private; its bounded `cleanup-<platform>.json` in the record directory and standard output contain the sanitized removal decisions and before/after measurements. It runs the final durations collection with both preparation and post-suite intervals; only a true `collected` value and the named durations file confirm this invocation's collection. Pending or unverified cleanup and collection are reported as such, independently of the suite's result. The command and its limits are described in the [host commands](../../../docs/images.md#running-a-live-run-with-the-host-commands).
