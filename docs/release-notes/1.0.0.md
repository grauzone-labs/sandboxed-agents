# sandboxed-agents 1.0.0

Version 1.0.0 is the first version of this implementation of `sandboxed-agents`, developed in `grauzone-labs/sandboxed-agents`. These notes describe what the version contains. They are committed before the preview tag, so they are part of the commit that the gates validate; they say nothing about whether a gate has passed. A stable release states the commit each gate passed on in the release text below these notes, written by the release workflow ([Releases](../releases.md#stable-release-check)). A preview of this version, tagged `v1.0.0-preview.YYYYMMDD.N`, uses these notes unchanged and is a maintainer test build.

## What it is

`sandboxed-agents` runs coding agents in rootless Podman containers, one sandbox per workspace, on Linux and Windows 11. An agent's mistake, such as deleting the wrong directory or installing a bad package, changes only what that sandbox holds: its workspace, its home data, and the credentials stored there. The workspace is a volume of the sandbox, or the one host directory you bind there, which the agent can change or delete. Host credentials, SSH-agent sockets, and container-engine sockets are never mounted. Outbound networking is open, so an agent can send anything it can read, including workspace files and the credentials stored in the sandbox, to any server it can reach. It is one static executable, and the host needs only Podman and OpenSSH.

## What this version contains

- **Sandboxes.** `up` creates a sandbox with a workspace volume of its own or exactly one host directory bound at `/workspace`; `list`, `check`, `start`, `stop`, `restart`, and `remove` manage it.
- **Agents.** `copilot`, `claude`, `codex`, and `opencode`, installed into a sandbox on request, with pins, login, one-shot runs, and persistent sessions you can detach from and reattach to ([agents](../agents.md)).
- **Toolchains.** The optional image toolchains `dotnet`, `playwright`, `azure`, and `native` ([images](../images.md)).
- **Integrations.** Git identity and credentials, GitHub, Azure, and Azure DevOps ([integrations](../integrations.md)).
- **SSH access.** An opt-in SSH setup for editors such as VS Code Remote SSH ([SSH access](../ssh.md)).
- **Tools.** T3 Code, tool name `t3code`, installed into a sandbox on request with `tools enable`, pinned or on a channel, kept running by the manager as `agent`, with `tools update`, `tools status`, and a complete `tools delete` that keeps your project files ([Tools](../tools.md)). It adds T3 Connect, a login to a T3 account with an outbound relay, and QR pairing of a phone over a Tailscale tailnet node that the Tool runs in the sandbox. T3 Connect login is a T3 account login, QR pairing is a device pairing, and an agent's provider sign-in stays `agents login`.
- **Updates.** `update` moves a sandbox to a newer image with rollback, and `update --all` does so for every sandbox.
- **Controller groups.** `SANDBOXED_AGENTS_GROUP` selects a separate namespace of sandboxes on the same host.

[Command reference](../command-reference.md) lists every command and option, the exit status rule, and the order of checks.

## T3 Code: network paths and what changed in the security stance

Enabling the T3 Code Tool changes no Podman option of the sandbox, and the SSH publish on host loopback is unchanged ([SECURITY.md](../../SECURITY.md#t3-code-network-paths)). The Tool's service listens on the sandbox's loopback. What is new, and only if you choose it:

- **T3 Connect relay.** After `tools connect NAME t3code login` and `link`, T3 Code makes outbound connections to its relay on TCP and UDP port 7844 and over HTTPS. No inbound port exists. A device signed in to the linked T3 account can then use the sandbox's T3 Code, so that account has an agent's reach in the sandbox: the workspace, the home data, and the credentials stored there.
- **Tailnet node.** After `tools tailscale NAME t3code login`, the sandbox runs its own Tailscale device in userspace networking mode, needing no TUN device and no capability, and Tailscale Serve maps an HTTPS origin in your tailnet to the service. Decision: this topology is how phone QR pairing is delivered ([ADR 0010](../adr/0010-t3-code-pairs-over-an-in-sandbox-tailnet-node.md)); Tailscale Funnel is never used. While the node is signed in, a device of your tailnet that your access policy allows also reaches the sandbox's `sshd` on port 22 and the T3 Code service on port 3773 through the node's address. Nothing is reachable from outside your tailnet or while no node is signed in.

The security policy's earlier limit "no managed services" now reads: one managed service, T3 Code's, and the tailnet node you sign in. Stopping, restarting, updating, or deleting interrupts the work T3 Code is driving, and `tools delete` removes the Tool and everything it stored.

Live evidence for these paths is limited. The tailnet topology and phone QR pairing were run on a Linux and a Windows 11 host, and the manual checklist item for QR pairing passed on a Linux preview; the T3 Connect phone link and the full live runs of the Tool commands are not on record ([maintainer notes](../maintainers.md#t3-code-tool-evidence-and-gaps)). These notes are not a gate result.

## Platforms and requirements

- Linux amd64 with rootless Podman 4.4.0 or newer.
- Windows 11 x64 with Podman 4.7.0 or newer and a running rootless WSL2 machine.
- OpenSSH on both.

## Release files and install methods

Every stable release and every preview carries five files, each with a build provenance attestation ([Releases](../releases.md#release-files)):

- `sandboxed-agents-linux-amd64` and `sandboxed-agents-windows-amd64.exe`;
- `SHA256SUMS`, covering both executables;
- `sandboxed-agents-VERSION.tgz`, the [npm package](../npm-package.md);
- `SandboxedAgents.VERSION.nupkg`, the [NuGet command package](../nuget-package.md).

`VERSION` is the version of the tag without the leading `v`: `1.0.0` for the stable release, and the preview's full version, such as `1.0.0-preview.YYYYMMDD.N`, for a preview.

The version is installed from a downloaded binary ([Linux](../quick-guide-linux.md), [Windows](../quick-guide-windows.md)), from npm as `sandboxed-agents` on Linux x64 and Windows 11 x64, or on Windows 11 from NuGet as `SandboxedAgents`. Only a stable release is published to the npm and NuGet registries; a preview is installed from its release files.

Builds are reproducible: the same commit and tag yield byte-identical executables and packages, and `sandboxed-agents version` prints the same `asset-sha256` for one commit on every platform. Installing, upgrading, or removing the executable never calls Podman and never touches sandboxes, SSH configuration, or sandbox data.

## Known limitations

[SECURITY.md](../../SECURITY.md) states the threat model and every limit. In short:

- A sandbox is not a defense against hostile code: it shares a kernel with the host, and on Windows with the WSL2 machine.
- Outbound networking is open, and agents in one sandbox share the user, the home data, the credentials, and the workspace.
- Only SSH is published, on host loopback. The T3 Code Tool publishes nothing; its relay is outbound only, and a signed-in tailnet node lets allowed devices of your tailnet reach the sandbox's `sshd` and the T3 Code service ([T3 Code network paths](../../SECURITY.md#t3-code-network-paths)).
- No command removes old images; remove unused ones yourself, for example with `podman image prune` ([images](../images.md#no-image-removal)).
- Owner conflicts are reported and not repaired ([command reference](../command-reference.md#ownership-and-names)).
- Linux amd64 and Windows 11 x64 only. ARM64, a self-update command, and install methods for agents other than npm are not part of this version.
