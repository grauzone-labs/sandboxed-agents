## OpenCode installs from `@opencode/cli`

The agent `opencode` is installed from the npm package `@opencode/cli`, OpenCode's v2 distribution, instead of `opencode-ai`. The agent name `opencode`, its command, and `opencode auth login` do not change, and neither does anything `opencode proxy` writes.

- **Existing installations keep working.** The manager still recognizes an `opencode-ai` installation in a sandbox's home data as the managed one, and never installs `opencode-ai` again. The manager checks the package when `--force`, a mismatched command link, an explicit `--version`, or `update` requires it: the metadata must name `@opencode/cli` or `opencode-ai` and the command must lie beneath that package, and any other package is refused. A bare `enable` of a healthy installation runs no check. Before a change that may remove the selected installation directory, the manager also checks that directory by itself and refuses one that is foreign or outside its own installations. A command link whose target is missing is refused even with `--force`, with a message that asks for manual recovery ([Agents](../agents.md#recover-from-an-interrupted-change)).
- **Update the sandbox first.** The manager that handles the commands below is part of a sandbox's image, and a sandbox keeps its image until `sandboxed-agents update NAME` runs. After installing the updated executable, run it before you migrate; the steps are in [Agents](../agents.md#move-opencode-to-its-new-package).
- **Migrating.** Either `sandboxed-agents agents update NAME opencode` or `sandboxed-agents agents enable NAME opencode --force` replaces an `opencode-ai` installation with `@opencode/cli`; a recorded pin is checked first, as under Pins below. A bare `agents enable NAME opencode`, and `enable --force` on a healthy `@opencode/cli` installation, migrate nothing and need no registry. `update` without `--force` refuses while an `opencode` session runs; either command with `--force` stops that session first.
- **Your data stays.** The migration touches the installation and the agent selection only, not OpenCode's configuration, the proxy configuration, or a stored login. OpenCode 2.x reads the old configuration file itself, and its own database migration imports the old credentials once, skipping integrations that already have a credential, so it does not replace credentials in an existing 2.x database. That was observed for 2.3.0 and is not a guarantee for every 2.x version. Reverting to an earlier manager does not undo later changes that OpenCode 2.x makes, its credential database included, so a return to `opencode-ai` is not promised to be effortless.
- **Pins.** A pin to a version of `opencode-ai`, such as `1.19.5`, names no version of `@opencode/cli`. For `opencode`, a requested `--version`, even one equal to the installed version, and a recorded pin, when a command has to install again, are first checked with a read-only `npm view` of the published versions of `@opencode/cli`, run with the sandbox's npm configuration, before anything is installed. A pin that is not published is refused with guidance to run `agents enable NAME opencode --version VERSION`, with the version that npm's `latest` tag points to; when `opencode` is already enabled, the guidance also names `agents update NAME opencode --unpin`. A failed `agents update` also ends with a generic `retry:` line that repeats the refused pin and fails again; use the named commands instead, with `NAME` replaced by your sandbox name. When the check cannot be made, the command is refused and changes nothing.

The details are in [Agents](../agents.md#move-opencode-to-its-new-package). The `opencode proxy` workflow was tested offline on Linux x64 against OpenCode 2.3.0 with the repository's contract test; the commands, checksums, source reading, and limits of that test are in the [offline record](../validation/issue-165/offline.md). The [live record](../validation/issue-165/live.md) holds the targeted live checks and the Linux full suite at `941caa6` (the Windows full suite failed there) and a passing Windows full suite at `ae4526e`. Later identity, ownership, selected-directory, and hint changes have offline tests but no new live proof yet, there is no same-commit full-suite pair, and none of this is a gate result.
