# Agents

This page shows you how to enable, pin, update, and disable an agent in a sandbox, sign in to it, run it once, and keep it running in an agent session you can detach from. Agents are the coding CLIs of the agent catalog: `copilot`, `claude`, `codex`, and `opencode`. A sandbox installs an agent into its home data and enables it there; the agents enabled in a sandbox, each with its pin if it has one, are the sandbox's agent selection.

## Requirements

Every `agents` command needs a running sandbox. A stopped sandbox fails and names `start NAME`; a sandbox with only volumes names `up NAME`. If the manager does not answer, the command exits non-zero, says that the manager does not answer, names `check NAME` for diagnosis and `restart NAME` as the next step, and changes nothing. This failure comes before the check that the agent is enabled and before the check for a terminal, so a `run`, `login`, or `session` command on a sandbox whose manager is broken reports the manager, not the agent. Nothing starts automatically and there is no fallback around the manager.

The manager installs and works on agents as `agent` (UID and GID 1000), never as container root ([ADR 0006](adr/0006-podman-target-and-execution-identity.md)). `run`, `login`, and `session` start the manager directly as `agent`, and the manager refuses to work under any other identity.

## Concurrent changes

Installation changes (`enable`, `update`, `disable`) and session changes (starting or stopping an agent session) take the manager lock, so only one runs at a time in a sandbox. The lock is exclusive and nonblocking, the same rule [ADR 0007](adr/0007-serialize-sandbox-lifecycle-commands.md) sets for lifecycle commands. A change that finds another agent or Tool change in progress does not wait. It exits non-zero, says that another agent or tool change is in progress, and tells you to retry. Nothing retries automatically: run the command again once the first one has finished, and scripts that change agents in parallel must retry themselves. Attaching to a running session, `agents run`, and `agents login` do not take the lock, with two exceptions: the `proxy` workflows of [`claude`](#claude-proxy-workflow), [`codex`](#codex-proxy-workflow), [`opencode`](#opencode-proxy-workflow), and [`copilot`](#copilot-proxy-workflow) write files in the home data and hold the lock while they do, and the `browser` and `device-code` workflows of `codex` hold it for the whole interactive login, from before their check that no proxy is configured until Codex's login command exits, so that no `codex proxy` write or removal runs while Codex writes its own login. All of them refuse with the same retry message while another change runs. `agents run NAME codex` takes no manager lock but holds a second lock, the Codex configuration lock, shared with other runs, for as long as the command runs; a `codex proxy` write or removal takes that lock exclusively, so a run and a proxy change refuse each other while no other agent or Tool is held back ([below](#codex-proxy-workflow)).

`agents status` and `list` do not take the lock. They read the agent selection as one consistent snapshot and stay responsive while an npm install runs (`status` may also run the status probe, which gives the agent's command one second to finish and then waits at most another 100 ms to end it, so it adds at most about 1.1 seconds). The snapshot only contains committed installations. While a first `enable` is still running, the agent is not in the snapshot yet: `status` reports it as not enabled and `list` omits it until the installation finishes. While an `update` or other replacement is running, the snapshot still shows the previously committed installation and version, not an absence, until the replacement commits.

The agent selection and its pins live in the sandbox's home data. They survive `stop` and `start`, and the host keeps no copy.

## Enable an agent

```text
sandboxed-agents agents enable agent01 claude
sandboxed-agents agents enable agent01 claude --version 1.2.3
```

Without `--version`, the command installs the agent's package at its newest version and records no pin. If the agent is already enabled, the command changes nothing, reports the installed version and the pin (or that there is none), and exits zero.

With `--version X`, the command installs exactly that package version and pins the agent to it. `X` must be an exact npm package version, `MAJOR.MINOR.PATCH` with an optional prerelease such as `1.2.3-beta.1`. Tags, ranges, and versions with `+build` metadata are rejected: npm strips build metadata, so it cannot provide an installation that matches such a literal pin.

- If that version is already installed, the command records the pin and installs nothing.
- If a different version is installed, the command replaces it with `X` and records the pin. This replacement refuses while a session of the agent is running; see [Sessions and installation changes](#sessions-and-installation-changes).

If an enabled agent's command is missing or does not match its selection entry, for example after an interrupted change, `enable` fails and names `--force` instead of reporting success or recording a new pin. See [Recover from an interrupted change](#recover-from-an-interrupted-change). On a healthy agent, a repeated `enable` without a new version is the same no-op with or without `--force`.

## Check an agent

```text
sandboxed-agents agents status agent01 claude
```

This reports whether the agent is enabled, its installed version, its pin, whether an [agent session](#keep-an-agent-running-in-a-session) of the agent is running, and whether it is signed in:

| Agent | `signed in` |
| --- | --- |
| `claude` | `yes` when Claude Code reports a login, `no` when it reports that it is signed out, `unknown` otherwise |
| `codex`, `copilot`, `opencode` | Always `unknown`; use the agent's own command in `shell NAME` to confirm a login |

`signed in` says that authentication is configured in the sandbox, not that the credential still works: a revoked or expired token can still show `yes`. Claude's answer comes from `claude auth status --json`, run as `agent` in the same worker as installation, so the agent's command never starts as container root. The check reads stored state only. It starts no login and refreshes no token, and it never prints the account details it reads. It also never contacts a [CLIProxyAPI server](#claude-proxy-workflow): after `claude proxy`, the answer reflects what Claude Code counts as configured authentication and says nothing about whether the server accepts the key. If the command has not finished after one second, it is ended and the status is `unknown`; ending it can take up to another 100 ms, so `status` can wait about 1.1 seconds for this check. A pin that selects a Claude Code version without the command or with a different output also gives `unknown`, never `no`. The other three agents offer no command that is both documented and read-only, which [Agent status probes](agent-status-probes.md) shows with the version and documentation of each.

The probe runs only when the agent's command link is the one the selection records; if the command is missing, mismatched, or not a managed link, `status` still reports the selection and shows signed in as `unknown`. See [Recover from an interrupted change](#recover-from-an-interrupted-change).

## Update an agent

```text
sandboxed-agents agents update agent01 claude
sandboxed-agents agents update agent01 claude --unpin
```

- A pinned agent is reinstalled at its pinned version.
- An unpinned agent is updated to the newest version.
- `--unpin` installs the newest version and clears the pin. On an unpinned agent it behaves like an ordinary update.

A pin lasts until `agents update --unpin`, `agents disable`, or a new `--version` on `agents enable` removes or replaces it.

`update` needs an enabled agent. If the command is missing, `update` installs it again. If the command link points to a different installation than the selection entry, `update` fails and names `--force`; see [Recover from an interrupted change](#recover-from-an-interrupted-change).

`update` refuses while a session of the same agent is running; see [Sessions and installation changes](#sessions-and-installation-changes).

If an `update` failure includes a `retry:` line, it repeats the command you ran, including `--unpin` and `--force` if you passed them. That line is an ordinary update. If the failure message names `--force` for a mismatched or interrupted managed installation, add `--force` to the retry; without it the retry refuses again. Add it only when the message names it. `--force` never bypasses the check for an unsafe command.

## Disable an agent

```text
sandboxed-agents agents disable agent01 claude
```

This removes the agent's managed command, its entry in the agent selection, and its pin. When it removed a pin, the output names it. It leaves the agent's credentials, cached data, and all other contents of the home data alone. Enabling the agent again without `--version` installs the newest version with no pin.

A missing command does not stop `disable`. If the command link points to a different installation than the selection entry, `disable` fails and names `--force`; see [Recover from an interrupted change](#recover-from-an-interrupted-change). For an agent that is not enabled, `disable` reports that there is nothing to disable. `disable` refuses while a session of the agent is running; see [Sessions and installation changes](#sessions-and-installation-changes).

## Recover from an interrupted change

An `enable` or `update` that is killed at the wrong moment, or cut off by a container stop, can leave the agent's command link and its selection entry disagreeing. The command may be missing, may point to an installation the selection does not record, or may exist for an agent that has no selection entry.

| State | Without `--force` | With `--force` |
| --- | --- | --- |
| Healthy: the link matches the selection entry | `enable` is a no-op; `update` and `disable` work as usual | The same. `enable --version X` with a different `X` still installs `X` and replaces the pin, as it does without `--force`. |
| Enabled, command missing | `enable` fails and names `--force`; `update` installs again; `disable` removes the entry | `enable` installs again and restores the command |
| Enabled, link points to a different installation | All three fail, name `--force`, and change nothing | `enable` and `update` install again and replace the link and the entry; `disable` removes the link and the entry |
| Not enabled, link points to an installation | `enable` fails and names `--force`; `update` and `disable` report the agent as not enabled | `enable` installs and creates the entry, with no pin unless `--version` is given; `disable` removes the link; `update` still needs `enable --force` first |

Installing again keeps the pin recorded in the selection. `enable --version X` replaces it with `X`, and `update --unpin` clears it. A change that fails never reports the agent as enabled.

A change that inspects an agent's command checks it before it runs npm or changes anything, and refuses an unsafe command, with or without `--force`. `--force` applies only to the managed installation of the same catalog agent. It never bypasses this check: a regular file, a link outside the manager's installations, a link into another agent's installation or package, and a link that escapes its installation are all refused. Read-only commands do not change the command and do not refuse because of a command-link mismatch. `list` reads only the selection. `status` reads the selection and the command link, and runs the status probe only when the link is the selection's managed link; otherwise it shows signed in as `unknown`. A normal `disable` of an agent that is not enabled still reports that there is nothing to disable.

`--force` does not bypass the manager lock, so a second agent change still fails with "retry". When the change would replace or remove the installation of an agent whose session is running, `--force` also stops that session; see [Sessions and installation changes](#sessions-and-installation-changes). It does not make a change crash-consistent: the manager has no recovery protocol for every point at which a change can be interrupted. When `--force` repairs a mismatched or unrecorded command link, the manager attempts, after the selection change is committed, to remove the installation directory that link pointed to, only if no committed selection entry references it. The removal can fail and leave that directory behind. When the selection change fails, the manager attempts no cleanup of that directory and makes a best-effort attempt to restore the previous link. The manager does not sweep home data for other installation directories that no selection entry records, so an interrupted change can still leave one behind.

## Sign in to an agent

```text
sandboxed-agents agents login agent01 claude browser
sandboxed-agents agents login agent01 codex device-code
```

`login` runs one of the agent's login workflows from the catalog, in `/workspace`, as `agent`. Each workflow is the agent's own login command with fixed arguments; the sandbox adds nothing and stores nothing itself. Whatever the agent writes, it writes into the sandbox's home data, so a login survives `stop` and `start` and is gone with `remove --volumes`.

| Agent | Workflows | What the sandbox runs | Primary reference |
| --- | --- | --- | --- |
| `copilot` | `device-code`, `proxy` | `copilot login --device-code`; `proxy` runs no login command and writes Copilot CLI's provider registry instead ([below](#copilot-proxy-workflow)) | [Copilot CLI command reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference) |
| `claude` | `browser`, `proxy` | `claude auth login`; `proxy` runs no login command and writes Claude Code's user settings instead ([below](#claude-proxy-workflow)) | [Claude Code CLI reference](https://code.claude.com/docs/en/cli-reference) |
| `codex` | `browser`, `device-code`, `proxy` | `codex login`, `codex login --device-auth`; `proxy` runs `codex login --with-api-key` in a staging directory and writes Codex's configuration ([below](#codex-proxy-workflow)) | [Codex CLI reference](https://developers.openai.com/codex/cli/reference/) |
| `opencode` | `provider`, `proxy` | `opencode auth login`; `proxy` runs no login command and writes OpenCode's configuration file instead ([below](#opencode-proxy-workflow)) | [OpenCode CLI docs](https://opencode.ai/docs/cli/) |

The workflow name is optional only when the agent has exactly one workflow, which no agent has any more: `agents login agent01 copilot` fails and lists `device-code` and `proxy`, `agents login agent01 claude` fails and lists `browser` and `proxy`, `agents login agent01 codex` fails and lists `browser`, `device-code`, and `proxy`, and `agents login agent01 opencode` fails and lists `provider` and `proxy`. An unknown workflow fails the same way, before Podman is called. Earlier releases ran `browser` for a bare `agents login agent01 claude`, `device-code` for a bare `agents login agent01 copilot`, and `provider` for a bare `agents login agent01 opencode`; since every agent gained `proxy`, name the workflow.

Only the `proxy` workflows take options: `--url URL`, `--model ID`, and `--remove` for all four agents, `--replace-login` for `codex` alone, and `--wire-api completions|responses` for `copilot` alone. For `claude`, `--model` is optional; for `codex`, `copilot`, and `opencode`, it is required unless `--remove` is given. Any of them on another agent or workflow, `--replace-login` on another agent or together with `--remove`, `--wire-api` on another agent or together with `--remove`, and a `codex proxy`, `copilot proxy`, or `opencode proxy` setup without `--model` are usage errors that exit 2 before Podman is called.

Every workflow except `proxy` needs an interactive terminal on both standard input and standard output, because it shows a URL or code and waits for input. Without one it fails and starts nothing. Before such a workflow starts, the command prints the agent's login message from the catalog, which says what to do on your host; for `codex`, the message comes only after the check that no proxy is configured ([below](#codex-proxy-workflow)), and a refusal prints no message and starts nothing. `proxy` prints no login message: it reads a key and writes the agent's own configuration, as described below for [Claude](#claude-proxy-workflow), [Codex](#codex-proxy-workflow), [OpenCode](#opencode-proxy-workflow), and [Copilot](#copilot-proxy-workflow).

The sandbox has no browser and publishes nothing beyond SSH. Open the URL the agent shows in a browser on your host or on any other machine. A device-code workflow (`copilot device-code`, `codex device-code`) needs no connection back into the sandbox: enter the code in the browser and the agent polls the provider itself. A browser workflow that waits for a callback on a local port inside the sandbox (`codex browser`) only completes when that port is reachable from your browser, which takes a port forward over SSH to the sandbox (see [SSH](ssh.md)); the catalog's login message for `codex` says so. `claude browser` and `opencode provider` show their URL or provider prompt and read the result in the terminal according to each agent's own documentation; follow the agent's instructions.

The exit status is zero when the agent's login command exited zero and non-zero otherwise, including when you cancel with Ctrl+C. A non-zero status prints `agents login failed` after the agent's own output. `login` needs the agent to be enabled; otherwise it names `agents enable NAME AGENT`.

Agents in one sandbox share the home data, so a login belongs to the sandbox, not to one session or run. `agents disable` keeps the credentials; `agents enable` afterwards finds them again.

### Claude proxy workflow

```text
sandboxed-agents agents login agent01 claude proxy --url http://proxy.example:8317
sandboxed-agents agents login agent01 claude proxy --url https://proxy.example --model claude-fable-5-1 < key.txt
sandboxed-agents agents login agent01 claude proxy --remove
```

The `proxy` workflow points Claude Code at a [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) server that you already run and that the sandbox can reach, and gives it one of the server's client API keys. It is the client half only: it installs, hosts, and configures no server, and it signs in to no upstream account. Claude Code then sends its requests to `/v1/messages` under the URL, with the key as a bearer token, instead of to Anthropic. The workflow follows the [Claude Code CLIProxyAPI guide](https://help.router-for.me/agent-client/claude-code.html) for the settings it writes and copies none of the guide's permission-bypass or model-tuning examples.

**What it writes.** The configuration lives in Claude Code's own user settings file in the home data, `/home/agent/.claude/settings.json`, which Claude Code reads on every start ([Claude Code authentication](https://code.claude.com/docs/en/authentication)): `env.ANTHROPIC_BASE_URL` holds the URL, `env.ANTHROPIC_AUTH_TOKEN` holds the key, and `model` is set to `ID` when you give `--model ID`. Beside them the workflow records a small ownership entry, `_sandboxedAgentsProxy`, which holds no secret: the SHA-256 of the URL value and of the key value it wrote, the model selection it set, and the one it replaced, the two models as plain JSON values. A later `--remove` uses it to tell its own entries from yours without a second copy of the key. The write merges into the existing file and keeps every other setting; it goes to a temporary file in the same directory, which is then renamed over the settings file, so a failure at any point leaves the previous file byte for byte as it was. The file is owned by `agent` and readable by `agent` only (mode `0600`). Because Claude Code reads it on every start, `agents run`, `agents session`, `shell NAME`, and an editor connected over SSH all see the configuration. Claude Code may put the two values into its own process environment; that is its documented client mechanism, not something the sandbox injects.

**`--url`.** The base address of the server as seen from inside the sandbox: `http` or `https`, a host, an optional port, and an optional path prefix. It takes no user information, query, fragment, or whitespace, and it must not end in `/v1`, which Claude Code appends itself; trailing slashes are removed. `127.0.0.1` and `localhost` are the sandbox's own loopback, not your host's: the sandbox adds no port forward and no route, so the server must be reachable from the container as written. For `http` to any host other than loopback, the command warns on standard error that the key travels unencrypted. A missing or invalid `--url` is a usage error that exits 2 before Podman is called.

**The key.** It is read the same way as the Azure DevOps token ([Integrations](integrations.md#azure-devops)) and is never accepted as an option or argument. When standard input is a terminal, a `Key:` prompt appears on standard error and nothing is echoed while you paste; Enter ends the input. Otherwise the first line of standard input is used, with surrounding whitespace removed, including a CRLF line ending, so a pipe or a file from any platform works and the workflow needs no terminal. Whitespace, a carriage return, NUL, or any other control character inside the key is rejected. An empty line, `</dev/null`, or such a key exits 1 and changes nothing: by then the sandbox checks, the manager's version and status answers, and the check that `claude` is enabled have run, and the configuration write has not started. Those checks come first, so a stopped sandbox or a silent manager is reported before any key is consumed. The key reaches the manager on its standard input only. It appears in no process argument on the host or in the sandbox, in no Podman argument, in no host environment variable, in no shell startup file, and in no manager log or command output.

**Refusals.** The workflow changes nothing and exits non-zero when the settings file is not a JSON object, when its `env` is not an object, when `env.ANTHROPIC_API_KEY` is already set, or when `apiKeyHelper` is set: each message names the cause. The same refusal applies to `--remove`. Those two settings are another way of giving Claude Code a credential, and the workflow never deletes such a credential and never sends it anywhere, in either direction: resolve the conflict yourself, by removing or moving the setting, before the proxy can be written or removed. A missing settings file is not an error: the workflow creates it.

**Success.** The command prints that the configuration was written and that the key was not checked against the server. It then suggests the noninteractive check, which is the only check there is:

```text
sandboxed-agents agents run agent01 claude -p 'Reply OK'
```

A reply means that Claude Code reached the server and the server accepted the key and the model. An authentication error in Claude Code's output means that the server rejected the key; a connection error means that the URL is not reachable from the sandbox. The sandbox interprets neither; `agents run` passes Claude Code's output and exit status through. Sessions and runs that were already running keep their old configuration until you start them again; the command restarts nothing.

The request path itself is covered offline by a contract test that runs a real `claude` command against a fake upstream server and asserts that every request goes to `/v1/messages` under the configured URL with `Authorization: Bearer` and the configured model, and that no request leaves for an Anthropic host. It needs a Claude Code executable on the machine that runs it:

```text
SANDBOXED_AGENTS_TEST_CLAUDE=/path/to/claude go test ./internal/manager -run TestClaudeProxyNativeClientReachesOnlyFakeUpstream -count=1
```

It has passed against Claude Code 2.1.301, which accepted the settings file with the ownership entry and sent the bearer key, the model, and the URL prefix to the fake upstream only. It does not replace the live checks against a real server, which the [manual checklist](manual-checklist.md#claude-proxy-workflow) still holds as not yet run.

**Running it again, and `--remove`.** A second `proxy` replaces the URL and the key, and `--model` replaces the model selection again. `--remove` reads no key and deletes only what the workflow owns: the two `env` entries when their values are still the ones it wrote, and the `model` entry when it is still the managed one, which is then set back to the selection it replaced or dropped if there was none. A URL, key, or model you edited by hand afterwards is yours and stays. One combination is refused: when the URL is still the managed one but the key has been edited and is still present, `--remove` exits 1 and leaves the whole file as it is, because deleting the endpoint alone would leave your key behind with no URL to bind it to, so that Claude Code would decide where it goes. The message says so and names the two ways out: restore the managed key by running `proxy` again, or remove `ANTHROPIC_BASE_URL` and `ANTHROPIC_AUTH_TOKEN` together in `settings.json` yourself. The other mixed states are handled without a refusal: when the key is already gone, the managed URL is deleted; when the URL was edited and the key is still the managed one, the key is deleted and your URL stays; when both were edited, both stay. `--remove` with `--url` or `--model` is a usage error. When nothing is managed, `--remove` changes nothing, still reports the removal, and exits zero. The workflow takes the manager lock for its write, so it refuses with the same retry message as an installation change while another agent or Tool change runs.

**`browser` and `proxy` together.** The workflow never touches the OAuth login of `browser`, in either direction. While the proxy configuration exists, Claude Code uses it; after `--remove`, a browser login that was there before applies again, and a browser login made while the proxy was configured applies once the proxy is removed.

**`agents status`.** The probe still runs `claude auth status --json`, which reads what Claude Code finds configured and never contacts the server. With a proxy key and no browser login, Claude Code 2.1.301 reports `loggedIn` true, so `agents status` shows `signed in yes`, and it made no request to the server to say so; the offline contract test above observed both. That `yes` means only that Claude Code counts the auth token in its settings as configured authentication. It does not say that the server accepts the key, and a later Claude Code version may answer differently. Use the `agents run` check above as the evidence, and let the [manual checklist](manual-checklist.md#claude-proxy-workflow) confirm the value against a live server.

**Where the key lives, and what can read it.** The key is stored as plaintext in the home volume. Every agent in the sandbox runs as `agent` and can read it, and so can anyone in `shell NAME` or connected over SSH. There is no encryption at rest; the keyring and encrypted-store work for other credentials ([#142](https://github.com/grauzone-labs/sandboxed-agents/issues/142), [#143](https://github.com/grauzone-labs/sandboxed-agents/issues/143)) does not cover it, and this workflow does not depend on either. The host keeps no copy. To take the key out of use, revoke it on the server; `--remove` only stops Claude Code from sending it. `remove NAME --volumes` deletes the home volume and the key with it.

**Persistence.** The URL, the key, and the managed model selection are home data, so they survive `stop` and `start`, `restart`, `update NAME`, `agents update`, and an `agents enable --force` reinstall of `claude`. `agents disable` keeps them, as it keeps every credential; `remove NAME --volumes` removes them.

### Codex proxy workflow

```text
sandboxed-agents agents login agent01 codex proxy --url http://proxy.example:8317 --model gpt-5.1-codex
sandboxed-agents agents login agent01 codex proxy --url https://proxy.example --model gpt-5.1-codex --replace-login < key.txt
sandboxed-agents agents login agent01 codex proxy --remove
```

The `proxy` workflow of `codex` points Codex at a [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) server that you already run and that the sandbox can reach, and gives it one of the server's client API keys. It shares the contract of the [Claude proxy workflow](#claude-proxy-workflow) above: it is the client half only, installing, hosting, and configuring no server and signing in to no upstream account; `--url` follows the same rules, including the loopback caveat, the `http` warning, and the ban on a trailing `/v1`; the key is read the same way, from the `Key:` prompt or the first line of standard input, never from an option or argument, and it appears in no process argument, Podman argument, host environment variable, log, or command output; and the key is checked against nothing. Codex then sends its requests to `/v1/responses` under the URL, with the key as a bearer token, instead of to OpenAI. The workflow follows the API-key mode of the [CLIProxyAPI Codex guide](https://help.router-for.me/agent-client/codex) and copies none of the guide's approval or sandbox examples; the guide's other mode, a ChatGPT login with the key in an `X-Api-Key` header, is not used. The [Codex proxy notes](codex-proxy.md) record those decisions for maintainers.

Two things differ from Claude because Codex differs: `--model ID` is required, and Codex keeps one stored login, so a ChatGPT login can only be replaced, never kept beside the key.

**`--model`.** Codex has no default model that fits a server it does not know, so you name the model ID that your server offers. The workflow writes it as Codex's top-level `model` and checks it against nothing: a wrong ID shows up as the server's error at the first request. `codex proxy --url URL` without `--model` is a usage error that exits 2 before Podman is called.

**Supported Codex versions.** The workflow needs Codex 0.166.0 or newer, the version the native contract test below passed against. The check reads the installed version from the agent selection, the one `agents status` shows, so a pin to an older version is refused as well. The refusal comes before the key is read; its message names `agents update` and `agents enable --version`. Older versions are untested, not known to be broken. The floor applies to setup only: `--remove` skips it on both the host and the manager, because removal uses the manager's own file operations and no Codex login API, and it must stay available after a downgrade so an owned proxy configuration cannot keep blocking the native logins; the ownership, lock, recovery, and enabled-status checks still apply to removal.

**What it writes.** Two files in Codex's own directory in the home data, `/home/agent/.codex/`, which Codex reads on every start ([Codex authentication](https://learn.chatgpt.com/docs/auth)):

- `config.toml` gets the top-level entries `model_provider = "cliproxyapi"` and `model = "ID"`, and the table `[model_providers.cliproxyapi]` with `name = "CLIProxyAPI"`, `base_url` set to the URL plus `/v1`, `wire_api = "responses"`, and `requires_openai_auth = true`, which tells Codex to use its stored login for this provider. The table holds no key and no header. Beside it the workflow records an ownership table, `[_sandboxedAgentsProxy]`, which holds no secret: a copy of the provider table it wrote, the SHA-256 of the key, whether `config.toml` already had a `model_providers` table, so that `--remove` keeps a table that was there before and drops only one the workflow created, and the `model_provider` and `model` values it replaced, each only when there was one. A later `--remove` uses it to tell its own entries from yours without a second copy of the key.
- `auth.json` holds the key, stored by Codex itself. The workflow runs `codex login --with-api-key` as `agent`, with the key on its standard input and `CODEX_HOME` pointed at a temporary directory inside the home data, so a login that fails changes nothing. It accepts the result only when that file holds exactly the key as `OPENAI_API_KEY` and no ChatGPT tokens, and then publishes it as the real `auth.json` in the order described under **Publication** below. The key reaches Codex on standard input only and is never put into `config.toml`.

**Publication.** The two files are published as one change under the manager lock and the Codex configuration lock, in a fixed order, so that a previous login is never left active beside a changed destination and no file the workflow did not write is replaced. It first checks that the recovery directory, `/home/agent/.codex/.sandboxed-agents-proxy/`, does not exist, and creates it with mode `0700`; while it exists, `agents run`, session starts and attaches, and every `login` workflow of Codex, `proxy --remove` included, refuse, while `agents session NAME codex --stop`, `status`, `enable`, `update`, and `disable` stay available ([Recover from an interrupted Codex proxy change](#recover-from-an-interrupted-codex-proxy-change)). The new contents go to private candidate files inside that directory, each synced to disk. The workflow then checks that `config.toml` and `auth.json` still hold what it read before the staged login, and refuses otherwise. It moves the previous `auth.json` and after it the previous `config.toml` into the directory as `auth.json.prev` and `config.toml.prev`, the login first so that no moment exists in which the old key sits beside a new destination. A move keeps each file's bytes and mode and copies nothing, and a login that does not change is later linked back from its moved file, so on this path the previous key is never duplicated; the new key exists in the staged login and in its candidate until both are removed. The workflow also notes each moved file's mode, for the one case below in which it writes a previous version again. Each candidate is then linked to its target name, `config.toml` first and `auth.json` second; a link succeeds only while no file of that name exists, so a file that something else created at that name is never replaced: it makes the step fail and is preserved, at the active name or, when the rollback moves it aside, inside the recovery directory. Once both are in place and verified, the previous versions, the candidates, and the recovery directory are removed, each after a check that it still holds what it should. When one of those removals fails, the workflow puts the change back: it writes each previous version it had already removed, from the bytes it still holds in memory, into a private candidate with the noted mode, links it back into the directory without clobbering, and then restores both files the same way as after any other failed step, so that `config.toml` and `auth.json` end with their previous bytes and modes, or absent where they were absent, after a write and after a `--remove` alike, and the message says `cannot finish Codex publication; previous configuration and login restored`. This is the one path on which previous bytes are written again rather than moved. When a step returns an error, the workflow moves whatever it finds at a target name into a `.failed-` subdirectory of the recovery directory, and, when every such file is one it published itself, links the previous files back the same no-clobber way, removes the directory, and says what was restored. When the workflow is interrupted instead, when a restoration fails, when a file at a target name is not one the workflow wrote, when a check before a removal finds a file changed, or when a previous version cannot be written back because something now sits at its name, the recovery directory stays with everything it holds, nothing is overwritten, and the message says that Codex publication requires recovery. A file the workflow stages anew, the configuration and a new login, is created with mode `0600`, subject to the process umask, so it is owned by `agent` and readable by `agent` only; a file that `--remove` links back or that a rollback restores keeps the mode it had, which may be `0644`. The Codex directory is created with mode `0700` when it is missing. Because Codex reads them on every start, `agents run`, `agents session`, `shell NAME`, and an editor connected over SSH all see the configuration.

**What publication guarantees, and what it does not.** The guarantee covers an interrupted manager process, a killed command, a panic, or a container stop at any point of the change, and the races the workflow checks for: an edit of either file between its read and the move, a moved file whose contents differ from what was read, a file created at a target name before the link, and a changed file at the final verification. In those cases the previous key is never active beside a changed configuration, no file the workflow did not write is overwritten or discarded, and the previous versions are either back in place or kept in the recovery directory, with one exception: when the manager is interrupted during the cleanup after a verified publication, the new files are in place and match each other, but a previous version that the cleanup had already removed is gone; a removal that fails without an interruption restores both files instead. A managed run is covered too: `agents run NAME codex` and a `codex proxy` change exclude each other through the Codex configuration lock, so no such run starts Codex while a change is in progress and no change begins while such a run is in progress. The two files are not an atomic unit beyond that bound. The candidate contents are synced before publication, but the moves and links that make them current, and the directory entries they change, are not, so a power loss or kernel crash during the change gives no promise about which names exist on disk afterwards and none that the two files were committed together. A process that already holds `auth.json` or `config.toml` open keeps its descriptor and can write through it; a writer that does not go through the manager is detected only when it races one of the checks; a Codex that was already running when the change began has loaded what it loaded. The change also isolates no network traffic: it routes Codex's model requests to the server and nothing else, as the [Codex proxy notes](codex-proxy.md#what-the-native-contract-test-isolates) explain.

The write decodes `config.toml` and encodes it again, so every other entry, table, and profile keeps its value, but comments, key order, and layout are not preserved. Keep a copy if the layout matters to you.

**Only file credentials.** The workflow stores the key as a file and nowhere else. When `config.toml` sets `cli_auth_credentials_store` to anything other than `file`, the workflow refuses and changes nothing. An unset value is accepted: the staged login runs with the file store selected explicitly, and the sandbox offers no operating-system credential store for Codex's default to prefer.

**One stored login, and `--replace-login`.** Codex keeps one login. When `auth.json` holds a ChatGPT login, from `browser` or `device-code`, the workflow refuses, names `--replace-login`, and changes nothing; by then the key has been read on the host and handed to the manager, which discards it without passing it to Codex. With `--replace-login`, the ChatGPT login is replaced by the API-key login and is kept nowhere: `--remove` does not bring it back, so sign in again with `browser` or `device-code` afterwards. An existing API-key login, for example one you made yourself with `codex login --with-api-key`, is replaced without the option. `--replace-login` with `--remove`, or on any agent other than `codex`, is a usage error that exits 2 before Podman is called.

**Refusals.** The workflow changes nothing and exits non-zero when `config.toml` is not valid TOML, when `model_providers` is not a table, when a `cliproxyapi` provider table exists that the workflow did not write or that was edited since, when the ownership table is malformed, when `auth.json` is not a JSON object, when `cli_auth_credentials_store` is set to a value other than `file`, when the directory or either file is not owned by `agent`, is a symbolic link, or has more than one link, when the recovery directory `/home/agent/.codex/.sandboxed-agents-proxy/` exists from an interrupted change ([below](#recover-from-an-interrupted-codex-proxy-change)), or when `config.toml` or `auth.json` changed while the staged login ran. Each message names the cause, and the same refusals apply to `--remove`. A provider table of your own under the name `cliproxyapi` is never replaced: rename or remove it yourself first. A missing directory or file is not an error: the workflow creates what it needs.

**Success.** The command prints that the configuration was written, that the key was not checked against the server, and that existing sessions must be restarted to load it. The noninteractive check, the only check there is, runs Codex once without a terminal; `--skip-git-repo-check` lets it run in a workspace that is not a Git repository:

```text
sandboxed-agents agents run agent01 codex exec --skip-git-repo-check 'Reply OK'
```

A reply means that Codex reached the server and the server accepted the key and the model. An authentication error in Codex's output means that the server rejected the key; a connection error means that the URL is not reachable from the sandbox. The sandbox interprets neither; `agents run` passes Codex's output and exit status through. Sessions and runs that were already running keep their old configuration until you start them again; the command restarts nothing. `agents status` has no probe for `codex` and shows `signed in unknown` before and after the workflow; the `agents run` check is the evidence.

The request path is covered offline by a contract test that runs a real `codex` command against a fake upstream server. It sets up the proxy with `--replace-login` over a stored ChatGPT login, asserts that `codex exec` sends a POST to `/v1/responses` under the configured URL with `Authorization: Bearer` and the configured model and that no request reaches an OpenAI or ChatGPT host, then removes the proxy and asserts that the previous model and an unrelated profile are back and the owned login is gone. It needs a Codex executable on the machine that runs it:

```text
SANDBOXED_AGENTS_TEST_CODEX=/path/to/codex go test ./internal/manager -run TestCodexProxyNativeClient -count=1
```

It has passed against Codex 0.166.0. The test routes all of Codex's traffic to the fake server and turns off Codex's analytics and some of its features for its own `codex exec` only; the workflow changes none of those settings in your sandbox, as the [Codex proxy notes](codex-proxy.md#what-the-native-contract-test-isolates) explain. It does not replace the live checks against a real server, which the [manual checklist](manual-checklist.md#codex-proxy-workflow) still holds as not yet run.

**Running it again, and `--remove`.** A second `proxy` replaces the URL, the key, and the model; the selection it records as the previous one stays the one from before the first run, as long as `model_provider` still names `cliproxyapi`. `--remove` reads no key and deletes only what the workflow owns: the `cliproxyapi` provider table, the ownership table, and the stored login when `auth.json` still holds the key the workflow wrote and no ChatGPT tokens. It sets `model_provider` and `model` back to the values it replaced, or drops them if there were none, only while `model_provider` still names `cliproxyapi`; a provider you selected since stays, and so does its model. A later ChatGPT login or an API-key login of your own stays too: ownership is checked by the key's hash, and a login with tokens is never deleted. The previous ChatGPT login that `--replace-login` replaced is not restored. `--remove` with `--url`, `--model`, or `--replace-login` is a usage error. When nothing is managed, `--remove` changes nothing, still reports the removal, and exits zero. Otherwise `--remove` publishes through the same recovery directory and in the same order as a write, so an interrupted removal is detected and refused the same way. The workflow takes the manager lock for the whole operation, the staged login included, so it refuses with the same retry message as an installation change while another agent or Tool change runs, including a `browser` or `device-code` login of `codex` that is still waiting for you. It also refuses, before it reads a key, while a Codex session started with `agents session NAME codex` exists, and names `agents session NAME codex --stop`; a session start requested during the change refuses with the retry message like any other change. And it holds the Codex configuration lock exclusively from before the staged login until the change is complete or restored, so it refuses with `Codex is running; wait for managed runs to finish before changing the proxy` while an `agents run NAME codex` is in progress, and an `agents run NAME codex` requested during the change refuses with `Codex proxy change is in progress; retry`. Neither waits. The lock is the file `codex.lock` beside the manager lock in `/home/agent/.local/share/sandboxed-agents/`, held by the `agents run` command for as long as it runs and shared between runs, so runs do not hold each other back and no other agent or Tool is affected. It covers the manager's own commands only: a Codex started in `shell NAME`, over SSH, or by an editor takes no lock and is not seen. Because the lock ends with the `agents run` command and a Codex can outlive it, each managed run also leaves a marker file in `/home/agent/.local/share/sandboxed-agents/codex-runs/` that only a completed run removes; the workflow refuses, before it reads a key, while any entry exists in that directory or the directory cannot be read, with `interrupted managed Codex run requires recovery; see docs/codex-proxy.md`. A marker holds no credential and no process ID, and nothing checks whether a process stands behind it: clearing it is your decision, after you have stopped every Codex ([Recover from an interrupted Codex proxy change](#recover-from-an-interrupted-codex-proxy-change)).

**`browser`, `device-code`, and `proxy` together.** While the proxy configuration exists, Codex uses it, and a ChatGPT login stored while it exists would replace the key and be sent to the server, which is not what the server expects. So `agents login NAME codex browser` and `agents login NAME codex device-code` refuse while `config.toml` selects `model_provider = "cliproxyapi"` or still holds the ownership table, which includes a `config.toml` whose selection you changed by hand while the table stayed: no login message is printed, Codex is not started, and both files stay as they are. While the ownership table exists the message names `proxy --remove`; run it first, deliberately. When only the selection is there, the workflow owns nothing and `--remove` would change nothing, so the message asks you to remove the top-level `model_provider` selection from `/home/agent/.codex/config.toml` by hand. After it, Codex has no login unless you made one since, and `browser` and `device-code` work exactly as before. Both native workflows hold the manager lock for the whole interactive login, so a `codex proxy` write or removal started in the meantime refuses with the retry message instead of changing the files while Codex writes its login. The guard covers these two commands only: a `codex login` you run in `shell NAME`, over SSH, or through `agents run NAME codex login ...`, and a Codex that was already running, are not controlled.

**Where the key lives, and what can read it.** The key is stored as plaintext in `auth.json` in the home volume, which is where Codex itself keeps an API-key login. Every agent in the sandbox runs as `agent` and can read it, and so can anyone in `shell NAME` or connected over SSH. There is no encryption at rest; the keyring and encrypted-store work for other credentials ([#142](https://github.com/grauzone-labs/sandboxed-agents/issues/142), [#143](https://github.com/grauzone-labs/sandboxed-agents/issues/143)) does not cover it, and this workflow does not depend on either. The host keeps no copy. To take the key out of use, revoke it on the server; `--remove` only stops Codex from sending it. `remove NAME --volumes` deletes the home volume and the key with it.

**Persistence.** The URL, the model, the key, and the ownership table are home data, so they survive `stop` and `start`, `restart`, `update NAME`, `agents update`, and an `agents enable --force` reinstall of `codex`. `agents disable` keeps them, as it keeps every credential; `remove NAME --volumes` removes them.

#### Recover from an interrupted Codex proxy change

When `/home/agent/.codex/.sandboxed-agents-proxy/` exists, a `proxy` write or removal did not complete: the manager was killed or the container stopped during publication, a restoration failed, or the workflow found a file at a target name that it did not write. While the directory exists, `agents run NAME codex`, starting or attaching an `agents session NAME codex`, every `agents login NAME codex` workflow, and `codex proxy --remove` refuse. The message says that Codex publication requires recovery and names the directory and the [Codex proxy notes](codex-proxy.md#recovery), which hold the steps. `agents session NAME codex --stop`, `status`, `enable`, `update`, and `disable` stay available, so that you can end a running Codex first.

The manager removes nothing, restores nothing, and infers nothing from the files it finds: which version is the one you want is your decision, and the reset in the notes, which stops every Codex, quarantines the whole Codex directory under a unique name, and signs in again to the provider you choose, is the supported way to make it. The refusal covers the manager's commands only: a Codex started in `shell NAME`, over SSH, or by an editor reads whatever the files hold.

A `codex proxy` command that says `interrupted managed Codex run requires recovery; see docs/codex-proxy.md` found a run marker in `/home/agent/.local/share/sandboxed-agents/codex-runs/` or could not read that directory: an `agents run NAME codex` ended without Codex exiting on its own, and the Codex it started may still be running. The command refused before reading a key and changed nothing, and no recovery directory is involved. Stop every Codex in the sandbox, make sure no managed run and no proxy login is in progress, and then delete the marker files by name, as the [notes](codex-proxy.md#interrupted-managed-runs) describe. A `restart` of the sandbox ends its processes but keeps the markers, and quarantining `/home/agent/.codex` does not clear them.

The staged login runs in a separate directory beside `/home/agent/.codex`, not inside it, named `/home/agent/.codex-proxy-` followed by random digits. The workflow removes it when it returns, but a manager killed or a container stopped at any point from the staged login to the end of publication leaves it, with the pasted key in its `auth.json` once the login had completed, and without a recovery directory when the interruption came before publication began. The notes say how to [find and delete such a directory](codex-proxy.md#recovery) without printing its contents.

### OpenCode proxy workflow

```text
sandboxed-agents agents login agent01 opencode proxy --url http://proxy.example:8317 --model ID
sandboxed-agents agents login agent01 opencode proxy --url https://proxy.example --model ID < key.txt
sandboxed-agents agents login agent01 opencode proxy --remove
```

The `proxy` workflow of `opencode` points OpenCode at a [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) server that you already run and that the sandbox can reach, and gives it one of the server's client API keys. Like the [Claude workflow](#claude-proxy-workflow), it is the client half only: it installs, hosts, and configures no server, signs in to no upstream account, and checks the key against nothing. OpenCode then sends its chat requests to `/v1/chat/completions` under the URL, with the key as a bearer token. The two workflows share one contract: `--url` is validated by the same rules, the key is read the same way, and `--remove` deletes only what the workflow owns. Two things differ. `--model ID` is required, because OpenCode addresses every model through a provider and the workflow has to name one. And the workflow does not follow the [CLIProxyAPI OpenCode guide](https://help.router-for.me/agent-client/opencode.html) in pointing the built-in `openai` and `anthropic` providers at the server: it adds a provider of its own, defined the way the [OpenCode providers documentation](https://opencode.ai/docs/providers/) describes a custom OpenAI-compatible provider, so that whatever `opencode auth login` stored keeps working.

**What it writes.** The configuration lives in OpenCode's own user configuration file in the home data, `/home/agent/.config/opencode/opencode.json`, which OpenCode reads on every start. Under `provider` the workflow writes a provider with the id `cliproxyapi`: its `npm` entry is `@ai-sdk/openai-compatible`, its `name` is `CLIProxyAPI`, `options.baseURL` holds the URL with `/v1` appended, `options.apiKey` holds the key, and `models` holds one entry for `ID`. The top-level `model` is set to `cliproxyapi/ID`, so the model is also the one OpenCode's own `--model` flag can name. Beside the two options the workflow records a small ownership entry, `_sandboxedAgentsProxy`, inside the provider's `options`; it holds no secret: a version number, the `model` selection the workflow replaced as a plain JSON value. OpenCode passes unknown entries in `options` on to the provider package, which ignores them: the contract test below observed OpenCode 1.19.5 accepting the file with the marker in place. The write merges into the existing file and keeps every other key, other providers included; it goes to a temporary file in the same directory, which is then renamed over the configuration file, so a failure at any point leaves the previous file byte for byte as it was. The file is owned by `agent` and readable by `agent` only (mode `0600`). Because OpenCode reads it on every start, `agents run`, `agents session`, `shell NAME`, and an editor connected over SSH all see the configuration.

**`--url`, `--model`, and the key.** `--url` takes the same values as for [`claude proxy`](#claude-proxy-workflow): `http` or `https`, a host, an optional port, and an optional path prefix, with no user information, query, fragment, or whitespace, and not ending in `/v1`, which the workflow appends itself. Loopback names mean the sandbox's own loopback, and `http` to any host other than loopback warns on standard error that the key travels unencrypted. `--model ID` is the ID of a model your server serves, written as the server names it, not the example model of any guide; the workflow checks it against nothing, and a missing `--model` is a usage error that exits 2 before Podman is called, as is a missing or invalid `--url`. The key is read exactly as for `claude proxy`: at a `Key:` prompt on standard error without echo when standard input is a terminal, otherwise from the first line of standard input, never from an option or argument, and it reaches the manager on its standard input only. An empty, whitespace-bearing, or control-bearing key exits 1 and changes nothing, after the sandbox and manager checks and the check that `opencode` is enabled have run.

**Refusals.** The workflow changes nothing and exits non-zero, naming the file, when the configuration file is not a plain JSON object, when its `provider` entry is not an object, or when a `cliproxyapi` provider is already there that the workflow did not write (one without a valid ownership entry). It also refuses, naming that file, when an `opencode.jsonc` sits beside it in the same directory: the workflow writes plain JSON only and will not add a second configuration file next to a JSONC one that OpenCode also reads. Comments, trailing commas, or an unparseable file count as not plain JSON. The directories and the file must be owned by `agent`, and the file must be a regular file, not a link. The same refusals apply to `--remove`. A missing configuration file is not an error: the workflow creates it, with its directory.

**Success.** The command prints that the configuration was written and that the key was not checked against the server. It then suggests the noninteractive check, which is the only check there is, in a form for POSIX shells and a form for PowerShell:

```text
sandboxed-agents agents run agent01 opencode run 'Reply OK' < /dev/null
'' | sandboxed-agents agents run agent01 opencode run 'Reply OK'
```

Both keep standard input off the terminal, so that `agents run` uses plain pipes and `opencode run` does not wait for input: the redirect gives OpenCode an empty input, and the PowerShell pipeline, since PowerShell has no `<` redirection, sends one empty line and then the end of input. A reply means that OpenCode reached the server and the server accepted the key and the model. An authentication error in OpenCode's output means that the server rejected the key; a connection error means that the URL is not reachable from the sandbox. The sandbox interprets neither; `agents run` passes OpenCode's output and exit status through. Sessions and runs that were already running keep their old configuration until you start them again; the command restarts nothing.

The request path itself is covered offline by a contract test that runs a real `opencode` command against a fake upstream server and asserts that the one chat request goes to `/v1/chat/completions` under the configured URL with `Authorization: Bearer` and the configured model, and that no request leaves for an OpenAI or Anthropic host. It needs an OpenCode executable on the machine that runs it:

```text
SANDBOXED_AGENTS_TEST_OPENCODE=/path/to/opencode go test ./internal/manager -run TestOpenCodeProxyNativeClientReachesOnlyFakeUpstream -count=1
```

It has passed against OpenCode 1.19.5 from the npm package `opencode-ai`, outside a sandbox, with a fresh `HOME` and fresh XDG directories, so that the test saw only the configuration the workflow wrote. The test also sets `OPENCODE_DISABLE_MODELS_FETCH=1`, `OPENCODE_DISABLE_AUTOUPDATE=1`, and `OPENCODE_DISABLE_DEFAULT_PLUGINS=1` to keep OpenCode's other network activity out of the measurement; the sandbox sets none of them, so OpenCode in a sandbox may fetch its model list, check for updates, and load its default plugins as it does without the proxy. OpenCode sent the bearer key, the model, and the URL prefix to the fake upstream only, and printed the fake upstream's reply.

**What OpenCode fetches on first use.** For the provider package, nothing, in OpenCode 1.19.5. The adapter the workflow names, `@ai-sdk/openai-compatible`, is a literal import bundled into the `opencode` executable at build time, and the provider loader takes that bundled entry and returns before the install fallback that would fetch a package from the registry. The workflow writes the name as the `cliproxyapi` provider's `npm` entry with no model-level override, and a configured provider `npm` takes precedence over the catalog defaults. This is read from OpenCode's source at the tag `v1.19.5` and checked against a locally inspected copy of the published `opencode-linux-x64` 1.19.5 archive; the executables on the live hosts were not hashed against it. The contract test corroborates it: OpenCode's one connection to `registry.npmjs.org:443` was refused and the chat still completed. Sources, artifact details, and limits are in the [first-use record](validation/issue-146/first-use.md#what-the-provider-package-needs-on-first-use).

**What that does not cover.** The statement is about the provider package only; OpenCode's other network paths, such as the model-list fetch, the updater's registry query, and a background plugin install, are independent of the adapter and stay enabled in a sandbox. The first `agents run` after `proxy` inside a sandbox has been observed once on a Linux host and a Windows host at commit `dbd5237a694064e7f0c64f64263ad64cac387610` on 2026-11-06 with OpenCode 1.19.5 and the sandbox's defaults ([first-use observation](validation/issue-146/first-use.md)): both runs printed the reply, exited zero, printed no install or download message, and wrote files in the `npm` cache among others; what those files hold and what wrote them is unknown. The reading holds for 1.19.5 only. A later release may require a package fetch on first use, so recheck it; the [manual checklist](manual-checklist.md#opencode-proxy-workflow) keeps the observation as an item for each live checkpoint.

**Running it again, and `--remove`.** A second `proxy` replaces the URL, the key, and the model; `--model` is required each time. The selection recorded as the one to restore stays the selection that the first `proxy` replaced, as long as `model` still points at the `cliproxyapi` provider. `--remove` reads no key and deletes the whole `cliproxyapi` provider, which the workflow owns as a unit: a URL or key you edited inside it goes with it, because the provider cannot exist without the ownership entry the workflow wrote. The top-level `model` is reset only while it still starts with `cliproxyapi/`: it goes back to the selection the workflow replaced, or is dropped if there was none. A `model` you changed to another provider by hand is yours and stays. `--remove` with `--url` or `--model` is a usage error. When nothing is managed, `--remove` changes nothing, still reports the removal, and exits zero. The workflow takes the manager lock for its write, so it refuses with the same retry message as an installation change while another agent or Tool change runs.

**`provider` and `proxy` together.** The workflow never touches what `opencode auth login` stores, in either direction, and it never changes the built-in `openai` and `anthropic` providers. While the proxy configuration exists, OpenCode's default model is the proxied one; a provider login made before or during stays available under its own provider, and after `--remove` OpenCode chooses a model from the providers it still has configured, as it did before.

**`agents status`.** OpenCode has no status probe, so `agents status` shows `signed in unknown` before and after `proxy`, as it always does for `opencode` ([why](agent-status-probes.md)). The `agents run` check above is the only evidence that the server accepts the key.

**Where the key lives, persistence.** The key is stored as plaintext in `opencode.json` in the home volume, with the same consequences as for `claude proxy`: every agent in the sandbox, `shell NAME`, and an SSH connection can read it, the host keeps no copy, and revoking it on the server is the way to take it out of use. The URL, the key, and the managed model selection survive `stop` and `start`, `restart`, `update NAME`, `agents update`, and an `agents enable --force` reinstall of `opencode`; `agents disable` keeps them, and `remove NAME --volumes` removes them.
### Copilot proxy workflow

```text
sandboxed-agents agents login agent01 copilot proxy --url http://proxy.example:8317 --model gpt-6.1-sol
sandboxed-agents agents login agent01 copilot proxy --url https://proxy.example --model gpt-6.1-sol --wire-api responses < key.txt
sandboxed-agents agents login agent01 copilot proxy --remove
```

The `proxy` workflow of `copilot` points Copilot CLI at a [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) server that you already run and that the sandbox can reach, and gives it one of the server's client API keys, under the same contract as the [Claude proxy workflow](#claude-proxy-workflow): client half only, no server installed or configured, no upstream account signed in, the key read from standard input and checked against nothing. Copilot CLI then sends the requests of the chosen model to `/v1/chat/completions` under the URL, or to `/v1/responses` with `--wire-api responses`, with the key as a bearer token, instead of to GitHub's Copilot inference hosts. The workflow follows [Adding LLM models to Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-llm-models) for the file it writes. Copilot needs a model that supports tool calling and streaming, and GitHub does not test Copilot CLI against CLIProxyAPI; the contract test and the manual checks below are the evidence that the combination works.

**What it writes.** The configuration lives in Copilot CLI's own provider registry in the home data, `/home/agent/.copilot/providers.json`, the bring-your-own-key file that Copilot reads on every start, so `agents run`, `agents session`, `shell NAME`, and an editor connected over SSH all see it. The workflow writes one provider entry, `name` `cliproxyapi`, `type` `openai`, `baseUrl` set to the URL with `/v1` appended, and `apiKey` set to the key, plus `wireApi` `responses` only when you give `--wire-api responses`; with the default `completions` it writes no `wireApi` field, which is Copilot's own default. It also writes one model entry, `id` set to `ID` from `--model ID` and `provider` `cliproxyapi`. Beside them it records the ownership entry `_sandboxedAgentsProxy`, which holds no secret: a version and the SHA-256 of the provider entry it wrote, so that a later run or `--remove` can tell its own provider from one you edited without a second copy of the key. The write merges into the existing file and keeps every other provider, model, and field; it goes to a temporary file in the `.copilot` directory, which is then renamed over the registry, so a failure at any point leaves the previous file byte for byte as it was. The file is owned by `agent` and readable by `agent` only (mode `0600`); a missing file or directory is created. The workflow sets no environment variable: it does not use the legacy `COPILOT_PROVIDER_*` or `COPILOT_MODEL` variables, which the registry takes precedence over, and it writes the key itself, never a `$VARIABLE` reference, because Copilot reads the file as literal text and interpolates nothing.

**`--url`.** The same rules as for `claude proxy`: `http` or `https`, a host, an optional port, and an optional path prefix; no user information, query, fragment, or whitespace; trailing slashes removed; loopback is the sandbox's own; `http` to a host other than loopback warns that the key travels unencrypted; a missing or invalid value is a usage error that exits 2 before Podman is called. It must not end in `/v1`: here the workflow appends `/v1` itself when it writes `baseUrl`.

**`--model ID`, required.** `ID` is a model the server serves. Unlike `claude proxy`, the workflow cannot do without it, because Copilot CLI addresses a bring-your-own-key model only through a model entry, so a missing `--model` is a usage error that exits 2 before Podman is called. The entry makes the model available; it does not make it the default. Select it on each run with `--model cliproxyapi/ID`, or in a session with Copilot's `/model`; Copilot's own `/model --global` persists a default, outside this workflow, and the workflow neither sets nor promises one. A second run with another `--model` adds a second entry and keeps the first; both select through `cliproxyapi/`.

**`--wire-api completions|responses`.** Which OpenAI-style API Copilot speaks to the server: `completions` is the default and uses `/v1/chat/completions`; `responses` uses `/v1/responses`. Which one a model works best with depends on the server and the model; the [manual checklist](manual-checklist.md#copilot-proxy-workflow) proves a tool call under each. Any other value, `--wire-api` together with `--remove`, and `--wire-api` on another agent or workflow are usage errors that exit 2 before Podman is called.

**Minimum version.** The workflow needs Copilot CLI 1.0.106 or newer, a stable release: a prerelease is refused. That is the version the contract test below ran against, a tested floor, not a claim about the earliest upstream release with the registry fields ([maintainer notes](maintainers.md#copilot-cli-floor-of-the-proxy-workflow)). An older installed or pinned version is refused before the key is read, on the host from the version the manager reports and once more in the manager, with a message that names `agents update NAME copilot --unpin` and `agents enable NAME copilot --version 1.0.106`. `--remove` has no version floor.

**The key.** It is read exactly as for `claude proxy`: a `Key:` prompt without echo when standard input is a terminal, the first line of standard input otherwise, never an option or argument, never a process argument, environment variable, shell startup file, log line, or command output. The sandbox checks, the manager's answers, the check that `copilot` is enabled, and the version floor run first, so a stopped sandbox, a silent manager, or an old Copilot is reported before any key is consumed.

**Refusals.** The workflow changes nothing and exits non-zero when the registry is not a JSON object, when `providers` or `models` is not an array of objects whose `name` or `id` is a nonempty string, when a model has no `provider` string, when the ownership entry is malformed, when the `.copilot` directory or the file is not owned by `agent`, not a directory or a regular file, or a symbolic link, or when a `cliproxyapi` provider or a model pointing to `cliproxyapi` exists that the workflow did not write: a provider with no ownership entry, a second provider of that name, or one whose hash no longer matches because it was edited. Each message names the cause, and the same refusals apply to `--remove`. Resolve a conflict yourself, by renaming or removing your own `cliproxyapi` entries, before the proxy can be written or removed.

**Success.** The command prints that the configuration was written and that the key was not checked against the server, names the `--model cliproxyapi/ID` selection, says that GitHub features still need the `device-code` login, and reminds you that running sessions keep their old configuration until you start them again; it restarts nothing. The check is the noninteractive run with that selection:

```text
sandboxed-agents agents run agent01 copilot -p 'Reply OK' --model cliproxyapi/ID
```

A reply means that Copilot reached the server and the server accepted the key and the model. An authentication error in Copilot's output means that the server rejected the key; a connection error means that the URL is not reachable from the sandbox. The sandbox interprets neither; `agents run` passes Copilot's output and exit status through.

The request path is covered offline by a contract test that runs a real `copilot` command against a fake upstream server in four scenarios: each wire API, once without a GitHub token and once with a dummy `GH_TOKEN` in the environment. The test points the command's `HTTP_PROXY`, `HTTPS_PROXY`, and `ALL_PROXY` at the fake server, which rejects every proxied destination it does not expect; it is a local proxy setting, not operating-system network isolation. For each scenario it asserts a streaming `POST` with tool definitions to `/v1/chat/completions` or `/v1/responses` under the configured URL prefix with `Authorization: Bearer` and the configured model ID, that the dummy token appears in no request to the server, and that the fake server saw no other request: it refuses a signed-in Copilot's account-metadata request to `api.github.com` locally with a 403, because the CLI still asks GitHub for its account while it uses a bring-your-own-key model, and it permits no Copilot inference traffic. It needs a Copilot CLI executable on the machine that runs it, and it checks that the executable reports version 1.0.106 before it runs anything:

```text
SANDBOXED_AGENTS_TEST_COPILOT=/absolute/copilot go test ./internal/manager -run TestCopilotProxyNativeClient -count=1 -v
```

Without the variable the test skips, so the ordinary `go test ./...` run does not cover it. All four scenarios have passed against Copilot CLI 1.0.106, whose `--version` output the test asserted, with the streaming tool-enabled request and the configured bearer key at the fake upstream in each. It does not replace the live checks against a real server, which the [manual checklist](manual-checklist.md#copilot-proxy-workflow) holds as not yet run.

**Running it again, and `--remove`.** A second `proxy` replaces the managed provider, so the URL, the key, and the wire API take the new values, and adds the model entry when it is not there yet. `--remove` reads no key and deletes only what the workflow owns: the `cliproxyapi` provider when it is still the one the workflow wrote, every model entry that points to `cliproxyapi`, and the ownership entry; every other provider and model stays. A `cliproxyapi` provider you edited by hand is yours: `--remove` refuses with the same message as a write and leaves the whole file as it is, so that no key of yours is deleted and no model of yours is left pointing nowhere. `--remove` with `--url`, `--model`, or `--wire-api` is a usage error. When nothing is managed, `--remove` changes nothing, still reports the removal, and exits zero. The workflow takes the manager lock for its write, so it refuses with the same retry message as an installation change while another agent or Tool change runs.

**`device-code` and `proxy` together.** The workflow never touches the GitHub login of `device-code`, in either direction, and `--remove` leaves it as it was. Inference through `cliproxyapi/ID` needs no GitHub login: the sandbox sends only the registry's key to the server, and the GitHub token is written to no registry entry and sent to no server, which the contract test asserts with its dummy token. Everything GitHub hosts still needs `device-code`: GitHub's own models, and the features Copilot asks GitHub for, such as repository and pull request access. A signed-in Copilot may still ask GitHub for account metadata while it uses the proxy model; that request carries the GitHub token to GitHub, not to the server.

**`agents status`.** `copilot` has no status probe, so `agents status` shows `signed in unknown` with or without the proxy configuration ([why](agent-status-probes.md)). The `agents run` check above is the only evidence that the key works.

**Where the key lives, and what can read it.** The same as for `claude proxy`: the key is plaintext in the home volume, readable by every agent in the sandbox, by anyone in `shell NAME`, and over SSH, with no encryption at rest and no host copy, which Copilot's documentation states for the registry as well. To take the key out of use, revoke it on the server; `--remove` only stops Copilot from sending it, and `remove NAME --volumes` deletes the home volume and the key with it.

**Persistence.** The provider entry, the model entry, and the ownership entry are home data, so they survive `stop` and `start`, `restart`, `update NAME`, `agents update`, and an `agents enable --force` reinstall of `copilot`. `agents disable` keeps them, as it keeps every credential; `remove NAME --volumes` removes them.

## Run an agent once

```text
sandboxed-agents agents run agent01 claude --help
sandboxed-agents agents run agent01 codex exec "list the TODO comments"
sandboxed-agents agents run agent01 opencode run "summarize README.md" < /dev/null
```

`run` starts the agent's command once in `/workspace` as `agent`, with every argument after the agent name passed on unchanged and in order, including arguments that start with a dash. So `--help` after the agent name shows the agent's own help; `agents run --help` without a sandbox name shows the help of `agents run` itself. The agent's standard input, output, and error are your terminal's streams, and the exit status of `agents run` is the agent's exit status. Only `run` passes another program's exit status through; every other `agents` command uses its own.

A terminal is not required. When both standard input and standard output are a terminal, the agent gets a pseudo-terminal and runs interactively; otherwise it runs with plain pipes, so you can script it, redirect its output, or feed it input from a file. In PowerShell, which has no `<` redirection, pipe an empty string instead of redirecting from `/dev/null`: `'' | sandboxed-agents agents run agent01 opencode run "summarize README.md"`. The agent has to be enabled; otherwise `run` names `agents enable NAME AGENT`. `agents run NAME codex` also refuses while a Codex proxy change is left incomplete ([recovery](#recover-from-an-interrupted-codex-proxy-change)). It holds the Codex configuration lock, shared, for as long as the command runs, so it refuses with `Codex proxy change is in progress; retry` while a `codex proxy` write or removal is in progress, and that change refuses while the run is in progress; runs do not hold each other back, and no other agent or Tool is affected ([Codex proxy workflow](#codex-proxy-workflow)). While it holds the lock, the command records the run as an empty marker file in `/home/agent/.local/share/sandboxed-agents/codex-runs/`, created before Codex starts and removed only when Codex has exited on its own, with any exit status. When Codex is ended by a signal, `Ctrl+C` included, when the manager is killed, or when the start fails, the marker stays, the command says `interrupted managed Codex run requires recovery; see docs/codex-proxy.md` when it can still print, and the next `codex proxy` write or removal refuses until you [clear the marker by hand](#recover-from-an-interrupted-codex-proxy-change). No run is held back by a marker.

A run is synchronous and not persistent: `agents run` waits for the agent and returns its exit status, and nothing in the sandbox keeps the run or reattaches to it. Interactively, the agent runs on a pseudo-terminal and normally stops when that terminal closes. With plain pipes, the agent is a `podman exec` process in the sandbox and the manager does not guarantee that it stops when the host command or the SSH connection goes away. Do not rely on either case to end the agent in time, and do not use `run` for an agent that should keep working: for that, use a [session](#keep-an-agent-running-in-a-session), which has a recorded lifetime and `--stop`.

## Keep an agent running in a session

```text
sandboxed-agents agents session agent01 opencode
sandboxed-agents agents session agent01 opencode --stop
```

An agent session is a persistent terminal session running one agent in `/workspace`, which you can detach from and reattach to. The manager keeps it in a tmux server of its own, run as `agent`, with tmux defaults and no user configuration. There is at most one session per agent in a sandbox, and the session's name is the agent's name.

`agents session NAME AGENT` starts the agent's session when none runs and attaches to it, or attaches to the existing one. Starting and attaching need an interactive terminal; without one the command fails and starts nothing. Only starting and stopping take the manager lock; attaching does not, so a second terminal can attach while a change on another agent runs. Starting or attaching a `codex` session refuses while a Codex proxy change is left incomplete; `--stop` does not, so that the Codex can be ended before [recovery](#recover-from-an-interrupted-codex-proxy-change). Starting checks that again under the manager lock, after the session list has been read. While a Codex session exists, a `codex proxy` write or removal refuses and names `--stop`.

- **Detach** with the tmux default, `Ctrl+b` then `d`. The agent keeps running. Closing the terminal, dropping an SSH connection, or killing the host command detaches too and leaves the agent alive.
- **Reattach** from any terminal, including a second one while the first is still attached, with the same `agents session NAME AGENT`. All attached terminals show the same session.
- **The session ends with its agent.** When the agent process exits, for example when you quit it from its own prompt, the session closes. A running session therefore always means a running agent, and `agents status` shows `session true` for it. The next `agents session NAME AGENT` starts a fresh one.
- **Stop** with `--stop`. It ends the session and with it the agent, like closing the agent's terminal, and prints the session it stopped. `--stop` needs no terminal. It exits zero when no session was running and reports that there is nothing to stop; it also exits zero on an agent that is not enabled. Stopping does not wait for the agent to save anything: detach and quit the agent from its prompt when you want an orderly exit.

Attach from a terminal that supports UTF-8 and 256 colours, as current terminal emulators do. The manager attaches with the tmux options `-u` and `-2`, which make tmux treat your terminal as a UTF-8 terminal with 256 colours whatever `TERM` and locale the terminal inside the sandbox reports. Without them, a `TERM` with eight colours, such as `xterm`, and no UTF-8 locale would make tmux draw the agent's logo, borders, and other non-ASCII characters as underscores and show the agent in eight colours. tmux can show an agent's 24-bit colours as the nearest of the 256. A terminal without UTF-8 or 256 colours shows those characters or colours wrongly.

The two options are automatic: the manager adds them, and `agents session` has no option of its own for them. A confirmed case: attaching OpenCode 1.19.4 without them drew only isolated fragments of its start screen, because tmux saw the client as a non-UTF-8 `xterm` with eight colours; with them the same session drew completely. To compare by hand, run tmux inside the sandbox as `agent`, for example in `shell NAME`, and give the options to tmux as global options before the subcommand, as in `tmux -L sandboxed-agents -f /dev/null -u -2 attach-session -t '=opencode'`; the options belong to tmux itself, not to `attach-session`. The [maintainer evidence](maintainers.md#cause-of-the-fragmented-session-2026-11-03) has the details and its limits.

A session lives in the running sandbox only. `stop NAME`, `restart NAME`, `remove NAME`, and `update NAME` end every session of the sandbox, which is why they refuse while sessions are running and name them unless you pass `--force`. Starting a sandbox again starts no session. The `session` command needs the agent to be enabled; otherwise it names `agents enable NAME AGENT`.

Sessions are not isolated from each other: the agents in a sandbox share its user, files, and credentials, and so do their sessions and runs.

## Sessions and installation changes

A change that would replace or remove the installation of an agent while that agent's session runs is refused, because the session's agent would keep running from a deleted installation. The guard runs under the manager lock, directly before the change, and it looks only at the session of the same agent: a session of another agent never blocks a change.

| Command on an agent with a running session | Without `--force` | With `--force` |
| --- | --- | --- |
| `agents disable` | Refuses, names the running session | Stops the session, names it, and disables |
| `agents update`, with or without `--unpin` | Refuses, names the running session | Stops the session, names it, and updates |
| `agents enable --version X` with `X` different from the installed version | Refuses, names the running session | Stops the session, names it, and installs `X` |
| `agents enable --version X` with the installed version `X` | Records the pin, installs nothing, no guard | The same |
| `agents enable` without `--version` | No-op, no guard | The same no-op |

`--force` here means "stop the session and proceed"; the command names the session it stopped. An `agents enable --force` on an agent that is not enabled, or without a `--version` that differs from the installed version, behaves as without `--force` and is not an error. The session guard and the command-link repair under [Recover from an interrupted change](#recover-from-an-interrupted-change) are independent: `--force` covers both, but a healthy agent with a running session is refused only for the session, and a mismatched command link without a session is refused only for the link.

## Choose agents at creation

```text
sandboxed-agents up agent01 --agents claude,codex
```

`up` enables the listed agents after the sandbox is running, for a new sandbox and for an existing one.

If an agent fails to install, the sandbox keeps running. `up` still attempts the remaining agents, exits non-zero, reports each failure, and names `agents enable NAME AGENT` to retry that agent.

The retry commands that `up` lists are ordinary `agents enable` commands without `--force`. If the failure message for an agent names `--force` because of an interrupted managed installation, run the listed retry with `--force` added, for example `sandboxed-agents agents enable agent01 claude --force`. `up` never adds `--force` itself. See [Recover from an interrupted change](#recover-from-an-interrupted-change).

If the manager does not answer, the sandbox also keeps running and `up` reports no agent as installed. If the manager stopped answering partway through, agents installed earlier in the same request are not rolled back. `up` reports that once, with one diagnosis that names `check NAME` and `restart NAME`, and lists the `agents enable NAME AGENT` command to retry for every agent you listed.

## See the selection

```text
sandboxed-agents list
```

`list` shows each sandbox's agent selection. For a sandbox that is stopped or whose manager does not answer, it shows the selection as unavailable instead of guessing.

## Limits

- `agents login` runs only the workflows the catalog records; it cannot pass options to an agent's login command. The only options it takes, `--url`, `--model`, `--wire-api`, `--remove`, and `--replace-login`, belong to the `proxy` workflows of `claude`, `codex`, `copilot`, and `opencode` and go to the sandbox's own configuration write, never to the agent's login command. Use `agents run NAME AGENT ...` to start any other command of the agent, including other authentication commands, but `agents run` does not guard a running session or take the manager lock.
- Only `claude` has a status probe. `agents status` shows `signed in unknown` for `codex`, `copilot`, and `opencode`, and for `claude` when its command is unavailable, slow, or older than the documented output ([why](agent-status-probes.md)).
- `signed in yes` means that the agent reports configured authentication; it does not show that the token is still valid or that the account can use the agent. After `claude proxy`, it does not show that the server accepts the key either; the documented check is `agents run NAME claude -p ...`. `codex` has no probe, so after `codex proxy` the documented check, `agents run NAME codex exec --skip-git-repo-check ...`, is the only evidence. After `opencode proxy`, `agents status` stays `signed in unknown`, and the documented check is `agents run NAME opencode run ...`; after `copilot proxy` it stays `signed in unknown` too, and the documented check is `agents run NAME copilot -p ... --model cliproxyapi/ID`.
- `claude proxy`, `codex proxy`, `copilot proxy`, and `opencode proxy` store the server key as plaintext in the home volume, readable by every agent in the sandbox, and validate it against nothing. Revoke it on the server to take it out of use. `copilot proxy` makes its model no default and covers inference only; GitHub-hosted features still need `copilot device-code`.
- `codex proxy` replaces a ChatGPT login only with `--replace-login`, and `--remove` does not restore it: Codex keeps one stored login. Sign in again with `browser` or `device-code` afterwards; both refuse while the proxy is configured and name `--remove`. The refusal covers `agents login` only, not a `codex login` run in `shell NAME`, over SSH, or through `agents run`.
- `codex proxy` isolates no network traffic. Only Codex's model requests go to the server; its analytics and feature traffic go where Codex sends them ([Codex proxy notes](codex-proxy.md#what-the-native-contract-test-isolates)).
- `opencode proxy` has been proven against a fake upstream outside a sandbox, and its first use inside a sandbox against a live server has been observed once on each platform ([first use](#opencode-proxy-workflow)): the request completed with the configured provider and model. In OpenCode 1.19.5 the provider package needs no network fetch on first use, read from OpenCode's source and a locally inspected copy of its published build; whether that run reached a registry for anything else, and what it left in the `npm` cache, was not observed, and a later release may require a package fetch and needs the same reading again. The rejected-key and `--remove` checks against a live server are not run ([manual checklist](manual-checklist.md#opencode-proxy-workflow)).
- The Codex configuration lock and the session check see `agents run NAME codex` and `agents session NAME codex` only, and the lock is held by the `agents run` command, not by the Codex it starts. A run marker left by an interrupted run, a Codex ended by `Ctrl+C` or another signal included, holds back the next `codex proxy` change until you clear it by hand; no run is held back by it, and nothing checks whether the process behind a marker still lives. A Codex started in `shell NAME`, over SSH, or by an editor is not seen at all.
- The sandbox publishes no port beyond SSH, so a login that waits for a browser callback inside the sandbox needs a port forward over SSH ([SSH access](ssh.md)).
- Installation changes are not crash-consistent. `--force` repairs a missing or mismatched managed command link as described under [Recover from an interrupted change](#recover-from-an-interrupted-change), but the manager has no complete recovery protocol for interrupted changes. A `codex proxy` write or removal differs in one respect: an interruption leaves a recovery directory that the manager's Codex commands refuse on until you [recover by hand](#recover-from-an-interrupted-codex-proxy-change). It syncs the new contents but not the moves and links that make them current, so a power loss during the change still gives no promise about which files are on disk, and the manager never recovers on its own.
- Sign-ins are checked by hand only: the live suite enables an agent, starts, detaches, and stops its session, but signs in nowhere ([releases](releases.md#live-suite)), and the logins are items of the [manual checklist](manual-checklist.md), which also holds the Claude `signed in` check and the [Claude](manual-checklist.md#claude-proxy-workflow), [Codex](manual-checklist.md#codex-proxy-workflow), and [Copilot](manual-checklist.md#copilot-proxy-workflow) proxy workflow checks, none yet run against a live server; of the [OpenCode checks](manual-checklist.md#opencode-proxy-workflow) only the valid-key run and the first-use observation have been. [Agent status probes](agent-status-probes.md#live-acceptance) records where it has been observed.
