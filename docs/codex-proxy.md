# Codex proxy notes

Maintainer notes for the `proxy` workflow of `codex` ([Agents](agents.md#codex-proxy-workflow), [#145](https://github.com/grauzone-labs/sandboxed-agents/issues/145)). The user-facing behavior lives on the Agents page; this page records the decisions behind it, the evidence each one rests on, and what the offline test does and does not show, so that a later Codex or CLIProxyAPI release can be checked against the same points.

## Key mechanism

The workflow stores the key through Codex's own API-key login, `codex login --with-api-key` with the key on standard input ([Codex authentication](https://learn.chatgpt.com/docs/auth)), and selects the stored login for the provider with `requires_openai_auth = true` in `[model_providers.cliproxyapi]`. The key lands in `auth.json`, the file Codex documents for the `file` credential store, and nowhere else.

The alternatives the story ruled out, and why:

- **An environment variable** (`env_key` on the provider, or `OPENAI_API_KEY` in the environment) would have to be present in every process that starts Codex. `agents run`, `agents session`, `shell NAME`, and an editor over SSH each start Codex differently, and none of them injects environment, so the key would be missing on some path. Codex also ignores `env_key` once `requires_openai_auth` is set.
- **The key in `config.toml`** has no documented field in API-key mode. The only place the guide puts a key into `config.toml` is the `X-Api-Key` header of its ChatGPT login mode, which is the mode below that the workflow does not use. A secret in `config.toml` would also sit beside settings the user edits and shares.
- **The operating-system credential store** (`cli_auth_credentials_store = "keyring"` or `auto`) is not available in a sandbox, which runs no secret service. The workflow passes `-c cli_auth_credentials_store="file"` to the staged login so that the login lands in a file, and refuses a `config.toml` that sets the store to anything other than `file`, because Codex would then look for the login where the workflow did not put it. An unset store is accepted: Codex's default falls back to the file when no store is available.

The staged login runs with `CODEX_HOME` pointed at a temporary directory under the home data, `~/.codex-proxy-` followed by random digits, created with mode `0700` beside `~/.codex` and removed when the workflow returns; a manager killed or a container stopped before that leaves it ([Recovery](#recovery)). That keeps a failed or unexpected login away from the active `auth.json` and lets the workflow inspect the result before publishing it: it accepts only a file whose `OPENAI_API_KEY` is exactly the key and that holds no `tokens`.

## Which CLIProxyAPI mode

The [CLIProxyAPI Codex guide](https://help.router-for.me/agent-client/codex) describes two client setups. The workflow follows the **API mode**: `model_provider = "cliproxyapi"`, a provider table with `base_url`, `wire_api = "responses"`, and `requires_openai_auth = true`, and the key in `auth.json`.

The guide's **OAuth mode**, which it recommends for interactive use, is excluded on purpose. It needs a ChatGPT login to exist, because Codex sends that login's token, and it carries the CLIProxyAPI key as an `X-Api-Key` header in `config.toml`. The story requires that no ChatGPT login is touched silently and that the key is not written into `config.toml` without a documented field, and the mode fails both. It also ties the proxy to an upstream account the sandbox has no business holding.

## The actor header

The guide's API-mode snippet includes `http_headers = { "X-OpenAI-Actor-Authorization" = "local-proxy" }`. The workflow does not write it. The story allowed the header only if CLIProxyAPI's API-key mode is shown to need it, and the evidence says it is a client-side signal, not a server requirement:

- Codex treats `X-OpenAI-Actor-Authorization` as a feature-eligibility signal: with the header present, or with `requires_openai_auth = true`, Codex offers tools such as image generation for the provider. Projects that added the header to a CLIProxyAPI setup did so to get image generation back, not to authenticate ([CLIProxyAPI fork PR #29](https://github.com/Automancer-Ltd/CLIProxyAPI/pull/29), [Paseo v0.9.905 release notes](https://github.com/iamriajul/paseo/releases/tag/v0.9.905)). The header's value is arbitrary, and the [codex-proxy-rs](https://github.com/zyycn/codex-proxy-rs/issues/373) configuration comment says it is not a secret.
- The workflow already sets `requires_openai_auth = true`, which covers the same eligibility gate, so the header would add nothing.
- The native contract test below passed without it: CLIProxyAPI-shaped requests reach `/v1/responses` with the bearer key, and the server authenticates by that key.

Revisit this if a CLIProxyAPI release starts to require the header, which would show up as a rejected request in the manual checks with a key the server accepts.

## The version floor

`codex proxy` refuses Codex older than 0.166.0, on both the host, from the installed version `agents status` reports, and in the manager, from the agent selection. 0.166.0 is the version the native contract test passed against, so it is the oldest version with evidence; older versions are untested, not known to be broken. The flags and settings the workflow depends on, `login --with-api-key`, `cli_auth_credentials_store`, and `requires_openai_auth`, are all documented without a version on the Codex authentication page. Raise the floor only with a reason, and lower it only after the native test has passed against the older version.

## Ownership record

`[_sandboxedAgentsProxy]` in `config.toml` holds `Provider`, a copy of the provider table the workflow wrote; `TokenHash`, the SHA-256 of the key; `ProvidersExisted`, whether `config.toml` already had a `model_providers` table before the first setup; and `PreviousProvider` and `PreviousModel`, the top-level `model_provider` and `model` values the first setup replaced, each omitted when there was none. The key itself appears only in `auth.json`.

The record is what makes `--remove` safe without a second copy of the key: the provider table is compared to `Provider` as a whole, so an edited table is refused rather than deleted; the stored login is deleted only when its `OPENAI_API_KEY` hashes to `TokenHash` and no `tokens` are present; `model_provider` and `model` are restored only while `model_provider` still names `cliproxyapi`; and an emptied `model_providers` table is dropped when `ProvidersExisted` is false, because the workflow created it, and kept when the table was there before. A ChatGPT login that `--replace-login` replaced is not recorded and not restored: Codex keeps one login, and keeping a copy of its tokens would put a second credential into the home data.

## Native login guard

`agents login NAME codex browser` and `agents login NAME codex device-code` refuse while `config.toml` holds the `[_sandboxedAgentsProxy]` table or has `model_provider = "cliproxyapi"`. Either condition alone is enough. The table, because the workflow still owns a provider and a key hash, and a native login over it would leave the ownership record describing a login the workflow did not write; the message names `proxy --remove`, the one deliberate way out, and after it the native workflows behave exactly as before the first setup. A user who changed `model_provider` by hand while the table stayed is still sent to `--remove`. The selection, because a ChatGPT login stored beside it would be sent to the CLIProxyAPI server; when the selection is there without the table, the workflow owns nothing and `--remove` would change nothing, so the message instead asks you to remove the top-level `model_provider` selection from `~/.codex/config.toml` by hand. The guard reads `config.toml` through the same file validation as the workflow, so an unreadable or malformed configuration refuses too; a missing file does not.

The check runs under the manager lock, and the lock is held until Codex's login command exits, including the whole time it waits for the browser or the device code. Checking and then releasing would let `codex proxy` publish while Codex writes its own `auth.json` at the end of the login; holding the lock is what keeps the guard's answer true when the login lands. The cost is that a `codex proxy` command during a login refuses with the retry message, the same message every other change gives.

The guard covers the manager's two commands only. A `codex login` in `shell NAME`, over SSH, or through `agents run` writes `auth.json` without any check, as it always did; the sandbox puts no new permission or guard in the way of the `agent` user's own files, and a Codex that was already running keeps whatever it loaded.

## Codex configuration lock

A managed run reads `config.toml` and `auth.json` when Codex starts, and a review of the publication order found that `agents run NAME codex` could pass the recovery check and then start Codex in the middle of a proxy change, with the login of one version beside the destination of another. The manager lock was the wrong tool: it is exclusive, and holding it for a run would hold back every agent and Tool change for as long as Codex runs. `lockCodexConfiguration` in `internal/manager/codex_lock_linux.go` adds a second lock, `codex.lock` beside `manager.lock` under `~/.local/share/sandboxed-agents/`, a `flock` taken without waiting: shared by `agents run NAME codex`, from before its recovery check until the command returns, and exclusive by the proxy workflow, after the manager lock and from before the staged login until the change is complete or restored. Runs admit each other and nothing else takes the lock, so unrelated agents and Tools stay available; a run and a change refuse each other, the run with `Codex proxy change is in progress; retry`, the change with `Codex is running; wait for managed runs to finish before changing the proxy`. Closing every copy of the descriptor releases the lock, and the cooperating manager commands keep a stable lock path and never unlink or repair it; the open refuses a final-component symlink, existing or dangling, and any non-regular file, without following it, with `cannot open Codex configuration lock` or `Codex configuration lock must be a regular file`. A raw filesystem writer under the same identity can still replace the path or an ancestor directory and leave two callers on different inodes, which defeats the coordination; that is outside the guarantee, which makes no adversarial or universal atomicity promise.

A Codex session runs under the manager's tmux server after the start command has returned, so no manager process can hold a descriptor for it. The workflow reads the session list under the manager lock instead, which session starts and stops take as well, and refuses while a `codex` session exists, before it reads a key, with `Codex session is running; run agents session NAME codex --stop before changing the proxy`. A session start rechecks the recovery directory under the lock after its unlocked session query, so a change that leaves the directory between the query and the lock is still seen. The native `browser` and `device-code` logins keep their whole-login manager lock and take no Codex configuration lock; the [guard above](#native-login-guard) is unchanged.

The lock and the session check see the manager's own run and session commands. A Codex started in `shell NAME`, over SSH, or by an editor is not seen, and the lock belongs to the `agents run` command, not to the Codex it starts: the command's descriptor is the lock, and a Codex that outlives its manager holds nothing.

### Run markers

`recordCodexRun` in `internal/manager/codex_runs.go` therefore records each admission as a run marker: an empty file, mode `0600`, named `run-` plus random digits, in `~/.local/share/sandboxed-agents/codex-runs/`, mode `0700`, both subject to the process umask, created under the shared lock after the recovery check and before Codex starts. When the directory cannot be made, is not a directory, or the file cannot be created, the run refuses with `interrupted managed Codex run requires recovery; see docs/codex-proxy.md` and starts nothing. The command removes its own marker, still under the lock, only after a completion it can vouch for: Codex exited on its own, with status zero or any other status. A Codex ended by a signal, a start that failed, an unknown error, and a manager that was killed, panicked, or ended on `Ctrl+C` all leave the marker, and the command prints the recovery message when it is still there to print. There is no deferred removal; a marker that outlives its command is the point. The proxy workflow, once it holds the exclusive lock and before it reads a key or checks the recovery directory, refuses with the same message when the directory holds any entry, cannot be read, or is not a directory. A marker holds no credential, no process ID, and no time: it records that a run was admitted, not that a Codex lives, and nothing infers liveness or age from it, so the manager never removes a marker it did not make in the same process. The signal handling of `agents run` is unchanged, and the cost is accepted: an interrupted run may cost a manual marker clear before the next proxy change, while no run is ever held back by a marker, because a run reads a configuration that the exclusion keeps consistent.

## Publication order and the recovery directory

The first implementation published `config.toml` and then `auth.json` by rename over each target and renamed the previous `config.toml` back when the second rename failed. The review of that implementation found two gaps. A rename replaces whatever is at the target, so an edit made to either file while the staged login ran was overwritten. And an interruption between the two renames left the previous key active in `auth.json` beside a `config.toml` that already pointed at the new server, so the next Codex start would have sent the old key to the new destination. `publishCodexFiles` in `internal/manager/codex_publication.go` replaces that write with this order:

1. **Refuse or claim the directory.** Refuse when `~/.codex/.sandboxed-agents-proxy/` already exists, as a file, a directory, or a dangling symbolic link; refuse when `config.toml` or `auth.json` differs from what the workflow read before the staged login; then create the directory with mode `0700`. Its existence is the marker: it is created before any active file changes, removed only after the change has completed or been fully restored, and removed by no `defer`, so an interruption leaves it.
2. **Stage the new contents.** Each new content goes to a private `.publish-` candidate inside the directory, written and synced with `fsync`. A login that does not change, as in a `--remove` that leaves a login the workflow does not own, gets no candidate; a login to delete gets none either.
3. **Move the previous files out, the login first.** Check both active files once more, then move `auth.json` and after it `config.toml` into the directory as `auth.json.prev` and `config.toml.prev`, and verify that each moved file holds the bytes that were read. The login moves first so that no state exists in which the old key sits beside a new destination. A move is a rename of the inode: bytes, mode, and ownership stay, and on this path the moved old credential is never duplicated; when it has to come back, the same inode is linked, not copied. The mode of each moved file is recorded here for the cleanup restoration in step 5, the one path that writes the previous bytes again. The new key is the one credential that exists twice for a moment, in the staged login's `auth.json` and in the candidate, both private and both removed by the end.
4. **Publish without clobbering.** Link `config.toml` and then `auth.json` from their candidates, or an unchanged login from its moved file, with `link`, which fails when the name exists. A file that something else created at the name since step 3 therefore makes the step fail and is preserved, at the active name or, when the rollback moves it aside, in a `.failed-` subdirectory of the recovery directory, while the previous version is still in the directory.
5. **Verify and clean up.** Verify both active files against the intended contents, remove the candidates and the `.prev` files after checking each still holds what it should, and remove the directory. The cleanup records which `.prev` file it has removed. When a removal returns an error, the workflow writes each removed previous version again, from the bytes read in step 1, into a `.publish-` candidate with the recorded mode, links it to its `.prev` name without clobbering, and then runs the rollback below, which quarantines the published files and restores both previous files, so that `config.toml` and `auth.json` end with their original bytes and modes, or absent where they were absent, after a setup and after a `--remove` alike, with `cannot finish Codex publication; previous configuration and login restored`. A check before a removal that finds a file changed, or a rewrite that fails, including one that finds a file something else put at the `.prev` name in the meantime, which is preserved, returns the recovery message and leaves the directory. The record of what the cleanup removed lives in the process only, so an interruption during the cleanup leaves the new pair active and matching, the marker in place, and a removed previous version gone; nothing infers that afterwards.

A step that returns an error rolls back. Each file found at an active name whose previous file the workflow had moved out, or at which it had published, is moved into a fresh `.failed-` subdirectory of the recovery directory as `auth.json.failed` or `config.toml.failed`, the login first, so that an interrupted rollback cannot pair a login with a restored destination either. An original the workflow had not yet moved out stays at its active name and is only verified against the bytes that were read. When every such file is one the workflow published itself, the `.prev` files are linked back to the active names, again without clobbering, the quarantined files are removed after verification, the directory goes away, and the message says what was restored: `previous configuration and login unchanged` when nothing had been published, `previous configuration restored` when the login could not be. When a file at an active name is not one the workflow wrote, when a restoration fails, or when a moved file is not what was read, the function returns the recovery message and leaves the directory with everything it holds: the `.prev` files, any candidate, and any `.failed-` subdirectory. Nothing is discarded and nothing is overwritten, which is why the directory, not the workflow, is where a human looks.

What this covers: an interrupted manager process at any point, including a panic and a container stop, the races the function checks, an edit during staging, a changed file at the move, a new file at the link, and a changed file at the final verification, a removal that fails during cleanup, and a managed run that would start Codex during the change, which the [Codex configuration lock](#codex-configuration-lock) refuses. What it does not cover: the candidates are synced, but the renames and links are not and no directory entry is synced, so after a power loss or kernel crash the names may or may not have reached disk and the two files have no durable joint commit; a process holding either file open writes through its descriptor; a writer that does not go through the manager is detected only when it races one of the checks; a Codex already running has loaded what it loaded. The pair is a bounded transaction against the manager's own interruptions and the races it checks, not a filesystem compare-and-swap and not a durability protocol. Documentation must not call it atomic without that bound. The manager lock serializes the manager's own writers, the native login included ([above](#native-login-guard)); the directory catches what the lock cannot.

## Recovery

While `~/.codex/.sandboxed-agents-proxy/` exists, the manager refuses `agents run`, starting or attaching a session, and every `login` workflow of Codex, `proxy --remove` included, with `Codex publication requires recovery; see docs/codex-proxy.md for ~/.codex/.sandboxed-agents-proxy`. `agents session NAME codex --stop`, `status`, `enable`, `update`, and `disable` stay available, so a running Codex can be ended first. The manager never recovers on its own. Inferring the right version from the directory's contents was considered and rejected: the phase the change reached is not recorded, a `.failed` file may be the user's own, and choosing which login to make active chooses where a key goes. The conservative reset below is the supported recovery. It preserves the files that remain, prints no key, and makes the provider choice an explicit login again. It does not preserve every version in every case: a cleanup interrupted after it had removed a previous version leaves that version gone, with the new pair active.

The directory may hold `config.toml.prev` and `auth.json.prev`, the files as they were before the change with their original bytes and modes; `.publish-` candidates with the new configuration and, when the login changed, the new key; and `.failed-` subdirectories with files moved out of the active names. `config.toml` and `auth.json` beside it may each be the new version, missing, or something else wrote. Any of these files may hold a key, and none of them is a file Codex should read next, because the change they belong to did not complete.

1. **Stop every Codex in the sandbox.** `agents session NAME codex --stop` ends the manager's session. A foreground `agents run NAME codex` is ended at the terminal that runs it: the manager tracks it through its lock and run marker but cannot stop it for you. A Codex started in `shell NAME`, over SSH, or by an editor, and one left behind by an interrupted run, is yours to end: the manager does not see it, and a Codex that keeps running keeps its open files and its loaded settings. Continue only when none runs.
2. **Quarantine the whole Codex directory without overwriting anything.** In `shell NAME`, as `agent`, create a private directory with a unique name under the home directory, on the same filesystem, and move `~/.codex` into it. A fixed name could collide with an earlier quarantine and a copy would duplicate the key, so use `mktemp -d` and `mv`:

   ```sh
   archive=$(mktemp -d "$HOME/codex-quarantine.XXXXXX") && mv "$HOME/.codex" "$archive/codex" && echo "$archive"
   ```

   The command prints the archive's path. Everything Codex kept, settings, history, the stored login, and every file of the recovery directory, is now in the archive, unchanged, with mode `0700` on the archive and readable by `agent` only. Nothing is deleted and no key is revoked by this step.
3. **Recreate an empty Codex directory** with `mkdir -m 0700 "$HOME/.codex"`. Codex and the sandbox now see a fresh directory with no login and no proxy, and there is nothing to `--remove`. The quarantine clears no run marker: when `~/.local/share/sandboxed-agents/codex-runs/` still holds an entry, the proxy workflow keeps refusing with `interrupted managed Codex run requires recovery`, so follow [Interrupted managed runs](#interrupted-managed-runs) before you sign in to the proxy again; nothing clears it for you.
4. **Sign in again, on purpose, to the provider you want.** Decide whether this sandbox should use a CLIProxyAPI server or an OpenAI account. For the server, run `agents login NAME codex proxy --url URL --model ID` and paste a key you know to be valid; for the account, run `agents login NAME codex browser` or `device-code`. Do not copy `auth.json`, `auth.json.prev`, a candidate, or the whole `config.toml` back from the archive: an `auth.json` holds the login for one destination, and a login beside a configuration it does not belong to is the state the change was preventing, so the key could go to a server it was not meant for. Copy back only settings you have read and found unrelated to the provider: no `model_provider`, `model_providers`, `cli_auth_credentials_store`, or other authentication setting, and no `[profiles.*]` table, because a profile can carry its own `model_provider` and `base_url` and would reroute the login you just made. `history.jsonl` holds no settings and can be copied on its own.
5. **Decide the archive's fate yourself.** It may hold the previous key, the new key, or both, in plaintext, readable by every agent in the sandbox. Delete it once you have what you need. When you cannot say where a key was sent, or whether a Codex sent it while the change was incomplete, revoke that key on the server; the manager never deletes an archive and never revokes a key.
6. **Delete retained staged login directories yourself.** The staged login runs in `~/.codex-proxy-` followed by random digits, beside `~/.codex` and not inside it ([Key mechanism](#key-mechanism)), so step 2 does not move it into the archive. The workflow removes it when it returns; a manager killed or a container stopped at any point from the staged login to the end of publication leaves it, with the pasted key in its `auth.json` once the login had completed. First make sure that no Codex and no proxy login runs, by the process list, not by the host: an `agents login NAME codex proxy` command that has returned on your host does not prove that its staged login has ended, because a manager killed before its child leaves that child running. Codex is installed from npm, so a running Codex may appear as a `node` process running the package's `codex.js` wrapper, as the native `codex-…` program, or as both; inspect both forms, and expect a staged login to be one of them running `login --with-api-key`. `pgrep` is best effort: it finds what names itself, and proves no absence against a process that does not. In `shell NAME`:

   ```sh
   pgrep -f -- '[c]odex'
   ```

   prints the ID of every process whose command line mentions `codex`, one per line and nothing else, and prints nothing with exit status 1 when there is none; the bracket keeps the pattern from matching a shell that carries the pattern on its own command line. This is a best-effort check of the process list, not a guarantee against another writer running as the same user: coordinate with anyone else who runs commands in the sandbox. For a listed ID, `ps -o pid,user,etimes,comm -p ID` shows the program name and age without arguments or environment. End every Codex of your own as in step 1, let a login that is still finishing finish, and continue only when `pgrep` prints nothing. Then list the entries without their contents:

   ```sh
   ls -ld "$HOME"/.codex-proxy-*
   ```

   `-d` lists the entries themselves, one line each with mode, owner, time, and path, and no file inside them; without a match, `ls` reports that no such file exists. A retained staged login is a directory, mode `drwx------`, owned by `agent`. An entry that starts with `l` is a symbolic link something else placed under that name, not a staged login; leave it alone. Delete each directory you have identified, one at a time, by the exact path the listing printed, with no pattern and no trailing slash:

   ```sh
   rm -r -- "$HOME/.codex-proxy-1234567890"
   ```

   `rm -r` on a named path removes that directory and what it holds, and removes a symbolic link it meets as a link, without following it. Which directories go is your decision; the manager deletes none of them after the fact.

Never print `auth.json`, `auth.json.prev`, a `.publish-` candidate, a `.failed` file, or the `auth.json` of a staged login directory, in a terminal, a log, or a report: a key is in them. `ls -laR "$archive/codex"` shows what is there without showing contents.

### Interrupted managed runs

`interrupted managed Codex run requires recovery; see docs/codex-proxy.md` from a `codex proxy` command means that `~/.local/share/sandboxed-agents/codex-runs/` holds an entry or cannot be read ([Run markers](#run-markers)). The workflow refused before reading a key and changed nothing; no recovery directory is involved, and the quarantine in step 2 above does not clear the markers. A `restart` of the sandbox ends every process in it but keeps the markers, and the restarted sandbox may have started processes of its own, so confirm the processes after any restart, not before it.

1. **Stop every Codex in the sandbox**, as in step 1 above, the native `codex-…` program and its `node` wrapper included, and make sure that no `agents run NAME codex` and no `agents login NAME codex proxy` is in progress. In `shell NAME`, `pgrep -f -- '[c]odex'` prints nothing and exits 1 when no process with `codex` on its command line is left; the check is best effort, as in step 6 above. Continue only then.
2. **List the markers.** They have no contents, so a listing shows everything there is:

   ```sh
   ls -la "$HOME/.local/share/sandboxed-agents/codex-runs"
   ```

   A marker the manager wrote is an empty regular file, `-rw-------`, owned by `agent`, named `run-` and digits. Any other entry, a file with contents, another name, a directory, or a symbolic link, is not the manager's: the workflow refuses while it exists, and the manager never removes it or guesses what it is. Decide yourself what it is before you touch it.
3. **Delete the markers by exact name**, one at a time, with no wildcard and no `-r`:

   ```sh
   rm -- "$HOME/.local/share/sandboxed-agents/codex-runs/run-1234567890"
   ```

   Leave `codex.lock` in the parent directory alone, now and always: a lock taken on a replaced name protects nothing. The next `codex proxy` command then runs; nothing in a marker said whether the run it recorded still had a process, which is why the process list came first.

## TOML round trip

The workflow decodes `config.toml` into a map and encodes it again. Values, tables, and profiles survive; comments, key order, and formatting do not. The Agents page tells users so. A format-preserving edit would need a different TOML library and was not worth it for a file Codex itself rewrites.

## What the native contract test isolates

`TestCodexProxyNativeClient` in `internal/manager/codex_proxy_test.go` runs only with `SANDBOXED_AGENTS_TEST_CODEX` set to a Codex executable. It has passed against Codex 0.166.0: setup with `--replace-login` over a stored ChatGPT login, a `codex exec` that sent a POST to `/prefix/v1/responses` with `Authorization: Bearer` and the configured model to the fake upstream only, and a `--remove` that restored the original `model`, kept an unrelated profile, and deleted the owned `auth.json`.

The test isolates Codex in two ways that the workflow does not:

- It routes all of Codex's traffic to the fake upstream with `HTTP_PROXY`, `HTTPS_PROXY`, and `ALL_PROXY`, so any request to another host is refused there instead of leaving the machine. That is how the test can assert that no request reached `api.openai.com` or `chatgpt.com`.
- Its own `codex exec` passes `-c analytics.enabled=false`, `-c features.plugins=false`, `-c features.apps=false`, `-c features.api_key_model_discovery=false`, and `-c features.api_key_cyber_access_programs=false`. Without them, a first run of the test saw Codex 0.166.0 attempt startup traffic to GitHub, `chatgpt.com`, and `ab.chatgpt.com`, unrelated to the model request, which the proxy refused and which made the run fail.

The workflow writes none of those settings and enforces no network isolation. In a sandbox, Codex keeps the user's analytics and feature settings, and whatever ancillary traffic those settings cause continues to go where Codex sends it; only the model requests go to the CLIProxyAPI server. The test shows that the model request path is routed and authenticated as documented, nothing more. The [manual checklist](manual-checklist.md#codex-proxy-workflow) holds the live checks against a real server, not yet run.
