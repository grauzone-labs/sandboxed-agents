# Codex proxy notes

Maintainer notes for the `proxy` workflow of `codex` ([Agents](agents.md#codex-proxy-workflow), [#145](https://github.com/grauzone-labs/sandboxed-agents/issues/145)). The user-facing behavior lives on the Agents page; this page records the decisions behind it, the evidence each one rests on, and what the offline test does and does not show, so that a later Codex or CLIProxyAPI release can be checked against the same points.

## Key mechanism

The workflow stores the key through Codex's own API-key login, `codex login --with-api-key` with the key on standard input ([Codex authentication](https://learn.chatgpt.com/docs/auth)), and selects the stored login for the provider with `requires_openai_auth = true` in `[model_providers.cliproxyapi]`. The key lands in `auth.json`, the file Codex documents for the `file` credential store, and nowhere else.

The alternatives the story ruled out, and why:

- **An environment variable** (`env_key` on the provider, or `OPENAI_API_KEY` in the environment) would have to be present in every process that starts Codex. `agents run`, `agents session`, `shell NAME`, and an editor over SSH each start Codex differently, and none of them injects environment, so the key would be missing on some path. Codex also ignores `env_key` once `requires_openai_auth` is set.
- **The key in `config.toml`** has no documented field in API-key mode. The only place the guide puts a key into `config.toml` is the `X-Api-Key` header of its ChatGPT login mode, which is the mode below that the workflow does not use. A secret in `config.toml` would also sit beside settings the user edits and shares.
- **The operating-system credential store** (`cli_auth_credentials_store = "keyring"` or `auto`) is not available in a sandbox, which runs no secret service. The workflow passes `-c cli_auth_credentials_store="file"` to the staged login so that the login lands in a file, and refuses a `config.toml` that sets the store to anything other than `file`, because Codex would then look for the login where the workflow did not put it. An unset store is accepted: Codex's default falls back to the file when no store is available.

The staged login runs with `CODEX_HOME` pointed at a temporary directory under the home data. That keeps a failed or unexpected login away from the active `auth.json` and lets the workflow inspect the result before publishing it: it accepts only a file whose `OPENAI_API_KEY` is exactly the key and that holds no `tokens`.

## Which CLIProxyAPI mode

The [CLIProxyAPI Codex guide](https://help.router-for.me/agent-client/codex) describes two client setups. The workflow follows the **API mode**: `model_provider = "cliproxyapi"`, a provider table with `base_url`, `wire_api = "responses"`, and `requires_openai_auth = true`, and the key in `auth.json`.

The guide's **OAuth mode**, which it recommends for interactive use, is excluded on purpose. It needs a ChatGPT login to exist, because Codex sends that login's token, and it carries the CLIProxyAPI key as an `X-Api-Key` header in `config.toml`. The story requires that no ChatGPT login is touched silently and that the key is not written into `config.toml` without a documented field, and the mode fails both. It also ties the proxy to an upstream account the sandbox has no business holding.

## The actor header

The guide's API-mode snippet includes `http_headers = { "X-OpenAI-Actor-Authorization" = "local-proxy" }`. The workflow does not write it. The story allowed the header only if CLIProxyAPI's API-key mode is shown to need it, and the evidence says it is a client-side signal, not a server requirement:

- Codex treats `X-OpenAI-Actor-Authorization` as a feature-eligibility signal: with the header present, or with `requires_openai_auth = true`, Codex offers tools such as image generation for the provider. Projects that added the header to a CLIProxyAPI setup did so to get image generation back, not to authenticate ([CLIProxyAPI fork PR #29](https://github.com/Automancer-Ltd/CLIProxyAPI/pull/29), [Paseo v0.9.905 release notes](https://github.com/iamriajul/paseo/releases/tag/v0.9.905)). The header's value is arbitrary, and the [codex-proxy-rs](https://github.com/zyycn/codex-proxy-rs/issues/373) configuration comment says it is not a secret.
- The workflow already sets `requires_openai_auth = true`, which covers the same eligibility gate, so the header would add nothing.
- The native contract test below passed without it: CLIProxyAPI-shaped requests reach `/v1/responses` with the bearer key, and the server authenticates by that key.

Revisit this if a CLIProxyAPI release starts to require the header, which would show up as a rejected request in the manual checks with a key the server accepts.

## The version floor

`codex proxy` refuses Codex older than 0.166.0, on both the host, from the installed version `agents status` reports, and in the manager, from the agent selection. 0.166.0 is the version the native contract test passed against, so it is the oldest version with evidence; older versions are untested, not known to be broken. The flags and settings the workflow depends on, `login --with-api-key`, `cli_auth_credentials_store`, and `requires_openai_auth`, are all documented without a version on the Codex authentication page. Raise the floor only with a reason, and lower it only after the native test has passed against the older version.

## Ownership record

`[_sandboxedAgentsProxy]` in `config.toml` holds `Provider`, a copy of the provider table the workflow wrote; `TokenHash`, the SHA-256 of the key; `ProvidersExisted`, whether `config.toml` already had a `model_providers` table before the first setup; and `PreviousProvider` and `PreviousModel`, the top-level `model_provider` and `model` values the first setup replaced, each omitted when there was none. The key itself appears only in `auth.json`.

The record is what makes `--remove` safe without a second copy of the key: the provider table is compared to `Provider` as a whole, so an edited table is refused rather than deleted; the stored login is deleted only when its `OPENAI_API_KEY` hashes to `TokenHash` and no `tokens` are present; `model_provider` and `model` are restored only while `model_provider` still names `cliproxyapi`; and an emptied `model_providers` table is dropped when `ProvidersExisted` is false, because the workflow created it, and kept when the table was there before. A ChatGPT login that `--replace-login` replaced is not recorded and not restored: Codex keeps one login, and keeping a copy of its tokens would put a second credential into the home data.

## Native login guard

`agents login NAME codex browser` and `agents login NAME codex device-code` refuse while `config.toml` holds the `[_sandboxedAgentsProxy]` table or has `model_provider = "cliproxyapi"`. Either condition alone is enough. The table, because the workflow still owns a provider and a key hash, and a native login over it would leave the ownership record describing a login the workflow did not write; the message names `proxy --remove`, the one deliberate way out, and after it the native workflows behave exactly as before the first setup. A user who changed `model_provider` by hand while the table stayed is still sent to `--remove`. The selection, because a ChatGPT login stored beside it would be sent to the CLIProxyAPI server; when the selection is there without the table, the workflow owns nothing and `--remove` would change nothing, so the message instead asks you to remove the top-level `model_provider` selection from `~/.codex/config.toml` by hand. The guard reads `config.toml` through the same file validation as the workflow, so an unreadable or malformed configuration refuses too; a missing file does not.

The check runs under the manager lock, and the lock is held until Codex's login command exits, including the whole time it waits for the browser or the device code. Checking and then releasing would let `codex proxy` publish while Codex writes its own `auth.json` at the end of the login; holding the lock is what keeps the guard's answer true when the login lands. The cost is that a `codex proxy` command during a login refuses with the retry message, the same message every other change gives.

The guard covers the manager's two commands only. A `codex login` in `shell NAME`, over SSH, or through `agents run` writes `auth.json` without any check, as it always did; the sandbox puts no new permission or guard in the way of the `agent` user's own files, and a Codex that was already running keeps whatever it loaded.

## Publication order and the recovery directory

The first implementation published `config.toml` and then `auth.json` by rename over each target and renamed the previous `config.toml` back when the second rename failed. The review of that implementation found two gaps. A rename replaces whatever is at the target, so an edit made to either file while the staged login ran was overwritten. And an interruption between the two renames left the previous key active in `auth.json` beside a `config.toml` that already pointed at the new server, so the next Codex start would have sent the old key to the new destination. `publishCodexFiles` in `internal/manager/codex_publication.go` replaces that write with this order:

1. **Refuse or claim the directory.** Refuse when `~/.codex/.sandboxed-agents-proxy/` already exists, as a file, a directory, or a dangling symbolic link; refuse when `config.toml` or `auth.json` differs from what the workflow read before the staged login; then create the directory with mode `0700`. Its existence is the marker: it is created before any active file changes, removed only after the change has completed or been fully restored, and removed by no `defer`, so an interruption leaves it.
2. **Stage the new contents.** Each new content goes to a private `.publish-` candidate inside the directory, written and synced with `fsync`. A login that does not change, as in a `--remove` that leaves a login the workflow does not own, gets no candidate; a login to delete gets none either.
3. **Move the previous files out, the login first.** Check both active files once more, then move `auth.json` and after it `config.toml` into the directory as `auth.json.prev` and `config.toml.prev`, and verify that each moved file holds the bytes that were read. The login moves first so that no state exists in which the old key sits beside a new destination. A move is a rename of the inode: bytes, mode, and ownership stay, and the moved old credential is never duplicated; when it has to come back, the same inode is linked, not copied. The new key is the one credential that exists twice for a moment, in the staged login's `auth.json` and in the candidate, both private and both removed by the end.
4. **Publish without clobbering.** Link `config.toml` and then `auth.json` from their candidates, or an unchanged login from its moved file, with `link`, which fails when the name exists. A file that something else created at the name since step 3 therefore makes the step fail and is preserved, at the active name or, when the rollback moves it aside, in a `.failed-` subdirectory of the recovery directory, while the previous version is still in the directory.
5. **Verify and clean up.** Verify both active files against the intended contents, remove the candidates and the `.prev` files after checking each still holds what it should, and remove the directory.

A step that returns an error rolls back. Each file found at an active name whose previous file the workflow had moved out, or at which it had published, is moved into a fresh `.failed-` subdirectory of the recovery directory as `auth.json.failed` or `config.toml.failed`, the login first, so that an interrupted rollback cannot pair a login with a restored destination either. An original the workflow had not yet moved out stays at its active name and is only verified against the bytes that were read. When every such file is one the workflow published itself, the `.prev` files are linked back to the active names, again without clobbering, the quarantined files are removed after verification, the directory goes away, and the message says what was restored: `previous configuration and login unchanged` when nothing had been published, `previous configuration restored` when the login could not be. When a file at an active name is not one the workflow wrote, when a restoration fails, or when a moved file is not what was read, the function returns the recovery message and leaves the directory with everything it holds: the `.prev` files, any candidate, and any `.failed-` subdirectory. Nothing is discarded and nothing is overwritten, which is why the directory, not the workflow, is where a human looks.

What this covers: an interrupted manager process at any point, including a panic and a container stop, and the races the function checks, an edit during staging, a changed file at the move, a new file at the link, and a changed file at the final verification. What it does not cover: the candidates are synced, but the renames and links are not and no directory entry is synced, so after a power loss or kernel crash the names may or may not have reached disk and the two files have no durable joint commit; a process holding either file open writes through its descriptor; a writer that does not go through the manager is detected only when it races one of the checks; a Codex already running has loaded what it loaded. The pair is a bounded transaction against the manager's own interruptions and the races it checks, not a filesystem compare-and-swap and not a durability protocol. Documentation must not call it atomic without that bound. The manager lock serializes the manager's own writers, the native login included ([above](#native-login-guard)); the directory catches what the lock cannot.

## Recovery

While `~/.codex/.sandboxed-agents-proxy/` exists, the manager refuses `agents run`, starting or attaching a session, and every `login` workflow of Codex, `proxy --remove` included, with `Codex publication requires recovery; see docs/codex-proxy.md for ~/.codex/.sandboxed-agents-proxy`. `agents session NAME codex --stop`, `status`, `enable`, `update`, and `disable` stay available, so a running Codex can be ended first. The manager never recovers on its own. Inferring the right version from the directory's contents was considered and rejected: the phase the change reached is not recorded, a `.failed` file may be the user's own, and choosing which login to make active chooses where a key goes. The conservative reset below is the supported recovery. It keeps every version readable, prints no key, and makes the provider choice an explicit login again.

The directory may hold `config.toml.prev` and `auth.json.prev`, the files as they were before the change with their original bytes and modes; `.publish-` candidates with the new configuration and, when the login changed, the new key; and `.failed-` subdirectories with files moved out of the active names. `config.toml` and `auth.json` beside it may each be the new version, missing, or something else wrote. Any of these files may hold a key, and none of them is a file Codex should read next, because the change they belong to did not complete.

1. **Stop every Codex in the sandbox.** `agents session NAME codex --stop` ends the manager's session. A Codex started in `shell NAME`, over SSH, through `agents run`, or by an editor is yours to end: the manager does not see it, and a Codex that keeps running keeps its open files and its loaded settings. Continue only when none runs.
2. **Quarantine the whole Codex directory without overwriting anything.** In `shell NAME`, as `agent`, create a private directory with a unique name under the home directory, on the same filesystem, and move `~/.codex` into it. A fixed name could collide with an earlier quarantine and a copy would duplicate the key, so use `mktemp -d` and `mv`:

   ```sh
   archive=$(mktemp -d "$HOME/codex-quarantine.XXXXXX") && mv "$HOME/.codex" "$archive/codex" && echo "$archive"
   ```

   The command prints the archive's path. Everything Codex kept, settings, history, the stored login, and every file of the recovery directory, is now in the archive, unchanged, with mode `0700` on the archive and readable by `agent` only. Nothing is deleted and no key is revoked by this step.
3. **Recreate an empty Codex directory** with `mkdir -m 0700 "$HOME/.codex"`. Codex and the sandbox now see a fresh directory with no login and no proxy, the manager's Codex commands work again, and there is nothing to `--remove`.
4. **Sign in again, on purpose, to the provider you want.** Decide whether this sandbox should use a CLIProxyAPI server or an OpenAI account. For the server, run `agents login NAME codex proxy --url URL --model ID` and paste a key you know to be valid; for the account, run `agents login NAME codex browser` or `device-code`. Do not copy `auth.json`, `auth.json.prev`, a candidate, or the whole `config.toml` back from the archive: an `auth.json` holds the login for one destination, and a login beside a configuration it does not belong to is the state the change was preventing, so the key could go to a server it was not meant for. Copy back only settings you have read and found unrelated to the provider: no `model_provider`, `model_providers`, `cli_auth_credentials_store`, or other authentication setting, and no `[profiles.*]` table, because a profile can carry its own `model_provider` and `base_url` and would reroute the login you just made. `history.jsonl` holds no settings and can be copied on its own.
5. **Decide the archive's fate yourself.** It still holds the previous key, and possibly the new one, in plaintext, readable by every agent in the sandbox. Delete it once you have what you need. When you cannot say where a key was sent, or whether a Codex sent it while the change was incomplete, revoke that key on the server; the manager never deletes an archive and never revokes a key.

Never print `auth.json`, `auth.json.prev`, a `.publish-` candidate, or a `.failed` file, in a terminal, a log, or a report: a key is in them. `ls -laR "$archive/codex"` shows what is there without showing contents.

## TOML round trip

The workflow decodes `config.toml` into a map and encodes it again. Values, tables, and profiles survive; comments, key order, and formatting do not. The Agents page tells users so. A format-preserving edit would need a different TOML library and was not worth it for a file Codex itself rewrites.

## What the native contract test isolates

`TestCodexProxyNativeClient` in `internal/manager/codex_proxy_test.go` runs only with `SANDBOXED_AGENTS_TEST_CODEX` set to a Codex executable. It has passed against Codex 0.166.0: setup with `--replace-login` over a stored ChatGPT login, a `codex exec` that sent a POST to `/prefix/v1/responses` with `Authorization: Bearer` and the configured model to the fake upstream only, and a `--remove` that restored the original `model`, kept an unrelated profile, and deleted the owned `auth.json`.

The test isolates Codex in two ways that the workflow does not:

- It routes all of Codex's traffic to the fake upstream with `HTTP_PROXY`, `HTTPS_PROXY`, and `ALL_PROXY`, so any request to another host is refused there instead of leaving the machine. That is how the test can assert that no request reached `api.openai.com` or `chatgpt.com`.
- Its own `codex exec` passes `-c analytics.enabled=false`, `-c features.plugins=false`, `-c features.apps=false`, `-c features.api_key_model_discovery=false`, and `-c features.api_key_cyber_access_programs=false`. Without them, a first run of the test saw Codex 0.166.0 attempt startup traffic to GitHub, `chatgpt.com`, and `ab.chatgpt.com`, unrelated to the model request, which the proxy refused and which made the run fail.

The workflow writes none of those settings and enforces no network isolation. In a sandbox, Codex keeps the user's analytics and feature settings, and whatever ancillary traffic those settings cause continues to go where Codex sends it; only the model requests go to the CLIProxyAPI server. The test shows that the model request path is routed and authenticated as documented, nothing more. The [manual checklist](manual-checklist.md#codex-proxy-workflow) holds the live checks against a real server, not yet run.

The guard and the publication order are covered by focused tests in the same file that need no Codex executable and inject failures through the `RenameFile` and `LinkFile` effects: `TestCodexProxyGuardsNativeLogin` and `TestCodexNativeLoginHoldsManagerLock` for the [native login guard](#native-login-guard); `TestCodexProxyPreservesEditsDuringLogin`, `TestCodexProxyPublicationRollback`, `TestCodexProxyPublicationPreservesRacingEdits`, `TestCodexProxyInterruptedPublicationFailsClosed`, `TestCodexProxyInterruptedUpdateAndRemovalKeepCredentialsInactive`, `TestCodexProxyFirstPublicationFailureRestoresAbsence`, and `TestCodexProxyCaptureAndAuthInterruptionsRetainRecovery` for the [publication order](#publication-order-and-the-recovery-directory) and the refusals while the recovery directory exists. They interrupt with a panic and race with direct writes, which is the bound the order claims; none of them simulates a power loss, and the [recovery](#recovery) steps are a human procedure that no test and no host run exercises.
