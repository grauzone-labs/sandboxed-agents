# Tools run as manager-supervised services as `agent`

The first version ships one Tool, T3 Code (Story [#89](https://github.com/grauzone-labs/sandboxed-agents/issues/89), Feature [#99](https://github.com/grauzone-labs/sandboxed-agents/issues/99)). A Tool is installed into a sandbox's home data after the sandbox exists, with the same npm install method as an agent, and its background service is kept running by a service supervisor that the manager starts as `agent`. Nothing about the sandbox's containment changes: no published port beyond SSH, no bind, device, capability, or network-mode change, no host software, and no init system in the image. Everything a Tool stores lives in one Tool directory in the home data, `~/.local/share/sandboxed-agents/tools/TOOL`, and `tools delete` removes that directory completely after it has relocated the user project files found inside.

This decision narrows two non-goals of Epic [#1](https://github.com/grauzone-labs/sandboxed-agents/issues/1) on purpose, so that they admit exactly this Tool, and it records the design choices that the implementation tasks of the Story need. The decisions D1, D2, and D4 below carry the numbers the Story gives them; D3, the Tailscale topology, belongs to task [#95](https://github.com/grauzone-labs/sandboxed-agents/issues/95) and is only constrained here. The facts it rests on come from a spike on a live sandbox and from upstream source at a pinned commit; where a fact was only read from source, the text says so. Where this ADR relies on a source-only fact, it says so.

## What stays binding

The following statements of the earlier ADRs and of the Epic hold unchanged for every Tool. A Tool that cannot work within them is not shipped.

- **ADR-0002.** Every sandbox publishes only SSH, on host loopback. The T3 Code service binds `127.0.0.1` inside the sandbox and is published to nothing. A T3 desktop client on the host reaches it through the existing SSH path, with a port forward that the user starts, as the Azure browser login does today.
- **ADR-0003.** A sandbox has three named volumes and at most one workspace bind. A Tool adds no mount: its installation, runtime, state, credentials, logs, and relay client live in the home volume. Host credentials, SSH-agent sockets, container-engine sockets, and display sockets stay unmounted.
- **ADR-0004.** Commands come first and the sandbox name is the first argument after the command path. The `tools` commands follow this grammar: `tools enable NAME TOOL`.
- **ADR-0005.** A Tool creates no Podman object. The container and the three volumes carry the same names and labels as before, and host state records nothing about a Tool.
- **ADR-0006.** Administrative control calls run as container root with `podman exec --user=0:0`; agent work runs as `agent`, UID and GID 1000. Tool work is agent work: installation, the service supervisor, the service and every process it starts (the downloaded runtime, the resource monitor, the relay client `cloudflared`), the T3 Connect commands, and QR pairing all run as `agent`. The host starts the manager for a `tools` command directly as `agent` with `podman exec --user=1000:1000 --env HOME=/home/agent`, as it does for `agents run`, `agents login`, and `agents session`; the manager refuses any other identity. Read-only queries that `check NAME` and the lifecycle commands make as container root re-exec the trusted worker as `agent` before they read the Tool directory, as the session query does.
- **ADR-0007.** The lifecycle lock covers `up`, `start`, `stop`, `restart`, `remove`, `update`, and the SSH setup mutations, and nothing else. The `tools` commands take no lifecycle lock; they take the manager lock inside the sandbox, as the `agents` commands do, with the exceptions that [Locking](#locking) names. The lifecycle commands hold their lock while they restore a Tool service, so the restore is covered without a new lock.
- **Epic #1, threat model.** The default Podman options of a sandbox are unchanged: `--userns=keep-id:uid=1000,gid=1000`, `--user=0:0`, `--security-opt=no-new-privileges`, `--network=pasta:--no-map-gw`, the resource limits, and only SSH published. Outbound networking stays open, which is what the T3 Connect relay and the npm install rely on.
- **Epic #1, order of checks.** The ten steps stay as they are. The `tools` commands take their places in them ([Command surface](#command-surface)).

## Narrowed non-goals

Two non-goals of Epic #1 are narrowed by this ADR and in the Epic's own text. No other non-goal changes.

- *"Managed services, service supervision, and port forwarding (the term "tool" is reserved for these)"* becomes: managed services and service supervision other than the T3 Code Tool of Story #89 under Feature #99, and any port forwarding or published port beyond SSH. Every further Tool, the Tailscale Tool of [#98](https://github.com/grauzone-labs/sandboxed-agents/issues/98) included, needs its own scope decision before it is admitted. The T3 Code service is supervised by the manager inside the sandbox, binds loopback there, and is reached over SSH, over its outbound relay, or over the Tailscale topology that task #95 proves. The executable forwards no port and publishes none.
- *"Hermes Agent and DeepSeek Harness, and any install method other than an npm package"* becomes: Hermes Agent and DeepSeek Harness, and any install method other than an npm package, where the T3 Code Tool is installed as the npm package `t3`, whose launcher downloads T3 Code's own runtime from its upstream release and verifies it against that release's checksums (observed). What T3 Code then downloads into its own home at the user's request, its relay client `cloudflared` on `link` against a pinned checksum, provider CLIs, or a headless browser (source-only, read from upstream source at a pinned commit), is T3 Code's behavior inside the Tool directory and no install method of the executable. The package stays the install method, the executable adds no download of its own, and no other Tool or agent install method is admitted by this wording.

## D1: supervision without systemd

Upstream's unattended mode, `t3 service install`, needs systemd user services and lingering. The sandbox has neither: PID 1 is `sshd`, started by the image's `ENTRYPOINT`, and the manager runs per request through `podman exec`. The service is therefore supervised by the manager itself, in the same way the agent sessions already outlive the `podman exec` that started them: a process that detaches from its caller is re-parented to PID 1 and keeps running while the container runs, which the agent sessions' tmux server already relies on, and `sshd` reaps the children it inherits: after a SIGCHLD its `child_reap_all_exited` calls `waitpid(-1, …, WNOHANG)` until no exited child is left (`child_reap_all_exited` in `sshd.c`, OpenSSH 10.0 source; the image's `versions.txt` records the installed `openssh-server` version), so an orphaned service leaves no zombie.

**The service supervisor.** `tools enable` and every start of the service make the manager, running as `agent`, start itself again as the service supervisor for the Tool: a detached process in a new session, with its standard streams on the Tool's log file, that does not end when the `podman exec` ends. The supervisor:

- takes an exclusive, nonblocking `flock` on `service/supervisor.lock` in the Tool directory, retrying for two seconds past the instant shared probes of status readers, and exits zero when the lock stays taken, so a repeated `enable`, `start`, `restart`, or `up` never leaves two supervisors, and two supervisors never leave two services. Readers probe the lock with a shared lock, which conflicts only with the exclusive holder. T3 Code's own ownership lock on `userdata/server-owner.sqlite` is a backstop, not the mechanism;
- runs the service as its child in a process group of its own: the launcher `t3 serve --host 127.0.0.1 --port 3773`, with `HOME=/home/agent`, `T3CODE_HOME` set to `home/` in the Tool directory, and the npm environment the manager sets. The flags are explicit because a flag beats the environment variable and the recorded origin must not depend on an inherited variable (observed in the spike). The port is fixed: every sandbox has its own network namespace, so two sandboxes on one host never collide, and the pairing and relay paths need a stable origin;
- writes `service/state.json` in the Tool directory with the service state (`running`, `stopped`, or `failed`), the pids of supervisor and service, the start time, the last exit status, the last failure reason, and the restart count. The state is reported only together with liveness: a reader treats `running` as true only when the supervisor's lock is held and the service pid is alive, so a service that died with the container, or that was killed, never shows as `running`;
- writes the service's standard output and error to `service/service.log` and keeps the previous run's log as `service/service.log.1`; T3 Code's own trace log stays where upstream writes it, under `home/userdata/logs/`;
- restarts the service after an unexpected exit, with a delay that starts at one second and doubles up to thirty seconds. A start counts as healthy once the service has run for sixty seconds. After five consecutive starts that were not healthy, the supervisor records `failed` with the last exit status and the last lines of the log, stops retrying, and exits; the next start request begins again. The bound keeps a broken installation from looping, and `tools status` and `check NAME` make the failure visible. No live run has measured these values; they are set from these considerations only, and the implementation tests check them through injected process functions;
- stops the service on SIGTERM: it forwards SIGTERM to the launcher, which forwards it to the runtime (source-only, observed to end all three processes within 0.2 s to 1.4 s), waits up to ten seconds, then sends SIGKILL to the process group so that no child, the relay client included, survives. It then records `stopped`, releases its lock, and exits. The manager that asked for the stop waits five seconds beyond that and then kills the service's process group and the supervisor itself.

**What the lifecycle commands do.** `up`, `start`, `restart`, and `update NAME`, and `update --all` for each sandbox it updates, end with a Tool restore step, after the sandbox counts as ready (the manager answers; for `update`, after the readiness wait of ADR-0007). The host asks the manager, as `agent`, to start the service of every enabled Tool whose service is not running; a start waits up to fifteen seconds for the supervisor to report the service as running or failed, and a supervisor that is between restarts is waited for rather than started twice. For `update NAME` this runs on the replacement and, when the replacement is given up, on the restored backup container once it runs again. When a service cannot start, the sandbox keeps running, the command reports the Tool's failure, names `tools status NAME TOOL`, and exits non-zero, as `up` does for a failed agent install. A `stop` does not stop the service separately: Podman ends every process when it stops the container, and the supervisor's liveness rule makes the stale state harmless. T3 Code tolerates the stale `server-runtime.json` this leaves: its ownership lock is released by the kernel when the process dies, the next `serve` writes the file afresh, and `pair` checks that the recorded pid is alive before it trusts the file (all source-only, read from upstream source at a pinned commit).

**Where state lives.** Everything is in the Tool directory `~/.local/share/sandboxed-agents/tools/t3code`, in the home volume:

| Path | Holds |
|---|---|
| `selection.json` | The Tool selection: channel or Tool pin, installed version |
| `npm/<version>/` | One npm prefix per installed launcher version; the Tool selection names the active one. A switch or repair stages the new prefix as `npm/.next-<version>/`, and a repair sets the prefix of the same version aside as `npm/.previous-<version>/` until the move succeeded |
| `home/` | `T3CODE_HOME`: `runtime/`, `userdata/` with the database, settings, secrets, and logs, `caches/`, `tools/cloudflared/`, and the default `worktrees/` and `projects/` roots |
| `service/` | `supervisor.lock`, `state.json`, `service.log`, `service.log.1` |
| `connect.lock` | The connect lock a T3 Connect login holds ([Locking](#locking)) |

Outside it lie only the command link `~/.local/bin/t3`, which the Tool creates and removes, and the npm cache `~/.npm`, which agents share with the Tool. Host state records nothing about a Tool, so the selection survives `stop`, `start`, `restart`, and `update`, the lifecycle commands restore the service from it, and `remove NAME --volumes` removes both with the home data.

**Version switches.** `tools enable` and `tools update` with a selector that differs from the recorded one, and `tools update` on a channel whose newest release is newer than the installed one, install the new launcher into a staging prefix beside the active one, run `t3 --version` from it so that the runtime is downloaded and verified into `home/runtime/versions/<version>/`, move the prefix to `npm/<version>/`, and only then stop the running service and start it from the new prefix. A damaged installation is repaired the same way: a repeated `enable` without a selector and an `update` of a pinned selection reinstall the recorded version without resolving anything, while an `update` of a channel selection moves to the channel's newest release as always. The Tool selection and the command link are rewritten only after the supervisor reports the new service as running. When any step fails, the command stops the new service if it started, starts the previous version again, removes the new prefix and the new runtime directory, leaves the selection and the command link as they were, and exits non-zero naming the failing step, so that a failed switch keeps the previous installation, selection, and running service. The previous prefix is removed once the new service runs; previous runtime directories are removed with it. A switch that is interrupted before it reaches either end can leave an extra prefix and runtime directory behind; the next `tools enable` or `tools update` removes every prefix and runtime directory that the Tool selection does not name before it does its own work, and the service keeps running from the named one meanwhile.

## D2: the service guard

The lifecycle commands and the agent installation commands refuse without `--force` while an agent session runs, because a session's terminal state would be lost silently. The question was whether `tools update`, `tools delete`, `stop`, `restart`, and `update NAME` refuse in the same way while the T3 Code service is serving agent work.

**Decision: no service guard in the first version.** These commands stop the T3 Code service without `--force`, and `--force` keeps its one meaning, ending agent sessions. `tools update` stops the running service only after the new installation and its runtime download have succeeded, directly before it starts the service on the new version, so a failed switch leaves the previous service running. The reasons:

- T3 Code reports a thread's activity only per project. `t3 project` offers `add`, `remove`, and `rename` and no list command (observed in the spike). `t3 thread list --json` takes one project, by id or by a path inside it, and signs in to the running server as a short-lived full-access client for each call (source-only, `apps/server/src/cli/thread.ts:204-234,499-531` at `044f072`, read beside the spike's citations); the run states are `preparing`, `queued`, `starting`, `running`, `waiting`, `completed`, `interrupted`, `failed`, `cancelled`, and `rolled_back` (source-only, `packages/contracts/src/orchestrationV2.ts:453-464`). The CLI exposes no query across projects. The server's MCP endpoint does: the thread CLI combines `t3_project_list` and `t3_thread_list` internally (source-only, `thread.ts:259-270,517`), and the Tool could do the same. That path is not relied on, because it would make every `stop`, `restart`, `update`, and `tools` change issue itself a full-access client session on the server, and because the MCP tools are the interface upstream offers to agents, not a documented operator contract whose shape the pinned versions promise to keep. A guard built on a signal that the Tool cannot read completely, or that may change without notice, would refuse or pass wrongly.
- T3 Code keeps its runs in its own database with a run state `interrupted` among them (source-only, same citation), and the service ends with a reconciliation step at shutdown (observed: "shutdown reconciliation completed"). What the phone shows for a run that was cut off by a container stop is not established; the manual checklist of the Story observes it. The session guard protects a terminal state that would be lost silently; T3 Code's state is persistent.
- Agents that run in agent sessions stay protected by the existing session guard, also while T3 Code is enabled.

The documentation states that stopping, restarting, updating, or deleting interrupts work that T3 Code is driving at that moment. The Story's criterion "Decision D2 is recorded, and its guard behavior is covered by tests" is met in the negative: tests prove that these commands stop the service without `--force` and that the session guard for agent sessions still applies while T3 Code is enabled. Should upstream publish a stable query for active runs across projects, an amendment of this ADR can add the guard; until then its absence is the decision.

## Locking

The manager lock, the one in-sandbox lock that serializes agent installation and session changes, also serializes Tool changes. It is taken by `tools enable`, `tools update`, `tools delete`, `tools connect NAME TOOL link` and `unlink`, every start and stop of a Tool service, including the Tool restore step of the lifecycle commands, and `tools connect NAME TOOL logout`. A command that finds it taken refuses at once with the existing message, which now names agent and Tool changes, and nothing waits or retries. `tools status`, `tools pair`, and `check NAME` take no lock and read the Tool directory as one snapshot.

`tools connect NAME TOOL login` is long and interactive: upstream's headless login waits up to ten minutes for the user's approval. It must not hold the manager lock, or every agent change in the sandbox would be refused while a user signs in on their phone. It must not run beside `tools delete` either, because a login that completes after the Tool directory is gone would write credentials to nothing, or into a directory the delete has already passed. The property to protect is that **a delete never leaves credentials behind**. The decision:

- Each Tool has a `connect.lock` in its Tool directory. `login` takes an exclusive, nonblocking `flock` on it for the whole login, and only after it holds the lock does it check that the Tool is enabled and start the upstream command; a Tool directory that is missing before the lock counts as not enabled. The lock is released when the login exits, also when the process dies.
- `tools delete` takes the manager lock first and then the same `connect.lock`, also exclusive and nonblocking, and holds both until the Tool directory is gone. A delete that finds the connect lock taken refuses before removing anything and says that a T3 Connect login is in progress. A login that finds it taken refuses and says that another Tool change is in progress.

Because the login holds the lock from before its enabled check until after the upstream command exits, and the delete holds it from before its first removal until after its last, no credential can be written by a login during a delete, and no delete can start while a login runs. `logout` and `unlink` are short and run under the manager lock alone; a delete that follows them finds no login in progress. `link` runs under the manager lock too and restarts the service once the upstream command has succeeded, because the link takes effect at the next server start (source-only, read from upstream source at a pinned commit).

## Network boundary

The T3 Code service listens on `127.0.0.1:3773` inside the sandbox and nowhere else. The three paths to it are:

- **SSH**, for a desktop client on the host: the user forwards the port through the sandbox's sshd, as for a browser login today. The executable adds no publish and no forward.
- **The T3 Connect relay**, for the phone through the T3 account: the service's relay client opens outbound connections only, to the relay on TCP and UDP port 7844 and over HTTPS, and the relay delivers to the service on loopback (observed from the spike that the path is open from a sandbox; the delivery address is source-only). No inbound port exists.
- **The Tailscale topology** that task #95 proves (decision D3 of the Story, a mandatory requirement): phone QR pairing issues a code only for the tailnet HTTPS origin, which is the only phone-reachable origin in the evidence. D3 is decided in its own ADR or amendment once a live run proves it within the sandbox rules; this ADR fixes only the constraint that whatever D3 chooses adds no `--publish`, bind, device, capability, or network-mode change, installs nothing on the host, requests neither `/dev/net/tun` nor `NET_ADMIN`, and uses no Tailscale Funnel.

Nothing in the sandbox's Podman options changes for a Tool. The consequences of ADR-0002 and ADR-0003 hold as written. The service never binds another address unless D3 records a need for one inside the sandbox.

## D4: user worktrees and complete delete

T3 Code creates Git worktrees for its threads at `<T3CODE_HOME>/worktrees/<repo>/<branch>` and repositories created in the app under `<T3CODE_HOME>/projects/`, both under `home/` and therefore inside the Tool directory (source-only for the layout; observed that `worktrees/` is created at start). The worktree location is a machine-wide server setting that the user can change in T3 Code at any time, and earlier locations stay managed (source-only). These directories are user project files. A delete that removed the Tool directory wholesale would take them along, and a worktree that is moved without Git's help is left with stale absolute links in both directions ([git-worktree(1)](https://git-scm.com/docs/git-worktree), quoted from Git's manual).

**Decision: relocate at delete, with Git's own commands, and refuse when that cannot be verified.** `tools delete` runs these steps, in this order, after it has stopped the service and before it removes anything:

1. **Inventory.** It walks the whole Tool directory and lists every directory that holds a `.git` entry: a file for a linked worktree, a directory for a repository. The walk excludes nothing, so a worktree in an unusual place inside the Tool directory is found too, and a false positive leads to a refusal, never to a removal.
2. **Relocate.** The target root is `/home/agent/t3code-files/`, kept by the delete, with each entry's path relative to `home/` preserved below it: a worktree moves to `/home/agent/t3code-files/worktrees/<repo>/<branch>`, a repository to `/home/agent/t3code-files/projects/<name>`. A linked worktree moves with `git worktree move`, run in the repository it belongs to (found through `git rev-parse --git-common-dir`), which updates the link in the repository and the `.git` file of the worktree. A repository moves with a rename, followed by `git worktree repair` run inside it, with the new paths of its linked worktrees as arguments when those moved too. Both commands are Git's documented way to relocate without leaving stale links.
3. **Verify.** For every moved entry, `git worktree list` in the repository shows the new path and `git rev-parse --git-dir` succeeds in the moved directory. The output of the delete names every moved path.
4. **Remove.** Only now does the delete remove the Tool directory and the command link ([Delete scope](#delete-scope)).

A failure in step 2 or 3 stops the delete before step 4. The command reports what moved and what did not, exits non-zero, removes nothing, and a rerun continues from the inventory, which finds what is left. A target path that already exists is a failure too, not an overwrite. There is no option to skip the relocation or to remove worktrees: the default is the only behavior, and it never deletes or damages a user worktree. A worktree whose location the user set outside the Tool directory is never touched by the delete.

The Story's rules are met under this option: every Tool-owned runtime, metadata, and credential file is removed even where worktrees lived inside `T3CODE_HOME`, because the directory is removed wholesale once nothing user-owned remains in it; no worktree is deleted or damaged, because Git itself moves and repairs the links and the result is checked; and a delete that cannot meet both rules refuses before it removes anything. T3 Code's own record of the worktree paths, inside its database, is Tool-owned and goes with the Tool. A later `tools enable` starts from scratch and knows nothing of the moved worktrees, which remain plain Git worktrees of their repositories.

## Delete scope

`tools delete NAME t3code` removes:

- the T3 Code service, by stopping its supervisor, and the supervision record;
- the T3 Connect login, best effort: it runs `t3 connect logout` first, which also asks the relay to revoke the link, and reports a relay-side failure as a warning without stopping the delete;
- the `t3` launchers in the Tool's npm prefixes and the command link `~/.local/bin/t3`;
- `home/`, which is `T3CODE_HOME`, with the downloaded runtimes, `cloudflared`, T3 Code's user data, database, settings, `service.env`, secrets and credentials, pairing codes and device sessions, caches, and logs, after the user project files have left it (D4);
- the Tool selection with its channel or Tool pin, the service state and logs, and with them the whole Tool directory;
- any Tailscale state or Serve mapping that the Tool owns, in the way D3 records.

It keeps: the workspace; every agent with its installation, pin, and credentials; every integration's configuration and credentials; the shared runtimes of the image, such as Node.js; the shared npm cache `~/.npm`; and every user worktree and repository, relocated as D4 describes and named in the output. `t3 uninstall` is not used, because it keeps `userdata` and `service.env`, and the delete removes the directory tree itself.

A second `tools delete` finds no Tool directory and no command link, says so, and exits zero. An interrupted delete reports what remains and exits non-zero; a rerun completes it, because every step is idempotent and the inventory of D4 runs again. `tools enable` after a delete starts from scratch: channel `latest`, no pin, no login, no paired device.

## Command surface

The final command words replace the proposed ones of the Story. Each behavior of the Story keeps its acceptance criterion under the new word. The user-facing semantics of each command are owned by the [command reference](../command-reference.md#tool-commands); this table fixes the words and what each one wraps.

| Command | Wraps upstream |
|---|---|
| `tools enable NAME TOOL [--channel latest\|nightly \| --version X]` | `npm install` of the Tool's package at the resolved exact version, then `t3 --version` as the runtime prefetch |
| `tools update NAME TOOL [--channel latest\|nightly \| --version X]` | the same install at the version the wrapper resolves |
| `tools status NAME TOOL` | `t3 connect status --json`, `t3 auth session list`, the Tool directory |
| `tools connect NAME TOOL login` | `t3 connect login --headless` |
| `tools connect NAME TOOL link` / `unlink` | `t3 connect link --headless` / `t3 connect unlink` |
| `tools connect NAME TOOL logout` | `t3 connect logout` |
| `tools pair NAME TOOL [--ttl DURATION]` | `t3 pair --tailscale [--ttl DURATION]` |
| `tools pair NAME TOOL --revoke` | `t3 auth pairing list` and `revoke` per code |
| `tools delete NAME TOOL` | more than `t3 uninstall` |

Two words changed from the proposal, both for the glossary's sake. QR pairing is not T3 Connect, so `pair` is its own command and no longer lives under `connect`; keeping it there would blur the distinction that the documentation has to make between the account login and the one-time pairing. The flag `--tailscale` is gone, because the tailnet origin is the only origin the command issues; a flag that selects the only behavior would be required and would say nothing. `tools status` reports the path instead. `--channel` with `--version`, and `--ttl` with `--revoke`, are usage errors. No `tools` command takes `--force`, because D2 records no service guard, and `enable` needs no repair flag: the launcher re-downloads a runtime whose completion marker is missing or wrong (observed), and a repeated npm install of the same launcher version replaces the package in place, which no spike run exercised.

Places in the order of checks that Epic #1 makes binding:

1. **Step 1.** An unknown Tool name, an unknown `connect` action, a `--channel` value other than `latest` and `nightly`, a `--version` that is not an exact `MAJOR.MINOR.PATCH` with an optional prerelease, `--channel` together with `--version`, and `--ttl` together with `--revoke` are usage errors before Podman is called. While the Tool is not delivered, `tools` itself is an unknown command.
2. **Step 7.** Every `tools` command needs a running sandbox and names `start NAME` on a stopped one.
3. **Step 8.** First a manager that does not answer; then, for every command but `enable`, `status`, and `delete`, a Tool that is not enabled, which names `tools enable NAME TOOL` (`status` reports the Tool as not enabled and `delete` finds nothing to remove, both with exit status zero); then, for `enable` and `update` with `--version`, a well-formed version that npm does not publish, before anything is installed or recorded; then a service that is not running, for `pair` without `--revoke` (revocation acts on the database and works with the service stopped, observed); then a missing Tailscale prerequisite, for `pair` without `--revoke`, with the distinct messages of D3.
4. **Step 9.** `tools connect NAME TOOL login`, `tools connect NAME TOOL link`, and `tools pair NAME TOOL` without `--revoke` need an interactive terminal and fail without one before changing anything.

There is no step 10 for a `tools` command, because D2 records no service guard. The command reference lists the commands as planned until a task delivers them; the executable rejects them as unknown until then, as it rejects undelivered catalog entries.

## Considered options

- **Autostart from the container's `ENTRYPOINT`.** The entrypoint could read the Tool selection and start enabled services when the container starts. Rejected: it would make PID 1's script read home data and change identity before `sshd` runs, couple the image to the Tool catalog, and leave `up` no way to report a Tool failure as it reports a failed agent install. The manager already has a post-readiness step for exactly this.
- **Running the service in a tmux session**, on the private tmux server the agent sessions use. Rejected: it would appear as an agent session to the session guard, tmux restarts nothing after a crash and records no exit status, and a second socket would duplicate the session machinery for one process.
- **Upstream's `t3 service install`.** Rejected: it needs systemd user services and lingering, which the image does not have and will not get; an init system in the sandbox would be a second supervisor beside the manager.
- **A long-lived manager daemon.** Rejected: ADR-0001 chose a manager that runs per request through `podman exec`; a daemon would need its own supervision and a control channel, for one service.
- **A service guard with `--force`, as for agent sessions** (D2). Rejected for now: T3 Code offers no stable query for active runs across all projects at the pinned versions, and it records interrupted runs itself; see D2.
- **A guard whenever the service runs.** Rejected: every `stop` of a sandbox with T3 Code enabled would need `--force`, which empties the flag of meaning.
- **Holding the manager lock during `tools connect … login`.** Rejected: a login waits up to ten minutes for the user, and every agent change in the sandbox would be refused meanwhile. The connect lock protects the one property that matters, that a delete never leaves credentials behind.
- **Configuring T3 Code's worktree location outside the Tool directory from the start** (D4). Rejected as the sole mechanism: the setting lives in T3 Code's settings file, whose format is source-only and may change, and the user can move the location back inside T3 Code at any time, so a delete must handle worktrees inside the Tool directory in any case. Relocation at delete handles both, and leaves upstream's defaults as they are. A later task may add the setting as a convenience; the delete's rules do not depend on it.
- **Detaching worktrees at delete**, for example with `git worktree remove` or by leaving the directories in place and removing only the Tool's other files. Rejected: `git worktree remove` deletes the files, and leaving user directories inside a directory that is otherwise removed would make the Tool directory impossible to remove completely.
- **A `--keep-worktrees` or `--delete-worktrees` option.** Rejected: the Story forbids a destructive default and asks for a delete that refuses when it cannot keep both rules; an option would make the user choose between a complete delete and their files.
- **A fixed service port chosen from a free range** instead of 3773. Rejected: the sandbox has its own network namespace, so the upstream default collides with nothing outside, and a stable origin keeps the pairing URL and the relay delivery address predictable.
- **Keeping `pair` under `connect` and keeping `--tailscale`.** Rejected: see [Command surface](#command-surface).

## Consequences

- The manager gains a Tool catalog, a `tools` request family, and the service supervisor; the host executable gains the `tools` commands and the Tool restore step in `up`, `start`, `restart`, `update NAME`, and `update --all`. `update --all` reports a sandbox whose Tool service fails to start, continues with the other sandboxes, and exits non-zero, as it does for any sandbox it could not update. Tasks [#92](https://github.com/grauzone-labs/sandboxed-agents/issues/92) to [#97](https://github.com/grauzone-labs/sandboxed-agents/issues/97) of the Story deliver them.
- The base image cannot run T3 Code today: the runtime needs `libatomic.so.1`, which only the `native` toolchain image provides (observed). Task #92 decided this: the base image gains `libatomic1`, so `tools enable` needs no toolchain, and the [images page](../images.md#base-image) names the library and its reason. The alternative, requiring a toolchain that provides it and naming the `update NAME --with …` command otherwise as the Azure integrations do for the `azure` toolchain, was not taken, because every sandbox would otherwise need a rebuild for one small runtime library.
- `check NAME` asks the manager for the state of every enabled Tool service and reports a `failed` service as a problem. `list` is unchanged.
- The manager lock's refusal message names agent and Tool changes. The glossary entries Tool, Tool catalog, Tool directory, Tool selection, Channel, Tool pin, T3 Code service, Service supervisor, T3 Connect, T3 Connect link, and QR pairing in `CONTEXT.md` carry this vocabulary.
- Stopping, restarting, updating, or deleting interrupts work that T3 Code is driving at that moment, and the documentation says so.
- `SECURITY.md`'s limit "No managed services or port forwarding" and the 1.0.0 release notes describe the state before this Tool ships; task #97 rewrites them when the Tool is delivered, stating the three network paths and the difference between T3 Connect login, QR pairing, and agent provider login.
- Decision D3, the Tailscale topology, remains open and blocked on a live run within the sandbox rules (task #95). Until it is proven, phone QR pairing is not delivered and the Story stays open.
