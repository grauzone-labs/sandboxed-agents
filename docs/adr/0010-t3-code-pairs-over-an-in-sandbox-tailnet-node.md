# T3 Code pairs over an in-sandbox tailnet node in userspace networking mode

Phone QR pairing of the T3 Code Tool needs an origin that a phone can reach. Upstream's `t3 pair` issues a code for the server's bind address unless `--tailscale` makes it publish the server through Tailscale Serve and issue the code for the node's tailnet HTTPS origin (Story [#89](https://github.com/grauzone-labs/sandboxed-agents/issues/89), E12 and E16). Inside a sandbox the bind address is loopback, so the tailnet origin is the only phone-reachable origin in the evidence, and task [#95](https://github.com/grauzone-labs/sandboxed-agents/issues/95) has to find a topology that gives the sandbox such an origin within the sandbox rules. This is decision **D3** of the Story, which [ADR 0009](0009-tools-run-as-manager-supervised-services.md) constrained and left open.

The decision is **accepted** on the record of the live run of #95 on 2026-10-23 and 2026-10-24, at revision `aace960`, on a Linux host (rootless Podman 5.4.2) and a Windows 11 host (Podman 6.1.4, WSL 2.7.12). On both hosts each of two sandboxes signed its own node in through the user's browser and got its own origin, `https://live-a.<tailnet>.ts.net/` and `https://live-b.<tailnet>.ts.net/`; a phone in the same tailnet scanned each QR code and opened the matching sandbox's T3 Code, and `tools delete` signed each node out and removed everything. The run added no publish, device, capability, or network-mode change. Two checks of the planned run are not on record yet and stay with #95: that an origin works again after `restart` and after `update NAME` without a second pairing, and whether Serve keeps working under `--shields-up`. On Linux the run first lost its sandbox whenever the user's last login session ended, because the host had no lingering; that is a host prerequisite of every rootless sandbox and not part of this decision ([#118](https://github.com/grauzone-labs/sandboxed-agents/issues/118)).

## Hard limits

Every candidate was judged against the limits the Story and the Epic fix, and the chosen one keeps all of them: the executable installs nothing on the host; the sandbox gets no `/dev/net/tun`, no `NET_ADMIN` or other capability, no host socket mount, no published port beyond SSH, and no change of its network mode; Tailscale Funnel is not used; and the executable adds no download of its own beyond the npm package `t3` (Epic #1 non-goals as ADR 0009 narrowed them). Offline tests check the Podman arguments of `up`, `tools tailscale`, and `tools pair` against these limits; the live run shows them on real hosts.

## Candidates

1. **An in-sandbox `tailscaled` in userspace networking mode, run as part of the Tool.** `tailscaled --tun=userspace-networking` needs no TUN device and no capability: it runs as an unprivileged user with its state directory and its local API socket wherever it is told (`cmd/tailscaled/tailscaled.go` at Tailscale v1.104.2, flags `--tun`, `--statedir`, `--socket`). Tailscale Serve is implemented inside `tailscaled`, which terminates the tailnet HTTPS connection with a certificate it provisions and proxies to a local address, and Tailscale's own container images run in exactly this mode with Serve (Tailscale documentation, Serve and userspace networking). Upstream's `t3 pair --tailscale` only needs a `tailscale` command on its PATH that reaches that `tailscaled` (`packages/tailscale/src/tailscale.ts` at `044f072`: `tailscale status --json`, `tailscale serve --bg --https=443 http://127.0.0.1:3773`). The node signs in through a browser on any device: `tailscale up` prints a login URL and waits, so no auth key is needed on the host or in the sandbox. Open questions this ADR answers: how the binaries get into the sandbox without a download by the executable, and how the node survives the lifecycle. **Chosen.**
2. **A user-managed host Tailscale with a route to the sandbox.** The service listens on the sandbox's loopback, which the host reaches only through the published SSH port. A host-side route would need either a second published port, a host process run by the executable that keeps an SSH forward and a `tailscale serve` mapping alive, or a change of the user's host Tailscale configuration without an explicit opt-in; each breaks a hard limit or ADR 0002. Moreover `t3 pair --tailscale` inside the sandbox cannot see the host CLI, so the QR origin would have to be assembled by the wrapper from host state, and two sandboxes on one host would share one node and have to share one origin by port. **Rejected.**
3. **Tailscale downloaded by the Tool at `tools enable`**, as T3 Code downloads its own runtime and `cloudflared`. Tailscale publishes static tarballs with checksums, but a download by the executable is exactly what the Epic's install-method non-goal excludes, and the Tailscale Story [#98](https://github.com/grauzone-labs/sandboxed-agents/issues/98) owns the decision to admit a checksum-verified download for a general tailnet device. **Rejected for this Story**; #98 may revisit it.

## Decision D3

Tailscale is a **managed part of the T3 Code Tool**, not a user-managed prerequisite. The Tool runs its own **tailnet node**: a `tailscaled` in userspace networking mode, signed in to the user's tailnet as a device of its own per sandbox. The binaries come with the base image, from Tailscale's Debian 13 package repository behind a fingerprint-pinned signing key ([images](../images.md#signing-key-checks)), so the executable downloads nothing of its own; the image starts no Tailscale process. This is no second install method: the Tool is still installed as the npm package `t3`, and the image carries Tailscale as it carries Node.js and `libatomic1`, shared runtimes a Tool relies on, which ADR 0009 and the Epic's non-goal now say. The following rules hold:

- **Lifetime.** The node exists from `tools tailscale NAME t3code login` until `tools tailscale NAME t3code logout` or `tools delete NAME t3code`. A sandbox whose Tool never signed in runs no Tailscale process and keeps no Tailscale state. The node's state directory inside the Tool directory, `tailscale/state/`, is the record that the node exists.
- **Process.** The node is `/usr/sbin/tailscaled --tun=userspace-networking --statedir=<Tool directory>/tailscale/state --socket=<Tool directory>/tailscale/tailscaled.sock --no-logs-no-support`, run as `agent` by the service supervisor of ADR 0009 as a second supervised process of the Tool, with its own lock, record, and logs in `tailscale/service/`, the same restart policy, and the same restore by `up`, `start`, `restart`, and `update`. Log upload to Tailscale is off; the node's own log stays in the Tool directory.
- **The Tool's `tailscale` command.** `bin/tailscale` in the Tool directory is a one-line wrapper that calls `/usr/bin/tailscale --socket=<the node's socket>`. The Tool's `tools pair` runs upstream's `t3 pair --tailscale` with that directory first on `PATH`, so upstream's `tailscale status --json` and `tailscale serve --bg --https=443 http://127.0.0.1:3773` reach the Tool's own node. The CLI reads the socket only from its `--socket` flag (`cmd/tailscale/cli/cli.go` at v1.104.2), which is why the wrapper exists.
- **Sign-in.** `tools tailscale NAME t3code login` needs an interactive terminal, starts the node when it is not running, and runs `tailscale up --hostname=<sandbox name> --accept-dns=false --accept-routes=false` on the caller's terminal: upstream prints the login URL, which carries a one-time code and is sensitive, intentional output, and waits until the user has approved the device in a browser on any device. The hostname is the sandbox's name as a DNS label (lowercased, other characters replaced by hyphens), so the MagicDNS name reads as the sandbox and two sandboxes on one host get distinct names; Tailscale appends a counter when a name is taken. No auth key is accepted from arguments or the environment. A login that fails or is interrupted on a node it created removes that node again, so nothing remains; a login on an existing node keeps it. A node that is already signed in is reported, and `up` is not run again.
- **Sign-out.** `tools tailscale NAME t3code logout` runs `tailscale logout` as a best effort, starting a stopped node for it, then stops the supervisor and removes `tailscale/` and the wrapper. A failed sign-out is a warning: the device then stays listed in the tailnet admin console until it expires or is removed there. Without a node the command says so and exits zero.
- **Pairing.** `tools pair NAME t3code [--ttl DURATION]` takes no lock and refuses, with one message each and before anything changes: a service that is not running, a node that is absent, stopped, failed, or not signed in (naming `tools tailscale NAME t3code login`), a tailnet without a MagicDNS name or without HTTPS certificates (naming the admin console's DNS page), a node that is offline, and a Serve mapping on HTTPS port 443 that fronts another target than the service's `http://127.0.0.1:3773` (naming `logout` and `login`, which reset the node's Serve configuration). Then upstream runs on the caller's terminal and prints its QR code, URL, token, and expiry; the wrapper adds that the code is single-use and valid until the printed expiry, that the command does not confirm the scan, and that paired devices appear in `tools status`. Upstream probes the origin from inside the sandbox, which in userspace networking mode has no route to the tailnet, so its note that the endpoint has not answered yet is expected; the wrapper checks the node's own Serve configuration instead, and when the mapping did not take it revokes the code it issued and exits non-zero. An origin that is unreachable for a reason the pre-checks cannot see is therefore caught only after upstream has printed its code, because upstream creates the mapping and mints the code in one command; the code is revoked at once and the command exits non-zero, so the Story's "issue no code" holds in effect: no usable code survives. A code that a failed or interrupted upstream run minted is revoked the same way, and earlier codes stay. `--ttl` takes a number with `ms`, `s`, `m`, `h`, `d`, or `w`. `tools pair NAME t3code --revoke` revokes every unused code through upstream's `auth pairing list --json` and `revoke <id>`, with or without a running service, and needs no terminal.
- **Serve mapping and origin.** Upstream's `pair --tailscale` creates the mapping `https://<MagicDNS name>/` → `http://127.0.0.1:3773` with `--bg`, which Tailscale persists in the node's state and resumes after a restart of `tailscaled`, so the origin works again after `stop`/`start`, `restart`, and `update NAME` without a second pairing; `tools status` reports the mapping and names `tools pair` when it is missing. Each sandbox's node is its own device with its own name and certificate, so two sandboxes on one host have distinct origins and each origin reaches only its own service. Funnel is never enabled.
- **Status.** `tools status NAME t3code` reports the node as absent, or as `running`, `stopped`, or `failed` with its failure and log, and for a running node its sign-in state, MagicDNS name, origin, Serve mapping, whether the tailnet grants HTTPS certificates, and whether the node is online, from `tailscale status --json` and `tailscale serve status --json`, plus the paired devices from upstream's `auth session list --json`. `check NAME` names the node on the Tool's line and counts a failed node as a problem.
- **Delete.** `tools delete NAME t3code` signs the node out as a best effort, stops it, and removes its state, its Serve configuration, and the wrapper with the Tool directory, which settles the open item of ADR 0009's delete scope.

## What this changes about the sandbox's reach

In userspace networking mode `tailscaled` forwards an inbound TCP connection that a tailnet peer makes to the node's tailnet address to the same port on the sandbox's loopback (`wgengine/netstack`, Tailscale v1.104.2; Story #98's sources). While the node is signed in, a device of the user's tailnet that the tailnet's access policy allows can therefore reach the sandbox's loopback listeners through the node: `sshd` on port 22, which accepts only the sandbox's key, and the T3 Code service on port 3773 over plain HTTP, which T3 Code's own session and pairing tokens protect, besides the HTTPS Serve origin on port 443. This reach exists only from the user's own tailnet, only while a node is signed in, and is governed by the tailnet's access policy, which the user administers; the host and the public internet gain nothing. The documentation states this as plainly as the protections, and `SECURITY.md` gets the statement in task #97 together with the Tool's other network paths. Story #98 decides a stricter incoming port policy for a general tailnet device; this ADR does not preclude it, and the `--shields-up` preference of `tailscale up` is checked in the live run as a candidate, since Tailscale's documentation does not say whether Serve keeps working under it.

## Considered alternatives

- **Running the node always while the Tool is enabled.** Rejected: a user of the T3 Connect path alone would carry a `tailscaled` and a tailnet device for nothing; the node exists from login to logout instead.
- **A separate `tools pair --login` or sign-in inside `tools pair`.** Rejected: the Story requires a missing or signed-out Tailscale to fail with the fix named and to change nothing, and the sign-in starts a supervised process under the manager lock while `pair` takes none; `tools tailscale NAME t3code login|logout` is its own command, with the product's name as the command word as `tools connect` has T3 Connect's.
- **Letting the service itself serve with `t3 serve --tailscale-serve`.** Rejected: upstream removes that mapping at every graceful shutdown and recreates it at start, which couples the origin's availability to the service's and makes the node a prerequisite of the service; the persistent mapping of `pair --tailscale` keeps the two independent.
- **Checking the origin's reachability from inside the sandbox through the node's local proxy.** Not done: the sandbox has no route to its own tailnet address without a TUN device, and whether `tailscaled`'s outbound proxy can dial the node itself is not established; the live run from a tailnet client is the reachability proof, and the Serve configuration is the offline check.
- **Keeping the node's state outside the Tool directory for Story #98 to share.** Rejected for now: the Story requires `tools delete` to remove every Tool-owned Tailscale state, and #98's own decision will say whether a general node takes over this one's place; the state layout under `tailscale/` is small enough to move then.

## Consequences

- The base image grows by the `tailscale` package and its dependencies `iptables` and `iproute2`; a sandbox created from an earlier image needs `build` and `update NAME` before `tools tailscale … login` works, and the login says so.
- The command surface of ADR 0009 gains `tools tailscale NAME TOOL login|logout`; `login` takes the manager lock and needs a terminal, `logout` takes the lock. `tools pair` keeps its place: no lock, a terminal for the issuing form only.
- `CONTEXT.md` gains the terms tailnet node and tailnet origin, and the user documentation names the Tailscale admin console settings a pairing needs: MagicDNS and HTTPS certificates.
- The node's device appears in the user's tailnet admin console under the sandbox's name and stays there after a failed sign-out until it expires or is removed by hand.
- Decision D3 is accepted on the live run of #95. The Story's criteria for the origin after `restart` and `update NAME` stay open until that check is on record.
